## Context

Draft 0.2 proposed iOS/iPadOS 18+ and macOS 14+ (D01) and asked that the exact non-beta Xcode be selected and recorded at kickoff (Section 6.3). The development Mac had Xcode 27.0 with the iOS 27 SDK and simulator runtimes for iOS 26.5 and 27.0 only, so iOS 18 could not be tested without additional runtimes or hardware, and iOS 18 is two major releases old at kickoff.

On 18 October 2026 at 07:28 NZDT the build Mac's Xcode updated itself from the Mac App Store to Xcode 27.1 (27A9275), and no Xcode 27.0 remained. From then `Scripts/ci.d/12-dependency-lock.sh` failed its toolchain check on this Mac whatever the commit, every repository check passing (integration log 9.5), and the Git LFS adoption, the M0 final review and both rounds of its fix were built and tested under 27.1. The product owner's question PO-35 (runbook decision D-3) put the choice: reinstall 27.0, or pin 27.1.

## Decision

**Deployment targets.** iOS and iPadOS 26.0; macOS 26.0 for the Mac companion. Packages declare `.iOS(.v26), .macOS(.v26)`.

**Toolchain.**

| Item | Pinned value |
| --- | --- |
| Xcode | 27.1, build 27A9275 (`/Applications/Xcode.app`), since 20 October 2026; 27.0, build 27A266a, from kickoff until then |
| Swift compiler | Apple Swift 6.4 (swiftlang-6.4.0.34.1, clang-2100.3.34.1), the same in 27.0 and 27.1 |
| SDKs | iOS 27.1, iOS Simulator 27.1, macOS 27.0 (Xcode 27.0 had iOS 27.0, iOS Simulator 27.0, macOS 27.0) |
| Simulator runtimes | iOS 26.5 (23F77), the default test runtime because it is closest to the floor; iOS 27.0 (24A434). Unchanged by 27.1, which brought no iOS 27.1 runtime |
| Project generation | XcodeGen 2.46.0 (`project.yml` per app or spike; ADR-0002) |
| Package manifests | `swift-tools-version: 6.2`, Swift 6 language mode, complete strict concurrency checking |
| Build host | macOS 26.6.2 (25G83), Apple M5 Max |

Scripts select Xcode through `DEVELOPER_DIR` (`Scripts/lib/env.sh`) and never change the machine's `xcode-select` setting. `sylvia_check_xcode` warns when the active build differs from the pin, and `Scripts/ci.d/12-dependency-lock.sh` fails on it (ADR-0014), naming the installed build. Since 20 October 2026 the drop-in compares the whole build line, so a build that only extends the pinned number (27A9275a) fails too; until then it searched for the pinned text, which such a build contains, and its failure named the first line of `xcodebuild -version` instead of the build (review of the re-pin round, TC-02). The pin is recorded together in this table, `SYLVIA_XCODE_BUILD_PINNED` in `Scripts/lib/env.sh`, the toolchain of `Docs/Licenses/inventory.json`, the Xcode guard of `.github/workflows/ci.yml` and `CLAUDE.md`'s toolchain line, and changes in all of them at once (ADR-0014 section 6). `12-dependency-lock` compares each of the others with the inventory's pin, this table's Xcode row included; until 20 October 2026 it compared `env.sh` alone, so a re-pin that missed the workflow's guard passed every local check (TC-08).

**The re-pin of 20 October 2026 (PO-35, D-3).**

- *Options.* (a) Confirm 27.0: reinstall it on the build Mac and repeat the complete CI under it, because the code changed since 14 October 2026 had been built only under 27.1. (b) Name 27.1 as the pin, changing the records above together; the evidence of 14 October stays recorded under 27.0. The recommended default was (b), on a condition: at `dc81fce` the gate summary's PO-35 row recommended it "once the release notes show 27.1 is a release build" (`Docs/Stage0/M0-gate.md` Section 4.1), and the runbook's D-3 "once Apple's release notes show 27.1 (27A9275) is a release build" (`Docs/Stage0/M0-device-runbook.md` Section 6), while the amendments' row still recommended (a) after a check of Apple's release notes. (These words were left out of this record until 20 October 2026, when the review of the re-pin round found the condition dropped from every record: TC-01, R8-03.)
- *Decision and its basis.* Asked for a call on PO-35, with the recommendation to re-pin to 27.1, under which every drop-in but the toolchain check had passed, and to turn off Xcode's automatic updates, the product owner replied on 20 October 2026: "don't know how to pin xcode". The message the owner answered, as relayed to the agents by the workflow, gave the recommendation without its condition. The reply did not name an option. The workflow took it as accepting the recommended option (b), which needs nothing done in Xcode: the pin is the repository's record of the build its checks expect, and this change makes that record 27.1. If that is not what the owner meant, option (a) is still open, and the pins change back together. The condition was not met: Apple's release notes have not been read (next item), so the record of the decision rests on the reading of the reply, and the pin on the circumstantial evidence below, until the technical lead's check (Open items). *(22 October 2026: the owner confirmed (b) on the M0 decision page, so the decision no longer rests on a reading of the reply and option (a) is closed; the pin's release status still rests on the evidence below until the technical lead's check.)*
- *Why (b).* 27.1 is what the build Mac has and what the latest code was built and tested with: in the M0 final fix's second round every drop-in but the toolchain check passed under it, G0.4's clock tests and G0.5 recovery's class-B readback included (`Docs/Stage0/M0-gate.md` Section 2.10). (a) would repeat that work under an older build.
- *Is 27.1 a release build?* Its build number, 27A9275, does not follow Apple's beta numbering pattern (a four-digit number beginning with 5, as in 17A5241e); the app is `Xcode.app`, not `Xcode-beta.app`; and the Mac App Store installed it (its bundle carries the App Store's receipt, `Contents/_MASReceipt/receipt`), which distributes Xcode's releases, while betas come from Apple's developer site. That points to a release but is not Apple's statement: Apple's release notes were not read in this change, which used no network, nor at the review of the re-pin round (20 October 2026), which used none either. Whether 27A9275 is the release, and not a beta or a release candidate, is the open item of the technical lead below; if it is not, PO-35 goes back to the product owner.
- *What changed with it, and what was checked* (20 October 2026; `Docs/Stage0/evidence/M0-Integration/repin-27.1/`; integration log section 13): `Scripts/lib/env.sh`, the inventory's toolchain and host-tool rows and `third-party-inventory.md`, the workflow's Xcode guard (which still stops a runner without the pinned build, with an error that names it), `CLAUDE.md`'s toolchain line, ADR-0002's CI paragraph, ADR-0014's notes, plan Section 6.3 (A01) and the Stage 0 records that named 27.0 as the pin. As ADR-0014 section 6 asks of a toolchain change, `xcode-settings.py` was run against 27.1: its output is the same as 27.0's, line for line, so the dependency check's setting lists need nothing new (`xcode-settings-compare.log`). `12-dependency-lock` failed on its toolchain line alone before the change and passes after it (`12-dependency-lock-before.log`, `12-dependency-lock.log`).
- *Which Xcode the evidence was produced on.* The Stage 0 gate evidence was produced on Xcode 27.0 (27A266a): the eight gate reports and their runs, M0 integration and M0 assembly, with its complete CI runs of 14 October 2026. The Git LFS adoption (19 October 2026), the M0 final review and both rounds of its fix (19 and 20 October 2026), this re-pin, and the review of it and that review's fix (20 October 2026) ran on Xcode 27.1 (27A9275). Each record keeps the Xcode it names; none is rewritten.
- *Keeping the build Mac on the pin.* The App Store's automatic app updates were on when this change was made (`defaults read /Library/Preferences/com.apple.commerce AutoUpdate` printed 1, read-only, `toolchain-state.log`), so another Xcode release would replace 27.1 the same way. Turning them off is the owner's action, not an agent's: in the App Store app, App Store > Settings, clear Automatic Updates; or in System Settings > General > Software Update, the information button beside Automatic Updates, turn off the App Store's application updates. These are the setting names macOS 15 and later show, not checked on this Mac (no agent operates its settings); afterwards the same `defaults read` should print 0, which was not verified either. If Xcode changes anyway, `12-dependency-lock` fails naming the new build, and the choice of PO-35 comes back. *(22 October 2026: the product owner reported the automatic updates turned off ("auto updates is confirmed disabled", PO-35's note on the M0 decision page). The same read-only `defaults read` printed 0 at 06:30 UTC that day, and the installed Xcode was still 27.1 (27A9275), `Xcode.app` unchanged since 18 October 2026 (`Docs/Stage0/evidence/M0-Decisions/adrs/app-store-updates.log`, written by `commands/app-store-updates.sh` there). The setting's name in the App Store app was still not looked at by an agent.)*

## Consequences

- SwiftUI and platform APIs introduced through iOS 26 and macOS 26 can be used without availability checks.
- iOS 26 runs on iPhone 11 and later and on the iPhone SE (2nd generation), so the oldest supported iPhone the product owner named on 22 October 2026, the iPhone 11 Pro (D-1 (b)), is supported; its A13 is older than the iPhone 12-class baseline's A14, so every budget measured on it is stricter, and the 375 × 667 pt floor stays a simulator check. (Until 22 October 2026 this line read: "iOS 26 runs on iPhone 11 and later, so the iPhone 12-class baseline remains supported.")
- Building against the iOS 27 SDK (27.1 since the re-pin) gives system bars the Liquid Glass treatment. Sylvia's chrome is its own opaque component per Section 4.4.7, so that change does not reach Sylvia's screens; any system surface Sylvia still presents (menus, alerts, share sheets) follows the system.
- Results on iOS 26.0 through 26.4 are untested; the 26.5 runtime is the closest available. For App Transport Security no claim about iOS 26.0 is needed since the product owner's decision D-9 (b) of 22 October 2026: `EndpointPolicy`, not ATS, is the cleartext gate on every OS version (ADR-0011).
- An Xcode update on the build Mac stops `12-dependency-lock` until the owner either reinstalls the pinned build or changes the pin, with every record of it, in one change (since 20 October 2026 also an update whose build number only extends the pinned one, and a change that misses one of the records).

## Alternatives considered

- **Keep iOS 18+ and macOS 14+.** Rejected by the product owner: it needs extra runtimes for testing, availability checks around newer APIs, and a floor that cannot be tested on any device here.
- **iOS 27+ only.** Smaller matrix, but it would exclude users on iOS 26 for no feature the plan requires.
- **Reinstall Xcode 27.0 after the update (PO-35 option (a)).** Not chosen on 20 October 2026, as the owner's reply was read: it would repeat under an older build the CI runs in which every drop-in but the toolchain check had passed under 27.1. Rejected by the product owner on 22 October 2026 (PO-35 (b) approved).
- **An iPhone 12-class phone as device A (D-1 option (a)).** It was the recommended default, as plan 19.1 and the checklists proposed it. Not chosen on 22 October 2026: the product owner has an iPhone 11 and an iPhone 11 Pro, older phones iOS 26 supports, and chose them (D-1 (b)), which makes the device evidence stricter (an A13 rather than an A14).
- **The iPhone SE (2nd generation) as device A, the 375 × 667 pt floor on a device.** Option (b) named it among the older phones; not available as a device, so that floor stays a simulator check.
