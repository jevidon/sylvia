## Context

Section 22 asks for a monorepo, pinned dependencies, CI that lints contracts and design literals, and reproducible Stage 0 evidence. Several workstreams run in parallel, so conventions must keep their files apart.

## Decision

**Layout.** As Section 22.1, plus `Spikes/` (Stage 0 harnesses: evidence code that is never shipped and is not a product UI target), `Scripts/` and `Docs/Stage0/` (gate reports and physical-device checklists).

**Xcode projects.** Each app, extension or spike with an Xcode target has a `project.yml` for XcodeGen 2.46.0. Generated `.xcodeproj` bundles are not committed. Each project's package lock is committed as `Package.resolved` next to its `project.yml`; `sylvia_generate` (`Scripts/lib/xcodegen.sh`) installs it into the generated project, and builds pass `-disableAutomaticPackageResolution` so they use exactly the locked versions. Pure Swift packages commit their own `Package.resolved`.

**Dependencies.** Third-party code is limited to what the plan needs. Each package is pinned to an exact version, justified in the ADR of the workstream that needs it, and recorded with its role and license in `Docs/Licenses/inventory.json`, which `Scripts/ci.d/12-dependency-lock.sh` checks on every run (ADR-0014). The pinned set at kickoff (latest releases on 6 October 2026):

| Package | Version | Needed for |
| --- | --- | --- |
| readium/swift-toolkit | 3.11.0 | EPUB (D02, G0.1) |
| groue/GRDB.swift | 7.11.1 | Persistence (D02, G0.5 recovery); FTS5 retrieval in the G0.5 AI spike (ADR-0011) |
| pointfreeco/swift-snapshot-testing | 1.19.6 | Design snapshots (T51, T53) |
| apple/swift-nio, swift-nio-ssl, swift-certificates, swift-crypto, swift-asn1 | 2.103.0, 2.37.5, 1.21.0, 5.0.0, 1.7.3 | Candidate stack for the Mac source service and certificate generation (G0.2 decides) |

Readium 3.11.0 brings its own transitive dependencies (among them `readium/ZIPFoundation`, whose module is `ReadiumZIPFoundation`); they are part of the lock and the license inventory. The complete lock after M0 integration, with every transitive package and its license read from the pinned checkout (including swift-nio's swift-atomics 1.3.1, swift-collections 1.7.1 and swift-system 1.8.1, and the BoringSSL that swift-nio-ssl vendors), is ADR-0014.

**Simulators.** Every job creates and uses its own named simulator (`Scripts/lib/sim.sh`), so parallel jobs never share one. The default is an iPhone 17 on the iOS 26.5 runtime. The paired physical iPhone is used only in serialized device runs.

**CI.** `Scripts/ci.sh` runs each executable drop-in in `Scripts/ci.d/` in name order and writes logs to `.build/ci-logs/`. Workstreams add their own numbered drop-in rather than editing shared files. The `00-*` drop-ins check the checkout itself (since 19 October 2026, `00-git-lfs`, below): they run first in every run, also when the filter words do not name them, and a failure stops the run. GitHub Actions (`.github/workflows/ci.yml`) is written to run the same script on a macOS runner. Because macOS runner minutes are billed on a private repository, the workflow runs only on manual dispatch (with an optional list of drop-in filters, by default `contracts hard-rules design`, so a default run includes the hard-rule audit), and the local script is the primary gate during Stage 0. The workflow refuses to run on a runner without the pinned Xcode build rather than silently using another one. It checks out with `lfs: true`, so the LFS files are downloaded (since 19 October 2026). Its limits, from GitHub's runner-image documentation read on 19 October 2026 and not run (final review CC-04): the `macos-26` image has Xcode 26.x only, so the guard stops every dispatch until a runner has the pinned Xcode, 27.1 (27A9275) since the re-pin of 20 October 2026 (27.0, 27A266a, before; ADR-0001); an image with 27.0 had only the iOS 27.0 simulator runtime (what an image with 27.1 has was not read), while the design and simulator drop-ins need iOS 26.5; and a dispatch of every drop-in cannot finish on a hosted runner (about 3 hours locally against a 120-minute timeout, Homebrew ffmpeg for the G0.4 fixtures not installed, and a fixture cache of about 29 GB against 14 GB of disk). Since the M0 final fix the Xcode and XcodeGen guards run before the checkout, so a stopped dispatch downloads no LFS object, and the input reaches the shell as an environment variable holding only filter words, never as script text (final review SEC-08).

**Tooling.** Python contract and lint tooling runs from a shared virtualenv (`$SYLVIA_TOOLS_VENV`, default `~/Library/Caches/SylviaTools/venv`), installed from the pinned `Scripts/tools/requirements.txt` by `Scripts/tools/bootstrap.sh`. The G0.4 audio fixtures also need ffmpeg and ffprobe 8.1.x from Homebrew, built with libmp3lame, libopus and AudioToolbox (8.1.2 on the build Mac), and macOS `afconvert`: `Scripts/fixtures/generate-g04-audio-fixtures.sh`, `generate-g04-audio-long-formats.sh`, `generate-g04-audio-probes.sh` and `generate-g04-audio-stereo.sh` (the fourth, from G0.4 review round 6, merged at M0 assembly) encode the fixtures with them, and `Scripts/ci.d/60-g04-audio.sh` decodes the exported excerpts with ffmpeg for its portability check. ffmpeg is a host tool only: it is not linked into or bundled with any target and is not a package dependency (ADR-0014). Each generator records the ffmpeg and macOS versions in its stamp and regenerates its fixtures when either changes, so another ffmpeg build can give other digests than the committed generation logs (`Docs/Stage0/evidence/G04-Audio/fixture-generation*.log`).

**Fixtures.** Small public-domain fixtures are committed under `Fixtures/`. Large ones are downloaded or generated into `$SYLVIA_FIXTURE_CACHE` (default `~/Library/Caches/SylviaFixtures`) by `Scripts/fixtures/fetch.sh` (SHA-256 pinned) and `Scripts/fixtures/generate-*.sh`. Provenance is in `Fixtures/LICENSES.md`.

**Branches.** One branch and one pull request per milestone (`m0`, `m1`, ...), merged after the milestone's exit review.

**Binary test baselines and evidence images: Git LFS (the product owner's decision of 13 October 2026, adopted on `m0-integrate` on 19 October 2026).** The decision replaces the deferral recorded at M0 integration (kept below as history): "Adopt Git LFS for the snapshot and evidence images once the current integration is complete. Use repository-local configuration, update CI and setup instructions, and verify a clean checkout. Leave existing history intact." Implemented by an agent and verified by an agent review, whose verdict (accept-with-minor) has no committed record; its three minor fixes not reviewed again; human sign-off pending (as the status line says; until 20 October 2026 this line still read "agent review and human sign-off pending": M0 final review round 2, R2-06 and R6-07). Commands and logs: `Docs/Stage0/evidence/M0-Integration/lfs/` (integration log section 9).

- *Stored with LFS.* `.gitattributes` gives `filter=lfs diff=lfs merge=lfs -text` to `**/__Snapshots__/**/*.<ext>` (snapshot references, in any `__Snapshots__` directory) and `Docs/Stage0/evidence/**/*.<ext>` (Stage 0 evidence images), for png, jpg, jpeg, gif, heic, tif, tiff and webp. Each extension is written as a letter-case class such as `*.[pP][nN][gG]`: git matches attributes case-insensitively only where `core.ignorecase` is true (macOS), and the classes make an image with an upper-case extension (`IMG_0001.JPG`) match on Linux and GitHub's servers too. At adoption the patterns match 777 files, 67,579,563 bytes: 527 snapshot references (37,703,582 bytes) and 250 evidence images (29,875,981 bytes), held in 719 distinct LFS objects (65,110,465 bytes; identical images share one). `git check-attr` over every tracked path, with either `core.ignorecase` setting, gives these attributes to exactly those files and to nothing else (`check-attr-adoption-commit.log`).
- *Plain git.* Everything else: the 25 design board PNGs in `Docs/Design/images`, the 2 SVG symbols in the design package's asset catalog, `Fixtures/` and the committed generated fixtures (EPUB, PDF, SQLite, DER), fonts, PDFs and all text. Videos are not covered: if a device session adds MP4 or MOV evidence (runbook D-8), the owner extends the patterns first, or the videos go into plain git.
- *Repository-local configuration.* `git lfs install --local` writes `filter.lfs.clean`, `filter.lfs.smudge`, `filter.lfs.process` and `filter.lfs.required` into the repository's own `.git/config` and installs git-lfs's `pre-push`, `post-checkout`, `post-commit` and `post-merge` hooks in `.git/hooks`; it writes nothing to the user's global or the system configuration. Because the repository does not set `extensions.worktreeConfig`, this configuration and these hooks apply to every worktree of the repository, the main checkout included. On a branch without LFS attributes they change nothing: the three post-* hooks only make files with the `lockable` attribute read-only, and none has it; `pre-push` uploads only the LFS objects that the pushed commits reference, none on such a branch (git-lfs may still ask the remote about file locks during a push). On the build Mac the filter entries and git-lfs 3.7.1's four hooks (byte for byte) were already in place before the adoption, the hooks dated 15 October 2026 12:13 NZDT, so the adoption's own `git lfs install --local` changed nothing (`config-before-install.log`, `config-after-install.log`). Other clones set this up with `Scripts/setup-repo.sh`. If git-lfs is removed from a Mac, the hooks print an error and `pre-push` blocks pushes until it is reinstalled or the hooks are deleted, and because the filter is `required`, adding or checking out an LFS file fails instead of silently storing the image or writing a pointer (`required-filter-check.log`).
- *History left intact.* The adoption commit `adab8e2` (parent `504fac2`) adds `.gitattributes` and replaces the 777 images with LFS pointers through `git add --renormalize`; nothing rewrote history (no `git lfs migrate`, filter-branch, rebase or amend) and no other branch changed (`verify-adoption.log`). Earlier commits keep their plain image blobs, so the repository does not shrink; every image version committed before the adoption stays in history. New versions of these images are stored as LFS objects, so a re-record or a screenshot refresh adds a pointer of about 130 bytes per image to git history instead of the image.
- *CI.* `Scripts/ci.d/00-git-lfs.sh` fails, naming `Scripts/setup-repo.sh`, when git-lfs is missing, when the repository-local filter is not set, when a file that `git lfs ls-files` lists or an LFS attribute matches is still a pointer in the working tree, or when a matched file is committed as a plain blob (`git lfs fsck --pointers`). Its self-test first plants each of these failures in a temporary repository, and a copy of the drop-in with any one of its checks disabled fails that self-test (`dropin-mutations.log`). `Scripts/ci.sh` runs the `00-*` drop-ins first in every run, filtered or not, and stops if one fails. The workflow checks out with `lfs: true`; its manual dispatch and Xcode guard are unchanged. With `lfs: true`, `actions/checkout` at the pinned commit runs `git lfs install --local` and `git lfs fetch origin <ref>` (its `src/git-command-manager.ts` at `11d5960`, read on 19 October 2026), so the runner's checkout meets `00-git-lfs`'s repository-local check; the workflow itself has not been run since the change.
- *Setup.* `Scripts/setup-repo.sh` checks for git-lfs, runs `git lfs install --local`, runs `git lfs pull` only when an LFS file is missing or a pointer, and ends with `00-git-lfs.sh` (CLAUDE.md, Setup). A clean clone of `m0-integrate` from the local repository, with no network, checked out the LFS files from the repository's own LFS storage without any extra setting: git-lfs uses its built-in `lfs-standalone-file` transfer for a local-path remote. Such clones passed `Scripts/setup-repo.sh`, `00-git-lfs`, the contract checks and both design drop-ins, the snapshot suite comparing against the smudged references; clones made with `GIT_LFS_SKIP_SMUDGE=1` or with no LFS setup failed `00-git-lfs` with its message, and `Scripts/setup-repo.sh` repaired them (integration log section 9.4).
- *Push-time cost.* Nothing has been pushed, and only the owner pushes. The first push of `m0-integrate` after the adoption runs the `pre-push` hook, which uploads the 719 LFS objects (65,110,465 bytes, about 0.061 GiB) to GitHub's LFS storage for `jevidon/sylvia`; later pushes upload only objects GitHub does not have. GitHub's documentation ("Git Large File Storage billing", https://docs.github.com/en/billing/concepts/product-billing/git-lfs, read on 19 October 2026) says: GitHub Free and GitHub Pro include 10 GiB of LFS storage and 10 GiB of LFS bandwidth, and the free quota resets at the start of each billing cycle; storage counts every LFS object associated with the repository, whenever it was uploaded; uploads count toward storage but not bandwidth; downloads by GitHub Actions count toward the repository owner's bandwidth, so each workflow run with `lfs: true` (65.1 MB at adoption) uses bandwidth, as does every clone that downloads the LFS files; beyond the included amounts, what happens depends on the account's budget and payment method (with a budget of $0, Git LFS use is blocked for the rest of the month). Which plan this account is on was not checked.

*The deferral this decision replaces (M0 integration, 13-14 October 2026), kept as the record of the measurements:* snapshot reference PNGs and Stage 0 evidence images were to stay in plain git; Git LFS was deferred, not rejected.

Of these, 762 are PNG (64,437,948 bytes, largest 450,701): 527 snapshot references in `Packages/Design/Tests/SylviaDesignSnapshotTests/__Snapshots__/` (37,703,582 bytes, largest 368,357) and 235 evidence images under `Docs/Stage0/evidence/` (26,734,366 bytes: G0.6 198, G0.1 PDF 20, G0.1 EPUB 11, G0.4 6). The rest are generated fixtures (17 EPUB, 3 PDF that git detects as binary, 1 SQLite database, 3 DER certificates; 827,530 bytes). Already in plain git before M0: `Docs/Design/images` (25 PNG, 5,953,264 bytes) and `Fixtures/` (6,782,114 bytes including `LICENSES.md`). *At the G0.4 merge* (14 October 2026) G0.4's final commit adds 12 evidence images (1,259,167 bytes, largest 222,609), not the 6 read at `943d5e7`, and no other binary file, so the eight gates add 792 binary files (66,082,214 bytes): 768 PNG (65,254,684 bytes, largest still 450,701), of which 241 are evidence images (27,551,102 bytes; G0.4 12) and the same 527 are snapshot references (`Docs/Stage0/evidence/M0-Integration/g04-binary-files.txt`, written by `commands/g04-binary-files.sh` beside it from the `m0-integrate` history). Every G0.4 image is under `Docs/Stage0/evidence/`, so the evidence pattern in step (1) below covers it. *At M0 assembly* (14 October 2026) the thirteen merged items add 233 binary file versions to history (29,577,209 bytes), none an LFS pointer and none with a git attribute: 232 PNG evidence images (29,224,953 bytes, largest 450,566), of which 9 are new paths and 223 replace existing images (G0.6's 196-screenshot refresh, 21,662,050 bytes, as anticipated under *Cost of waiting*; G0.1 PDF 18, 7 of them new; G0.1 EPUB 4; G0.4 14, its final set, 2 new and 12 replaced, 1,754,208 bytes, largest 241,516), and the regenerated G0.5 recovery `library-v1.sqlite` (352,256 bytes). Snapshot references are unchanged (527). No `.gitattributes` exists (`Docs/Stage0/evidence/M0-Integration/assembly-binary-files.log`, written by `commands/assembly-binary-files.sh`). The decision below stands.
- *Why not now.* On the build Mac, git-lfs 3.7.1 is installed but not set up: `git config --show-origin --list` shows no `filter.lfs.*` setting at the system (`/opt/homebrew/etc/gitconfig`) or repository level, and there is no user `~/.gitconfig`. With a `.gitattributes` rule in place, every checkout made on this Mac (each parallel agent's worktree, and the clean verification run that follows integration) would contain small pointer files instead of PNGs, so the snapshot suite would fail and the evidence images would be unreadable until the owner runs `git lfs install`, which writes the user's global git configuration. That is the owner's action, not an agent's, and many agents work from worktrees of this repository at once.
- *Cost of waiting.* PNG data does not delta-compress, so every committed version stays in history at about its full size: the 65 MB above already does, a full re-record of the snapshot references adds about 37 MB, and a G0.6 evidence refresh about 21 MB. LFS helps only from the commit that adopts it.
- *Trigger and steps.* Adopt LFS before the first re-record of the snapshot references after M0 (the first token value change) or before `m0` is first pushed, whichever comes first, once the owner has run `git lfs install` on every Mac that builds Sylvia: (1) a `.gitattributes` with `Packages/**/__Snapshots__/**/*.png filter=lfs diff=lfs merge=lfs -text` and `Docs/Stage0/evidence/**/*.png filter=lfs diff=lfs merge=lfs -text` (`Docs/Design/images` and `Fixtures/` stay plain; the evidence pattern also covers G0.4's images); (2) `git add --renormalize` of those paths in a dedicated commit; (3) a CI drop-in that runs first and fails with a clear message if a tracked file matching those patterns is still an LFS pointer, so the snapshot suite never fails confusingly; (4) `lfs: true` on the checkout step in `.github/workflows/ci.yml`. Rewriting the unpushed history with `git lfs migrate import` would also keep the earlier copies off GitHub, but it changes every commit SHA that parallel branches start from, so it is a separate owner decision.
- *Push-time cost once adopted.* LFS objects count against the owner's GitHub account LFS storage and bandwidth quotas (not verified here, so no figures are given). Old versions stay in LFS storage until purged, and each CI run with `lfs: true` downloads the current set, about 65 MB after the G0.4 merge.

## Consequences

- Generated projects cannot drift from `project.yml`, and package versions cannot drift silently.
- A clean clone needs XcodeGen, Python 3 and network access for package and fixture downloads, and Homebrew ffmpeg for the G0.4 audio fixtures.
- The G0.4 drop-in also needs the build Mac's default audio output to be a device with a short output latency, such as the built-in speakers or wired headphones: the iOS Simulator plays through that device, and an AVPlayer's clock includes its latency, so with a long one (an AirPlay output: 2.012 s, as CoreAudio reports it) seven of its tests failed after 77 minutes in the M0 final fix's complete run of 19 October 2026. Since 20 October 2026 `Scripts/ci.d/60-g04-audio.sh` reads the device and its latency at its start, read-only, records them in its log and in every row of `host-load.tsv`, and stops at once, naming the device, above 0.3 s (M0 final review round 2, CC2-01). With the built-in speakers (0.027 s) as the output, the same code passed every step of the drop-in on 20 October 2026, those seven tests included (`Docs/Stage0/integration-log.md` section 12). A person changes the output; agents never change the Mac's audio device, and the tests' tolerances are not widened for it.
- A clean clone also needs git-lfs and `Scripts/setup-repo.sh` before its snapshot suite can run; until then `00-git-lfs` stops every CI run with that instruction. Every clone from GitHub and every workflow run downloads the current LFS objects, which counts against the owner's GitHub LFS bandwidth.

## Alternatives considered

- **Commit `.xcodeproj` bundles.** Rejected: merge conflicts across parallel workstreams and drift from intent.
- **Tuist.** Not installed; XcodeGen covers the need with less machinery.
- **SwiftLint for design literals.** Not installed; a small purpose-built script checks exactly the Section 4.4.9 rules.
- **Amend the branch rule after pull request #4** (H-1's other option). Not chosen on 22 October 2026: the product owner recorded the merge as a one-off exception and kept the rule.
