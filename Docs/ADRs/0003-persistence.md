## Context

The plan asks for GRDB over SQLite, one serialized writer, foreign keys, WAL and "a durability configuration tested for acknowledged saves" (7.4), migrations with fixture upgrades, integrity checks and a recovery path (7.4), a transactional ChangeJournal (7.4), and identity rules where removing bytes never removes knowledge (I-02, 7.3). "Saved" may appear only after a durable commit (I-03). The G0.5 recovery spike (`Spikes/G05-Recovery`) built the subset of Section 7.2 the restore drill needs and tested these rules. The evidence report is `Docs/Stage0/G05-Recovery.md`.

## Decision

**Library and dependency.** GRDB.swift 7.11.1 (exact pin, revision `b83108d10f42680d78f23fe4d4d80fc88dab3212`, MIT licence) over the system SQLite. No other persistence dependency. Store the database at `Application Support/Sylvia/Library/library.sqlite`, never in Documents.

**Connections.** One `DatabasePool` per process: one writer connection (all mutations are serialized through it) and concurrent read-only readers. `foreignKeysEnabled = true`, `busyMode = .timeout(10 s)`.

**Durability for acknowledged saves.** WAL, `PRAGMA synchronous = FULL`, `PRAGMA fullfsync = ON`, `PRAGMA checkpoint_fullfsync = ON`, applied on the writer **after** the pool is open and read back on every open; a mismatch is an open failure. Approved by the product owner on 22 October 2026 as the I-03 setting (D17, PO-21 (a)); its readback and save latency on a phone are still pending (Open items). Reasons:

- WAL with `synchronous = NORMAL` (GRDB's default) is durable against process death but, per SQLite's documentation, may roll back the last commits after power loss or an OS crash, which would break I-03.
- `FULL` syncs the WAL at every commit; on Apple platforms `fsync` does not flush the drive cache, so `fullfsync` makes that sync reach stable storage.
- The measured cost is small against the 200 ms budget: on the host, a capture save with this setting has p95 3.25 ms (2,000 saves, review-round-4 run). Host runs under parallel load do not resolve its cost relative to GRDB's default (p95 1.53 ms in the same run; the review-round-3 run had them the other way round, 2.59 ms for the default against 1.51 ms). Device numbers are pending.
- GRDB 7.11.1 runs `PRAGMA synchronous = NORMAL` on the writer after `Configuration.prepareDatabase`, so setting `synchronous` in `prepareDatabase` is silently overridden. The post-open apply and readback are therefore required, not optional (test `DurabilityTests.grdbOverridesPrepareDatabase`).

**Schema rules.** `STRICT` tables. IDs are lowercase UUID text generated on device. Sizes, durations and positions are 64-bit `INTEGER` (bytes, milliseconds). Event timestamps are UTC integer milliseconds (`*_at_ms`). User-effective dates are separate text columns (`YYYY`, `YYYY-MM`, `YYYY-MM-DD`) with a `*_precision` column. `CHECK` enforces only the precision value (`year`, `month`, `day`) and that the date and its precision are null together; the date text itself (its format, with every component ASCII digits only, so a sign such as `+019` is refused; its agreement with the precision; and that the day exists) is validated in code: by `EffectiveDate` when the app builds a date, and by `RowCheck` for every date of a backup's database before it is restored (ADR-0012). Adding the format to the schema would need a table rebuild of four tables; the spike did not, so the schema alone accepts `banana` with precision `day` (`SchemaTests.typing`). TEXT values are valid UTF-8 without U+0000: GRDB 7.11.1 binds a `String` as a C string (`sqlite3_bind_text` with length -1) and reads TEXT with `String(cString:)`, so text holding a NUL is stored cut off at it, and stored text holding one reads back cut off (finding F12 in the report, `SchemaTests.nulTextIsRefused`). The store therefore refuses text containing U+0000 before writing anything (`ValidationError.textContainsNUL`), and `RowCheck` refuses a backup's database holding a NUL or invalid UTF-8 in any TEXT value (ADR-0012). Ratings are `INTEGER 1-10` half-stars with `NULL` meaning cleared, plus an explicit `scale` column. Digests are checked lowercase hex SHA-256. JSON is used only for versioned locator payloads, source snapshots, provider identity and retrieval metadata (`json_valid` checked).

**Media never cascades into knowledge.** Removing media changes `asset_location.availability` (`on_device` → `at_source` or `unavailable`) and deletes files; it never deletes `asset`, `edition` or `work` rows. Every knowledge table references media and works with `ON DELETE RESTRICT`, so even a mistaken `DELETE FROM asset` fails instead of cascading. `ON DELETE CASCADE` is used only for subordinate rows: a capture's anchors, a note's revisions, a conversation's messages, a context pack's evidence, an asset's locations and membership joins. Availability is resolved as on device (file present with the recorded size), "Not on this device · from {source}", or "Record only"; a missing file is never an error or a corrupt record.

**Commands.** A capture save is one write transaction containing the capture, its anchors, the optional comment note and first revision, the ledger event and ChangeJournal entries, keyed by an idempotency key (`UNIQUE`); a retry returns "already saved" instead of a duplicate. Text containing U+0000 fails the command before anything is written (Schema rules), so "Saved" never stands for text stored cut off. The method returns only after the commit, and only then may the UI say "Saved". Note edits are revision-checked: an editor holding a stale revision gets `staleRevision`, never a silent overwrite.

**ChangeJournal.** Every mutation appends `(seq AUTOINCREMENT, entity, entity_id, revision, operation, recorded_at_ms)` in the same transaction. It is a local diagnostic and export-boundary record, not a sync protocol. The backup manifest records the highest sequence in each snapshot.

**Migrations.** `DatabaseMigrator` with `eraseDatabaseOnSchemaChange = false`, one identifier per migration, each flagged destructive or not. On open:

1. Read **all** applied identifiers with `appliedIdentifiers(_:)`. GRDB's `appliedMigrations(_:)` returns only registered identifiers and so cannot see that a newer build touched the file; any unknown identifier refuses the open without changes (`newerSchema`).
2. If a pending migration is destructive and the library is not new: check free space for a snapshot plus a rebuild plus a reserve (stop with `insufficientSpace` otherwise), then take a recovery snapshot with SQLite's online backup API into `Recovery/pre-migration-<ms>-<id8>.sqlite`, integrity-checked and flushed. A retry from the same pre-state does not take another snapshot: if `Recovery/` already holds an intact pre-migration snapshot whose whole logical content (schema, applied migrations and every row, `LibraryChecks.contentDigest`) equals the live library's, it is reused. The digest reads every value as stored, TEXT as its bytes rather than GRDB's decoding (which stops at an embedded NUL and replaces invalid UTF-8; review round 4 found the first version blind to that), so equal digests mean the same schema and the same values byte for byte, whatever the files' page layout or journal mode. Then write the put-back intent `Library/migration-putback.json` (the snapshot's path and the pending migrations) durably, before the first migration runs.
3. Migrate. GRDB runs each migration in its own transaction with deferred foreign-key checks.
4. After migrating, run `integrity_check`, `foreign_key_check` and compare every table's row count with the count before migrating. If all pass, remove the intent.
5. On any failure in 3 or 4, close the pool and put the snapshot back, resumably: copy the snapshot into `Staging/Persistence/putback-<id>.sqlite.partial` (first removing a partial copy that an interrupted staging left), flush it and rename it to `putback-<id>.sqlite`; only then move `library.sqlite`, `-wal` and `-shm` to `Recovery/failed-<id>/`, rename the staged copy to `Library/library.sqlite`, and remove the intent, flushing the directory after each rename. Then report the failure (`migrationFailed` or `postMigrationCheckFailed`). If the put-back itself fails (for example a full disk), the failure is reported with `restoredFromSnapshot: false` and the intent stays. Removing the intent is the last step: once it is gone the put-back is complete, so a failure of only the flush after it is reported as a completed put-back (a removal lost to a crash would only make the next open repeat a put-back that finds the snapshot already in place).
6. Every open first reconciles an intent left by a crash or by a failed put-back, before SQLite opens anything: which files exist tells how far it got (staged copy present: move the live files aside and move it in; staged copy gone and the failed database already aside: it was moved in; neither: stage again from the snapshot). Before resuming, it removes abandoned files from this layer's `Staging/Persistence/` except this put-back's staged and partial copies, which the put-back itself moves in or removes ("Retention of `Recovery/` and `Staging/Persistence/`" below), since they may be what filled the disk. The open then reports `migrationInterrupted`, so the user sees the recovery screen once, and the next open retries the migration. If the put-back still cannot finish (for example the disk is still full), the open fails with the typed `migrationPutBackPending(reason:)`, never a raw file-system error, and the intent stays for the next open. An intent that exists but cannot be read (for example before first unlock) or is not valid fails the open with nothing changed, `Staging/Persistence/` included. The intent lives inside `Library/`, so a restore swap moves it with the library it describes.
7. The open never lets SQLite create a new database where one should be: if `library.sqlite` is missing and the installation record exists or `Recovery/` holds copies, it fails with `libraryMissing` (listing the copies) instead. The database is created before the installation record on a new installation, so a crash between the two cannot trigger this.

In every failure the app opens a recovery screen with read-only access (`RecoveryAccess.openReadOnly`), from which the user can export. It never creates an empty replacement library.

A migration that cannot convert a value fails (`CHECK` constraint) rather than dropping the row.

**Retention of `Recovery/` and `Staging/Persistence/`** (plan 17.1, "visible cleanup policy for abandoned jobs"; `RecoveryRetention`, `StagingCleanup`). Review round 3 found that every failing launch added a new snapshot and a new failed copy to `Recovery/`, about 2.2 times the library each time, and nothing removed them; this layer's abandoned temporary files (a crashed media import's copy can be audiobook-sized) were never removed either. `Recovery/` is pruned after a put-back completes and after a guarded migration succeeds, only once no put-back intent is pending, and best effort (an error leaves the copies for the next time and never fails the open):

- Pre-migration snapshots: only the snapshot the operation used is kept; older ones are removed. So the kept snapshot stays until a later guarded migration succeeds or is put back with another snapshot, and damage found after an upgrade can still be recovered meanwhile. Retries from the same pre-state reuse it (step 2).
- `failed-<uuid>/` copies: only the latest is kept, for diagnosis; all are removed when a guarded migration succeeds. They never hold data the snapshot lacks, because a migration and its put-back run inside an open (the put-back possibly at the next one), before anything can write.
- `pre-restore-<id>/` copies hold the library a confirmed restore replaced and may be its only copy, so they are never removed automatically (ADR-0012).
- A snapshot or failed copy named by a put-back intent inside a pre-restore copy is kept; if such an intent cannot be read, nothing is removed. Names other than the two generated forms (`pre-migration-<ms>-<8 hex>.sqlite`, `failed-<uuid>`) are never removed.
- `Staging/Persistence/` holds this layer's own temporary files and nothing else: durable writes' temp files, snapshots being taken, media copies being imported, and a put-back's staged and partial copies. Each is renamed into place or removed by the operation that wrote it, and an open runs before the library is used (one store per installation), so every entry an open finds there is abandoned. Each open removes them all, except a pending put-back's staged and partial copies (step 6), which the put-back itself moves in or removes; with an intent that cannot be read or is not valid, nothing is removed. Best effort, like the pruning.
- The rest of `Staging/` is not this layer's. ADR-0010 keeps intake's durable state there: the import journal (`journal.json`) and the jobs in `Staged/`, `Rejected/`, `Abandoned/` and `Extracting/`, where a staged job can be the only copy of an item the share extension already reported as received (I-03). Plan 8.2 requires a relaunch to finish those jobs, and plan 17.1 keeps staging data for live operations with cleanup only for abandoned jobs, so intake's own journal and rules finish, expire or remove them (ADR-0010). This layer creates `Staging/` and excludes it from device backup, but never writes, reads or removes anything in it outside `Persistence/`. Review round 4 found that the first version of this rule emptied all of `Staging/`, which would have deleted acknowledged imports at every launch; `PutBackTests.abandonedStagingIsCleared` now plants intake's layout beside abandoned persistence files and checks it byte for byte after the opens.

`Recovery/` therefore holds at most one pre-migration snapshot and one failed copy (plus pre-restore copies and anything a pre-restore intent needs), however often a migration fails, and after an open `Staging/Persistence/` holds nothing from an earlier launch except a pending put-back's staged or partial copy (or an entry its best-effort removal could not delete, retried at the next open). Showing these copies with their size and a remove action is product work for the storage and recovery screens (M1 recovery journal, M7 retention controls). The product owner decided on 22 October 2026 (PO-40 (a)) that for V1 the kept copies stay until the user removes them there; an age-based expiry is revisited with the M7 retention controls.

**Files.** Directories are created with the data-protection class before files are written in them (see ADR-0012 for the class and its readback). All renames that publish data are same-volume `rename(2)` followed by a directory sync; file contents are synced with `F_FULLFSYNC` (falling back to `fsync`) before the rename.

## Consequences

- Acknowledged saves cost one WAL sync each. That is affordable at capture rates but rules out "Saved" on uncommitted batches. Bulk imports should batch rows into fewer transactions.
- Every migration must preserve row counts unless it states otherwise; a migration that deletes rows on purpose must say so, and the post-check must be extended for it.
- `appliedMigrations` must not be used for version checks anywhere in the product.
- Any operation that replaces the library's files (the put-back here, the restore swap in ADR-0012, and any later one) writes an intent first and is finished or rolled back by the next open before SQLite opens anything. Copies are staged and flushed before the live files are touched.
- A destructive migration's open shows the recovery screen once after an interrupted put-back (`migrationInterrupted`); the next open retries. A migration that crashes the process every time therefore alternates between the recovery screen and a retry instead of looping silently, and, because a retry reuses the snapshot and only the latest failed copy is kept, the retries do not consume more space each time (review round 3 measured about 2.2 times the library added per failing launch before this rule).
- The retention rule keeps one full copy of the database in `Recovery/` after every guarded migration until a later one succeeds or is put back with another snapshot. The product must show `Recovery/` (snapshot, failed copy, pre-restore copies) with sizes and a remove action; an age-based expiry was a product decision left open until 22 October 2026, when the product owner chose to keep the copies until the user removes them for V1 and to revisit an expiry with the M7 retention controls (PO-40 (a)).
- Every open removes everything in `Staging/Persistence/` except a pending put-back's staged and partial copies, so nothing may rely on a file there outliving the process that wrote it, and only one store may use an installation at a time. The rest of `Staging/` belongs to intake (ADR-0010) and this layer never touches it; each component that keeps files in `Staging/` owns one subdirectory and cleans only that (open items).
- GRDB writes and reads TEXT as C strings (finding F12 in the report), so text containing U+0000 cannot be stored exactly through a `String` binding. The store refuses it before writing; the product's capture and note commands must refuse it with a clear message or remove it visibly before saving (I-05), never store it cut off. Re-check on GRDB upgrades.
- Not proven, and cannot be proven by a process-kill drill: durability across power loss, kernel panics or storage firmware that ignores flushes. These rest on SQLite's and APFS's documented guarantees with `FULL` and `F_FULLFSYNC`.
- Re-check on GRDB upgrades: whether `DatabasePool` still overrides `synchronous` after `prepareDatabase` (the readback fails the open if it changes behaviour in either direction).

## Alternatives considered

- **WAL + `synchronous = NORMAL` (GRDB default).** Slightly faster, but may lose the last acknowledged commits on power loss, which conflicts with I-03.
- **Rollback journal (`DELETE`) + `FULL`.** Durable, but readers block the writer during commits and it gives up GRDB's `DatabasePool` concurrency.
- **Core Data / SwiftData.** No direct control over pragmas, migrations as rows-preserving checks, or the online-backup snapshot the backup format needs. The plan already names GRDB (6.3).
- **Setting pragmas in `prepareDatabase` only.** Silently overridden for `synchronous` by GRDB 7.11.1 (tested).
