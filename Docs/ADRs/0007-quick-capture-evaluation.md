## Context

The plan ships standard lock-screen and headphone playback controls, and one-tap capture inside the player. A dedicated quick-capture surface (lock screen, Control Center, Action button, Siri) is a separate feasibility gate (3.3, 10.5). It may become a release promise only if it works on supported iOS versions while the phone is locked, saves durably before it says so (I-03, T25), and does not repurpose play or skip.

Capture semantics are fixed by Section 10.2 and ADR-0006: a capture writes the anchor (the preceding 30 seconds as file-local ranges) and the note durably, then exports the excerpt. A surface can therefore acknowledge "Moment saved · preserving audio" as soon as the anchor write returns; "Audio excerpt saved" follows when the export is durable.

## Decision

1. **Release baseline (unchanged):** the labelled Capture button in the player (plan 3.3), plus the standard remote commands (play, pause, toggle, skip ±15 s, scrubbing, previous/next track as chapter navigation, rate). No transport command is ever mapped to capture.
2. **Candidate quick-capture surface:** one App Intent, `CaptureMomentIntent` ("Capture the last 30 seconds"), exposed three ways: a Control (`ControlWidgetButton`) for Control Center, the Lock Screen and the Action button; an App Shortcut (Siri, Spotlight, Shortcuts, and the Action button through Shortcuts). The intent:
   - adopts `AudioPlaybackIntent`, the documented way to have a widget or control intent performed in the app's process, where the playback position is live;
   - uses `authenticationPolicy = .alwaysAllowed` and `supportedModes = .background`, so it can run while locked without opening the app;
   - returns only after `QuickCaptureCoordinator.captureNow` has written the anchor durably, and throws (no acknowledgement) when there is no moment to capture, the write fails, or it finds itself outside the app process. The error text the system shows is a proposed vocabulary key, never an invented phrase: `[audio.nothing_to_capture]` when there is no moment to capture, `[audio.moment_not_saved]` when the durable write fails (the note editor's `save.failed`, "Not saved · your text is still here", would be untrue: a capture has no text; review R2-04);
   - captures only a moment heard in the app process (review R6-01): main playback has played since the book was loaded there (it plays now, or was paused after playing). A process the system launches to perform the intent restores the last book paused and has heard nothing, so it answers nothing to capture, whether its restore finished before the intent arrived or not. The earlier rule, "nothing loaded", made the answer depend on that race (device checklist step 12 could not state its result): on the simulator, with the harness not running, the system launched it in the background and the intent arrived while the restore was still running (the capture line says `loaded=true played_since_load=false`; the old rule would have saved a capture of a moment nobody had just heard). The remote bookmark command follows the same rule; the in-player Capture button does not need it (the listener sees the book and its position, and captures there whether or not it has played: device checklist step 15.3);
   - records the entry-point kind and the process in the capture's `origin`, so the device run shows where it actually ran: the control creates its intent with the optional parameter `surface = .control` (`intent.control@<bundle id>`); the App Shortcut, Siri, Spotlight and the Shortcuts app perform it without one (`intent@<bundle id>`). The control's placements (Control Center, a Lock Screen slot, the Action button) run the same configured intent, so the record cannot tell them apart; the device checklist separates them by time (review R2-05). Through the system on the simulator the parameter reached the app with a team-signed build and was lost with an ad-hoc-signed one (Evidence); device builds are team-signed, and checklist step 9 checks the field. If a device ever loses it, the control gets its own parameterless intent type, so the record names it by type;
   - never creates a second capture for one request. An App Intent carries no delivery identifier, so a re-delivered intent or a double press would otherwise save twice: a request with the same `origin` (the same entry-point kind in the same process) within 2 s of wall time, at a position no further away than 2 s of playback at the fastest rate allows (6.5 s), reuses the first request's idempotency key, and the store answers with the existing record (no second save, no second export). A control press and an App Shortcut run within 2 s are two captures; two presses of the control within 2 s, from Control Center and the Lock Screen, are one. A caller with a request identity passes its own key instead, and the window does not apply to it: the in-player Capture button passes a new key for every tap, so two quick taps at the same place are two captures, each with its own export (review R3-04; `QuickCaptureTests.inPlayerTapsEachMakeACaptureEvenWithinTheRepeatWindow`). The window therefore applies only to the App Intent and the bookmark remote command.
   It becomes a release promise only if every device item in `Docs/Stage0/device-checklists/G04-Audio.md` (steps 9-13) passes on iOS 26. Until then it is **not advertised** (T25).
3. **Not adopted:** the `MPRemoteCommandCenter.bookmarkCommand` (no documented display on current iOS; reported gone from the lock screen since iOS 16) and a Live Activity button (documented as inactive on a locked device). The bookmark prototype stays in the harness, off by default, for the device check only.
4. **Storage condition for any locked capture:** every store a capture writes (capture records, the anchor transaction, retained excerpts, position checkpoints, and the directories that hold them) uses file protection class C, `completeUntilFirstUserAuthentication`, applied explicitly, never left to the platform default and never weaker: no class D, no `none`. Disabling or lowering protection to make background or locked behaviour work is excluded (CLAUDE.md non-negotiables; plan 18.1 "never ... an unsafe downgrade", 22.3; T50), and class C is the class ADR-0012 (G0.5 recovery) sets for every persistent file, retained excerpts included. **Trade-off** (plan 18.1 asks for it to be documented): class C keeps the files encrypted from a restart until the first unlock and readable and writable by the app while the phone is locked after that, so a person with a locked, once-unlocked phone and a way into the app's container could read capture records, notes and excerpts; class A (`complete`) would close that window shortly after locking (its class key is discarded about 10 seconds after the lock, per Apple's Platform Security guide), but then a locked capture could not write its anchor, a locked playback could not write its checkpoints, and nothing could be acknowledged, which defeats the surface. Class B (`completeUnlessOpen`) was set aside in ADR-0012 (files closed while locked cannot be reopened). Before the first unlock after a restart nothing can be written, so nothing may be acknowledged: the intent fails visibly with the proposed key `[audio.moment_not_saved]` (checklist step 13), and the class is never lowered to get past that state. In the spike, `DurableFile` writes records and checkpoints with class C into class-C directories, and the excerpt exporter sets class C on the finished excerpt before renaming it into place (review R5-04: the excerpt had been left to the platform default; `ExcerptProtectionTests`, and an excerpt whose class cannot be set is not kept). The iOS Simulator ignores file protection (it logs "ignoring unsupported value: kCFURLFileProtectionKey=NSFileProtectionCompleteUntilFirstUserAuthentication" for the excerpt's temporary file, `simulator-file-protection.txt`, and reads back class C, the harness's `record_protection=` and `excerpt_protection=` in `quick-capture-simulator-*.txt`; ADR-0012 found it reads back class C whatever is set), so the class a device reads back is checklist step 9 (`record_protection=` and `excerpt_protection=`).

## Consequences

- If the device run passes, Sylvia can offer capture from the Lock Screen, Control Center, the Action button and Siri with one intent and one save path, and the acknowledgement is honest by construction.
- Adopting `AudioPlaybackIntent` for an action that does not start or pause audio is the weakest point: it is the documented route to the app process, and on the simulator the system took it for the control (the intent was performed in the playing app's process, Evidence), but it stretches the protocol's stated purpose. Risks: App Review, or a future iOS that treats `AudioStarting` intents differently. If the device run shows the intent performed in the extension, or the protocol is judged inappropriate, the fallback is an App Group handoff: the extension appends a capture request to a shared, class C queue and returns only after the app (alive, because it is playing) has committed the anchor; without a playing app it fails. That design needs its own spike.
- The surfaces need class C storage for every store on the capture path; that constrains the persistence ADR.
- Before the first unlock after a reboot, quick capture cannot work; it must fail without acknowledgement, which the checklist verifies.
- The vocabulary has no key for "nothing to capture" or for "the moment was not saved"; the prototype shows the proposed keys `audio.nothing_to_capture` and `audio.moment_not_saved` (open question for G0.6; since the product owner's decision PO-28 of 22 October 2026 each gap is added before the milestone that first shows it, here M4, in one design review pass).

## Alternatives considered

- **Repurpose play/skip (for example a double press) as capture.** Rejected by the plan (10.5): undocumented behaviour, breaks headphone and car controls.
- **Bookmark remote command as the release surface.** Rejected unless the device shows it on iOS 26; even then the system gives no confirmation text, so the user cannot see "Moment saved".
- **Live Activity button.** Rejected for locked capture on documented behaviour; it also needs ActivityKit and a second lock-screen surface during playback.
- **Control intent running in the widget extension with App Group storage.** Possible, but the extension cannot read the live playback position (only the last checkpoint, up to 5 s old) unless the app answers a request; kept as the fallback above.
- **Open the app (`OpenIntent`) to capture.** Requires unlock and takes the user out of the lock screen; no better than the in-player button.
