# ADR-0008: Pairing and transport security

- **Status:** Proposed
- **Date:** 2026-10-07 (part 2 additions and round 1 and round 2 review corrections 2026-10-12)
- **Deciders:** pending (product owner; security reviewer for the pairing protocol)
- **Plan references:** Sections 6.4, 14.2, 14.3, 15.1, 15.2, 15.3, 15.5, 16.3, 18.1; XFER-01, XFER-04; tests T36, T37, T41, T43; gate G0.2

## Context

Section 15.2 proposes a user-mediated trust bootstrap with standard parts only: the Mac has its own key and certificate, issues a single-use invitation carrying the key fingerprint and a high-entropy secret, the phone pins the key before sending the secret, the Mac user approves, and the phone receives a scoped per-device credential. A six-digit code over an unauthenticated channel is ruled out, and so is inventing a cryptographic protocol. Section 14.2 asks for deliberate Keychain accessibility classes, Section 14.3 forbids weakening TLS validation or disabling ATS, and Section 16.3 asks for explicit bind interfaces and revocation.

This ADR records what the G0.2 spike built and tested (`Spikes/G02-Transfer/`; part 1: pairing and the Mac source; part 2: the iOS background-download client), and what stays open. The transfer protocol itself is ADR-0009.

## Decision

### Mac identity

- The Mac source generates a P-256 signing key (swift-crypto 5.0.0) and a self-signed X.509 v3 certificate for it (swift-certificates 1.21.0): subject and issuer `CN=Sylvia source <source_id>`, `BasicConstraints` CA false (critical), `KeyUsage` digitalSignature (critical), `ExtendedKeyUsage` serverAuth, ECDSA with SHA-256, valid for ten years. The validity period is informational: the phone trusts the key, not the dates or a CA.
- The private key lives in the macOS Keychain as a non-synchronizable generic-password item (raw 32-byte scalar), service `com.jevidon.sylvia.source.identity`, account = source ID, in the data protection keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. That keychain needs a keychain access group, which only signed code has. By default the store uses nothing else: a missing entitlement (`errSecMissingEntitlement`) is an error, so a signed companion with a misconfigured access group fails loudly instead of silently keeping its key in a weaker store (review finding R1-11). The unsigned command-line tools opt in to falling back to the login (file-based) keychain (`KeychainIdentityStore.Policy.allowLoginKeychainFallback`) and print which one they used. The certificate and the stable source ID (a UUID) are public and live in the state directory (`identity.json`, directory mode 0700).
- **Trust anchor:** the pin is SHA-256 over the DER `SubjectPublicKeyInfo` of the certificate (the value `openssl x509 -pubkey | openssl pkey -pubin -outform der | sha256` prints). Pinning the key, not the certificate, lets the Mac reissue its certificate without re-pairing; a new key always needs re-pairing.
- If the identity is reset or a new key is created, every existing pairing token is revoked at start-up, so no phone can come back except through a new invitation.

### Invitation (pairing payload)

- Fields (`Contracts/schemas/pairing-payload.v1.schema.json`): `schema_version`, `protocol_version`, `source_id`, `source_name`, `endpoints` (1 to 8 host and port pairs: IPv4, IPv6 or DNS name such as a Tailscale MagicDNS name), `spki_sha256`, `invitation_id`, `invitation_secret` (32 random bytes, 256 bits, unpadded base64url; at least 128 bits is required), `expires_at`.
- Text forms: the code `SYLVIA1-<base64url(JSON)>` and the link `sylvia://pair/v1#<base64url(JSON)>` (payload in the fragment, never a query). A QR code is the link encoded; the spike prints the code and link and does not draw a QR. Encoded payloads are limited to 4,096 characters.
- **The `sylvia://` link can be intercepted by another app** (review finding R2-05; for the security review). iOS does not reserve custom URL schemes: any installed app may declare `sylvia`, and a tapped link or a QR code of the link scanned with the system Camera may open that app instead of Sylvia. That app then holds the pin and the invitation secret and can pair as a new device, under a device name it chooses, before the real phone does; the Mac user's approval prompt is the only barrier, and the device name it shows is chosen by whoever sends the request, so it proves nothing. It would receive a token scoped to catalog, read, download and receipt for the shared library. Scanning the QR code inside Sylvia (`DataScannerViewController` in the harness) and pasting the code do not pass through the system's URL routing and are not exposed. Recommendation: the product's pairing flow asks the person to scan with Sylvia's own scanner or paste the code, and does not advertise the link for the system Camera or other apps; if Sylvia ever has its own domain, a universal link (whose domain association iOS verifies) can replace the custom scheme. The Mac's prompt should also show the requesting address and the time, and the companion should list a device that never connected (Consequences).
- The Mac keeps only the SHA-256 of the secret, compares in constant time, and enforces: expiry on its own clock (default 10 minutes; the CLI allows 1 to 60); single use (the invitation is consumed as soon as a request presents the right secret, before the approval prompt, so a concurrent or later use fails whatever the user answers); an attempt limit (five wrong secrets destroy the invitation); and a rate limit (ten pairing requests per remote address per minute, then 429 with `Retry-After`). Invitations live only in memory; a restarted Mac has none.
- The phone validates the payload before using it: shape, version, identifiers, endpoint syntax, pin syntax, secret length and expiry on its own clock.

### Pairing exchange

1. The phone opens TLS to the first endpoint. Its `URLSession` delegate answers the server-trust challenge by computing the SPKI pin of the presented leaf certificate and comparing it in constant time with `spki_sha256`. A mismatch cancels the challenge: the handshake fails and no HTTP request, header or body (so neither the secret nor a token) is sent. The phone then tries the next endpoint.
2. Over the pinned connection the phone sends `POST /v1/pair` with `invitation_id`, `invitation_secret`, `source_id`, its own `device_id` (UUID made on the phone) and `device_name`.
3. The Mac checks rate limit, shape, secret, single use, expiry and source binding (in that order; see the OpenAPI document), consumes the invitation, and asks its user. The prompt shows the device name, device ID, remote address and the Mac's own fingerprint in uppercase groups of four (`2BF2 BE4A 247A ...`), which the phone also shows (plan 15.2: identity on both ends). No answer within 120 seconds is a denial; a late answer is ignored.
4. On approval the Mac creates a token of 32 random bytes, stores only its SHA-256 with the device record (`devices.json`, file mode 0600, written atomically and flushed), and returns `pair-response.v1`: token, `token_type` bearer, scopes, and the pin again. The phone checks that the response names the same source, device and pin before storing the token.

### Credentials and scopes

- Tokens are scoped to `catalog`, `read`, `download` and `receipt` (`TransferProtocol.allScopes`). There is no scope for deletion, upload, arbitrary paths or administration; the only destructive call a phone can make is revoking its own pairing.
- Tokens travel only in `Authorization: Bearer`. A request with a credential-like query parameter (`access_token`, `token`, `authorization`, ...) is refused with 400 and never used; durable transfer URLs therefore never contain secrets (plan 18.1).
- **Keychain accessibility (plan 14.2):**
  - Transfer credentials (the pairing token on the phone, the source identity key on the Mac): `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable, data protection keychain. Authorized background transfers must read the token while the phone is locked after its first unlock; "this device only" keeps it out of iCloud Keychain and device backups, so a restored phone must pair again.
  - AI provider credentials (owned by ADR-0011, recorded here as the agreed contrast): `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, not synchronizable. A provider request needs the user present, so the key is unreadable while the phone is locked. Neither class may be weakened to `kSecAttrAccessibleAlways*` or made synchronizable.
- The Mac never logs the token, the invitation secret or the pairing code. The CLI prints the code to its own terminal because that is how it reaches the phone; scripted runs redact it before writing any log.

### Transport

- HTTP/1.1 over TLS 1.2 or 1.3 (1.3 negotiated in every run so far), ALPN `http/1.1`. The server (NIOSSL, ADR-0009) offers only forward-secret AEAD suites with ECDSA for TLS 1.2 (`ECDHE-ECDSA-AES128-GCM-SHA256`, `ECDHE-ECDSA-AES256-GCM-SHA384`, `ECDHE-ECDSA-CHACHA20-POLY1305`). Clients set `tlsMinimumSupportedProtocolVersion = .TLSv12`. These settings meet App Transport Security's requirements, so no ATS exception is needed for the pinned connection; `NSAllowsArbitraryLoads` is never used.
- The phone's session is ephemeral: no URL cache, cookies or credential storage, no redirects (a redirect would otherwise carry pinned trust to another host; plan 14.3).
- After pairing, every connection is pinned the same way. A different key is `pinMismatch`, which pauses transfers with "The Mac's identity changed. Pair again and compare the fingerprint." There is no "ignore certificate" switch and no trust-all code path, in tests or otherwise.
- The service binds only explicitly named addresses (loopback by default). Wildcard addresses are refused unless the owner explicitly allows all interfaces. Bonjour advertises `_sylvia-src._tcp` with only the protocol major and source ID in the TXT record, and registers local-only when bound to loopback. An advertisement or an address is only a hint where to connect; the pin decides trust (plan 18.1: pairing advertisements are untrusted).
- Browsers are not clients: a request carrying `Origin` gets 403 and no CORS header is ever sent.
- Unauthenticated surface: `GET /v1/capabilities` (protocol version, limits, source ID; no titles, counts or names) and `POST /v1/pair`.

### Revocation and identity change

- The Mac owner revokes any device (CLI `revoke <device-id>`; the companion's device list later). A device may revoke only itself (`DELETE /v1/pairings/{device_id}`). Revocation is persisted before it is acknowledged and survives restarts; the token then gets 401 and the phone pauses with "re-authentication required", keeping verified bytes (plan 15.5). Revocation cannot erase files a phone already imported.
- A changed Mac key requires explicit re-pairing with a new invitation and fingerprint. Tokens from the old key are void even for a client that accepted the new key.

### iOS client: trust in background sessions (G0.2 part 2)

- **One trust path.** Every session of the transfer client (the foreground client of part 1, the background download session and the ATS probe) answers server trust only through `PinnedTrustEvaluator.answer` (`PinnedSession.swift`): the leaf's SPKI SHA-256 must equal the pin, then and only then the challenge is answered with that trust; otherwise it is cancelled and nothing is sent. `URLCredential(trust:)` exists once in the code base (checked by the CI drop-in). There is no host-name, CA or "allow anyway" fallback.
- **Task-level challenge only.** The background coordinator implements `urlSession(_:task:didReceive:completionHandler:)` and not the session-level method, because with a session-level handler URLSession delivers server trust there without the task, and the pin could not be tied to the job's own source. The task's description names its job; the job names its source; the source record holds the pin.
- **Pairing from the phone.** The harness decodes a pasted code or `sylvia://pair/v1#...` link (QR on a device), shows the source name, addresses, expiry and the fingerprint in uppercase groups of four, and sends nothing until the person taps Pair; the invitation then goes only over a connection whose key matched (part 1's `SourceClient.pair`). Before pairing the person may replace the code's addresses with one they type (the Mac moved, or the code lists an address the phone cannot reach); the pin and secret stay the code's, so another Mac at that address fails the pin check and receives nothing. The token goes to the Keychain (below) and the public pairing record (source ID, name, device ID, pin, endpoints, scopes) to the app's store; the code field is cleared afterwards whatever the outcome. Pasting, opening the link through the system and the replaced address leading to another Mac are XCUITests on the simulator (`simulator/pairing-entry.log`).
- **Addresses.** A manually entered address or a Bonjour result becomes an endpoint only after a pinned `GET /v1/capabilities` through it returns the paired source ID. Bonjour is a hint; the pin decides.
- **Local network permission denied** (plan 14.3 "permission denied", 15.5; round 2, finding R2-03). URLSession reports a connection refused by iOS local network privacy like any failed connection. After a network failure (unreachable, timed out, name not resolved, other transport error) the client opens a plain TCP connection to the same addresses (no TLS, nothing sent, closed at once; `LocalNetworkProbe`) and reads the connection path's `unsatisfiedReason`; `.localNetworkDenied` (Apple TN3179) turns the error into `localNetworkDenied`: pairing says "local network access is off for this app ... Settings > Privacy & Security > Local Network ... Nothing was sent", and a transfer that paused as `source_unreachable` is changed to `local_network_denied` with that next step. A pin mismatch, a TLS failure or an HTTP answer is never reclassified (the network worked). The denial itself exists only on a device, so the classification around the probe and the probe's other answers are tested on the host (`LocalNetworkProbeTests`, `background-host/local-network-check-*.log`, where the probe's answer is substituted) and the denial is checklist steps 4 and 18.
- **When the system asks the app** (simulator evidence, `simulator/relaunch-*.log`, `simulator/background-*.log`): the background session delivers each new connection's server-trust challenge to the app's task-level delegate while the app runs, in the foreground and also during a system background relaunch (`app_state=background_relaunch`, after `handleEventsForBackgroundURLSession`). Reused connections need no new challenge. No challenge was answered while the app was suspended or not running. After a kill, the system relaunched the app in the background once, about 4 s later; during that relaunch the app answered the waiting challenges of tasks it had created in the foreground (the source had accepted their TCP connection about 0.4 s before the relaunch, so the handshake waited for the app). Tasks the app created during the background relaunch opened no connection in the following 59 s, and the system did not wake the app again in that time; Apple documents that transfers started while the app is in the background are treated as discretionary ("Downloading files in the background"). Long background progress therefore depends on tasks created in the foreground and on the system relaunching the app; the device must show how this behaves when locked for minutes (checklist step 13).
- **Credentials in background tasks.** The bearer token is set as the `Authorization` header of each part request. For a background task the system's transfer daemon keeps that request, token included, until the task ends; it is outside the Keychain for that time. The window of four outstanding tasks per job bounds how many copies exist, and a revocation (401) or a pause cancels the job's tasks. Apple documents `Authorization` among headers URLSession may manage itself; it was sent unchanged in every run here (the source authenticated every part), but it is a platform behavior to re-check with each iOS release.
- **Keychain.** The token is stored with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable (part 1, `ci/simulator.log`), and read for every new task. A missing token pauses as `reauthentication_required`. If the Keychain refuses with `errSecInteractionNotAllowed` while the job store is readable, the job pauses as `device_locked` ("Unlock this iPhone to continue. Verified parts are kept.") and nothing is downgraded; this is a defensive rule, because the token and the store become readable at the same moment (below).
- **Files.** The transfer store (jobs, manifests, staging, ledger, event log) is created with `NSFileProtectionCompleteUntilFirstUserAuthentication`, the same "after first unlock" class as the token (plan 18.1). The simulator reports no protection class at all, so the class is unverified until the device step (checklist step 17).
- **Before the first unlock** both the token and the store are unreadable. The client does not act on that state at all: while any store file (`sources.json`, `imports.json`, a `job.json`) exists but cannot be read, which is what the class C files report before the first unlock (EPERM), it defers its launch (no session, so no outstanding task is adopted or cancelled; no job paused or rewritten; no store written; an unreadable store is never taken for an empty one). If that launch was a background relaunch for session events, the stored completion handler is called at once, so the system is not left waiting. The client starts again on `protectedDataDidBecomeAvailableNotification` (a retry trigger only) or at the next launch. Host evidence: `background-host/unreadable-stores-deferred.log`; device: checklist step 15.
- **Locked after the first unlock** the store and the token are readable, and background transfers must run: launch never defers then. `UIApplication.isProtectedDataAvailable` is deliberately not consulted: it reports class A (`NSFileProtectionComplete`) availability, which is false every time a phone with a passcode is locked, also long after its first unlock, so it cannot tell "before the first unlock" from "locked". The harness only logs it (`app_launch`, `coordinator_start`, `protected_data_will_become_unavailable`, `protected_data_available`) so the device run can see which state the phone was in. Host evidence: `background-host/locked-after-first-unlock.log` (protected data reported unavailable, every store readable: the relaunched client starts, reconciles, requests the missing parts and finishes). Device: checklist steps 8 and 13.
- Corrections. Round 1 (finding R1-04): an earlier version of this section said a job would be paused as `device_locked` before the first unlock, which could not happen, and the code would have treated the unreadable stores as empty. Round 2 (finding R2-01): the round 1 fix also deferred every launch while `isProtectedDataAvailable` was false, which would have stopped a locked phone's background relaunches from taking their session events (no session, no new part task, the completion handler never called) until the next unlock; the test that shows it failed on that code (`review/round2-before-fix.log`).

### App Transport Security (G0.2 part 2, plan 14.3)

Measured on the iOS 26.5 simulator with the harness (no `NSAppTransportSecurity` key) and two probe variants of it (`ats/ats-probe-*.log`; the variants are a separate, never-shipped app, `G02TransferATSVariant`):

| Address form | No ATS key | `NSAllowsLocalNetworking` | Per-domain exception `ts.net` and `100.64.0.0/10` with `NSExceptionAllowsInsecureHTTPLoads` |
| --- | --- | --- | --- |
| 127.0.0.1, ::1, `localhost`, LAN IPv4 (192.168.x), `<name>.local` | pinned HTTPS works (foreground and background); cleartext also loads | same | same |
| Tailscale IPv4 (100.64.0.0/10) | pinned HTTPS fails: the challenge reaches the app and the pin matches, then the connection fails with -1200 (stream -9802); cleartext blocked (-1022) | same as no key | pinned HTTPS works (foreground and background); cleartext loads too |
| MagicDNS name (`*.ts.net`) | same as the Tailscale IPv4 | same as no key | same as the Tailscale IPv4 |

What this means:

- For local forms ATS does not apply on iOS 26.5 (even cleartext loads), so the pinned self-signed design needs no exception there. (iOS 17 extended ATS to connections made with an IP address and let `NSExceptionDomains` take CIDR keys, per the iOS 17 release notes as quoted by Apple DTS in developer forum threads 731217 and 747421; private and loopback addresses were still treated as local here, and the Tailscale address worked once the variant declared the `100.64.0.0/10` key, which is the only key in it that can match a bare address.) Because ATS does not protect these forms, the client itself must never build a non-`https` URL for a source; today `PairingPayload.Endpoint.baseURL` is the only constructor and always uses `https`.
- For Tailscale forms ATS applies in full: it requires default trust (a CA-issued certificate for the name) after the delegate's answer, and a delegate cannot loosen that. `NSAllowsLocalNetworking` does not cover them. The only ATS key that loosens trust for a domain is `NSExceptionAllowsInsecureHTTPLoads`, which also permits cleartext HTTP to that domain.
- Plan 15.1 and XFER-04 promise an explicitly entered Tailscale address or MagicDNS name. **With the self-signed, pinned identity and no ATS key, that promise cannot be met.** This is a negative gate result, recorded with evidence; it changes the approach before release promises (plan 15.2, 21.1).

**Proposed for the security review and the product owner (not decided here):**

1. *Scoped exception* (measured working): `NSExceptionDomains` for `ts.net` (with subdomains) and `100.64.0.0/10`, each with `NSExceptionAllowsInsecureHTTPLoads`. The pin is still the only trust decision. The cost: ATS no longer stops a programming mistake from sending cleartext to those hosts, so the client must refuse any non-`https` URL itself (a check and a test), and the exception covers every tailnet name, not only the user's Mac. Narrow, explicit and validated, as plan 14.3 allows; it needs the reviewer's approval.
2. *Validated certificate for the MagicDNS name*: Tailscale can issue a publicly trusted certificate for `<mac>.<tailnet>.ts.net` (`tailscale cert`, Let's Encrypt). Default trust then passes with no ATS key and the app can still pin (pinning may tighten trust under ATS). Costs: HTTPS certificates must be enabled for the tailnet, the name is published in Certificate Transparency logs, certificates expire every 90 days, and the pin must follow the certificate's key (pin the key the Mac generates and reuses, or re-pair on renewal). Not tested here: issuing a certificate publishes the owner's machine name, which needs the owner's decision.
3. *No Tailscale route in v1*: keep LAN, `.local` and manual LAN addresses only, and change XFER-04's promise. Needs the product owner.

The spike's recommendation is option 1 for v1 (it keeps one trust model and is measured), with option 2 evaluated for later, subject to the security review; the harness stays without any ATS key until that decision.

### Rejected for v1

- A short human-typed code: needs a reviewed PAKE (for example CPace or SPAKE2) and is out of scope; the copyable invitation is the baseline the plan proposes.
- Trust on first use without a fingerprint: a rogue host on the LAN could answer first.
- A public CA certificate: there is no stable public name for a Mac on a LAN or tailnet, and it would add a third party to a local transfer.
- Client TLS certificates instead of bearer tokens: no gain over a pinned server plus a scoped token, and iOS client identities in background sessions add more failure modes.

## Consequences

- No CA, account or cloud relay is involved; trust is exactly the fingerprint the user carried from the Mac to the phone.
- Whoever sees a valid invitation (shoulder-surfing, a shared screenshot, a synced pasteboard) or receives it through a hijacked `sylvia://` link (above) holds both the pin and the secret until it is used or expires. The approval prompt, single use and a short expiry limit this; the device name on the prompt is chosen by the requester and is not evidence of which phone asked. The app must not leave the code in pasteboard history it manages (use local-only pasteboard items with an expiration) and should prefer scanning the QR code with Sylvia's own scanner, or pasting the code, over opening the link through the system. (Round 2 correction: an earlier version advised preferring "the QR or link" without the interception risk.)
- Background transfers with the pinned delegate work on the simulator: the system calls the task-level delegate for background download tasks while the app runs, also when it relaunched the app in the background. It was not seen to wake a suspended app only to answer a challenge, and tasks created during a background relaunch did not start while the app stayed suspended (59 s observed). Until the device shows otherwise, the honest promise is "continues in the background when iOS allows it, and resumes from verified parts whenever Sylvia runs", not uninterrupted background completion (plan I-10).
- Tailscale routes need an ATS decision (above) before XFER-04 can be promised.
- Rotating the Mac key always costs a re-pairing of every phone; this is intended.
- If the phone disconnects while the Mac user is deciding, an approval still creates a device record whose token was never delivered. It is harmless (the Mac holds only the token's hash) and the owner can revoke it; the companion should show such a device as "never connected".
- The unsigned CLI keeps its key in the login keychain, by explicit choice. The companion app must be signed with a keychain access group so the key gets the data protection class; with the default policy it fails to start rather than fall back. The signed probe (checklist step 20) checks this as soon as the team can sign again; the companion itself is re-tested when it exists.

## Alternatives considered

- **PAKE with a short code:** better ergonomics, but needs a reviewed implementation and protocol design; deferred.
- **Certificate pinning (whole certificate) instead of SPKI:** would force re-pairing whenever the certificate is reissued, with no security gain.
- **Storing tokens in the clear on the Mac:** rejected; a copied state directory would then grant access. Only SHA-256 digests are stored; 256-bit random tokens make offline guessing infeasible.
- **`kSecAttrAccessibleWhenUnlocked` for the transfer token:** safer while locked, but background transfers after first unlock would fail; the plan accepts after-first-unlock for transfer credentials only.
