## Decision

### Server stack: SwiftNIO with NIOSSL

The Mac source service is a Swift library plus a command-line host (`sylvia-source`) built on swift-nio 2.103.0 (NIOCore, NIOPosix, NIOHTTP1) and swift-nio-ssl 2.37.5, with swift-certificates 1.21.0, swift-crypto 5.0.0 and swift-asn1 1.7.3 for the identity (ADR-0008). Transitive packages in the lock: swift-atomics 1.3.1, swift-collections 1.7.1, swift-system 1.8.1. All are Apache-2.0; NIOSSL vendors BoringSSL (OpenSSL and ISC style licenses). The built service links two BoringSSL copies: swift-nio-ssl's (OpenSSL and SSLeay licenses) and, through swift-certificates' `_CryptoExtras`, swift-crypto's (Apache-2.0); each is updated only through its package's releases (ADR-0014, `Docs/Stage0/evidence/M0-dependencies/linkage.log`; added at M0 assembly). Versions are the ADR-0002 pins, required with `exact:`. The two XcodeGen projects that build these packages resolve them themselves, so each commits the same pins in its own `Package.resolved` (the identity probe through SourceService, the iOS harness through TransferKit), and the CI drop-in compares them (round 3, an M0 integration open item: without a lock the probe's transitive packages followed swift-nio's version ranges; `package-locks.log`).

Reasons, against Network.framework with a hand-written HTTP/1.1 layer:

- **Maturity and audit surface.** The HTTP/1.1 request parser is the part a LAN attacker talks to first. NIOHTTP1 uses llhttp (the Node.js parser), is fuzzed and deployed in production servers (Vapor, Hummingbird, gRPC Swift). A hand-written parser would be new code on that boundary with no history. The Sylvia-owned code is then only routing, authentication, Range and If-Match semantics, and file streaming.
- **Range correctness.** RFC 9110 range and precondition logic is Sylvia's code either way; it lives in the platform-neutral core (`HTTPRanges.swift`) so the client validates with the same rules, and is unit tested on its own and end to end. NIO provides exact framing: a declared `Content-Length` with no chunking, pipelining, keep-alive and back-pressure (`NIOAsyncChannel` writes suspend while the socket is not writable, so a slow phone never makes the Mac buffer a file).
- **TLS control.** NIOSSL lets the server fix TLS 1.2 to 1.3 and the exact TLS 1.2 suites and serve a self-signed P-256 identity from memory, without touching the system keychain's trust settings.
- **Costs accepted.** BoringSSL is bundled, so TLS security fixes arrive by updating the package, not with macOS updates; the dependency must be watched (ADR-0014 inventory). The packages are Mac-only: the iOS client uses `URLSession`, and `SylviaTransferCore` depends only on swift-asn1.
- **Connection lifecycle (found in the round 1 review).** NIO's async channel wrapper (`NIOAsyncChannel(wrappingChannelSynchronously:)`) traps the whole process if a wrapped connection is released before `executeThenClose` runs ("Deinited NIOAsyncWriter without calling finish()", a `preconditionFailure` that release builds keep). The first version handed wrapped connections to an accept loop through the listener's async sequence, which can drop them when the listener closes; stopping the source while a phone connected crashed it in 2 of 7 host-suite runs. Now each connection is wrapped in its child channel initializer and moved, in the same critical section, into the task that serves it, whose first action is `executeThenClose`; a connection whose initializer runs after `stop()` began is closed without ever being wrapped. A stress test stops the source 200 times while pinned TLS clients and stalled TCP handshakes connect in tight loops (`ServerStopStressTests`): it trapped with the old code (`review/stop-trap-before-fix.log`) and passes with the new (`review/stop-while-connecting.log`). This is what plan 16.3's "stop serving immediately" relies on.

### Platform-neutral core (iOS and macOS)

`Spikes/G02-Transfer/TransferKit` holds what both ends share and what the iOS background client (G0.2 part 2) imports: `SylviaTransferCore` (wire models, manifest model and semantic validator, part plan, Range and Content-Range parsing, strong ETags, response head and body validation with a recovery for every failure, the part state machine, SPKI pin computation, pairing payload codec, RFC 3339 and base64url codecs) and `SylviaTransferClient` (pinned `URLSession` delegate, Keychain credential store, durable part staging, a foreground transfer engine). Both build for iOS 26 and macOS 26 in Swift 6 mode with complete strict concurrency, and their tests pass on host and simulator.

### Endpoints (all under `/v1`)

| Endpoint | Auth | Behavior |
| --- | --- | --- |
| `GET /capabilities` | none | Protocol version, supported majors, source ID, part size default/min/max, limits, auth scheme, scopes, pin algorithm. No titles, counts or names. |
| `POST /pair` | none (pinned TLS) | ADR-0008. |
| `GET /catalog?cursor&limit` | `catalog` | Items ordered by `item_id`; the opaque cursor names the last item seen, so additions and removals never repeat or skip remaining items. `current_version_id` is null until prepared; `preparation_state` is `not_prepared`, `ready` or `source_unavailable`. |
| `GET /items/{id}/manifest?part_size` | `read` | Prepares the item if needed and returns its manifest. If preparation takes longer than 10 seconds, 503 `preparing` with `Retry-After`; preparation continues and the next request joins it. |
| `GET /assets/{id}/content` | `download` | Bytes of the current immutable version; Range and If-Match rules below. |
| `GET /device-inbox?cursor&limit` | `catalog` | This device's queue entries, oldest first. Listing marks them `observed_by_phone`; it implies neither download nor import. |
| `POST /receipts` | `receipt` | Idempotent receipts (below). |
| `DELETE /pairings/{device_id}` | any valid token | Self-revocation only. |

Every path is matched segment by segment against these routes; percent-encoding, empty segments, `.` and `..` are 400; every ID must be a lowercase UUID (400 `invalid_id`); an ID only selects an entry of the Mac's index, so no remote path reaches the file system. Another major version (`/v2/...`) is 400 `unsupported_protocol_version` with "Update Sylvia on both devices." Unknown optional fields are ignored by both ends. Errors use `error.v1` (`code`, `message`, `retryable`, optional `retry_after_seconds`); messages never contain secrets, paths or titles. Request bodies are limited to 64 KiB; a connection idle in both directions for 60 seconds is closed, except while its request is being handled.

### Immutable versions (Mac side)

- Items come only from user-selected roots: each top-level regular file is a single item; each top-level folder is a group whose regular files, recursively and sorted by relative path, are its ordered members. Hidden files, symbolic links and package contents are skipped. Item and asset IDs are UUIDs kept in the index across scans.
- **Preparing a version** opens each member from the root one path component at a time with `O_NOFOLLOW` (so a folder swapped for a symbolic link after the scan cannot redirect the read outside the root), clones it from that descriptor into the state directory with `fclonefileat` (APFS clone: no extra space, a point-in-time copy), or copies it with `fcopyfile` when the volume cannot clone (`ENOTSUP`, `EXDEV`). The original's stamp (size, mtime and ctime in nanoseconds, inode, device) is read before and after; if it changed during the clone the clone is discarded and retried, up to three times (then 409 `source_changing`). The clone is made read-only and then hashed: SHA-256 of the whole asset and of each part. The original is never served.
- **Detecting change.** Every catalog, manifest and content request compares each member's current stamp with the version's. Any difference, or a missing or damaged snapshot, invalidates the version: its snapshot is deleted (responses already streaming keep their open descriptor and finish with the old bytes), old ETags then fail with 412, and the next manifest request prepares a new version with a new `item_version_id`. A version's bytes therefore never change, and two versions' bytes are never mixed in one response.
- The content endpoint opens the snapshot inside the library actor right after confirming the version, so invalidation cannot remove the file between the check and the read.
- The index, device list and queue are small JSON files written atomically (temporary file, `F_FULLFSYNC`, rename, directory flush).

### Manifest (`transfer-manifest.v1`)

- Identity fields: `schema_version` 1, `protocol_version` {major 1, minor 0}, `source_id`, `item_id`, `item_version_id`, `created_at`, `manifest_digest`. Grouping: `kind` (`single` with exactly one asset, or `group`), `title`, optional `creators`. Optional `cover_asset_id` naming a listed asset.
- Per asset: `asset_id`, `ordinal` (array position), `display_name` (a label, never a path: no `/` or `\`), `media_type`, `length` (1 to 2^53 - 1 bytes), strong `etag` (`"sha256-<hex>"`, compared byte for byte), full `sha256`, `part_size`, and `parts` with `index`, `offset`, `length`, `sha256`.
- **Part size:** 16 MiB by default; any whole number of MiB from 1 to 64 MiB, advertised in capabilities and requested with `part_size`. Every part except the last is exactly `part_size`; the last is 1 to `part_size` bytes.
- **Manifest digest:** lowercase hex SHA-256 of an ASCII text, so any implementation can reproduce it without canonical JSON. Lines, each ending in a line feed: `sylvia-transfer-manifest-v1`, `protocol=<major>.<minor>`, `source=<source_id>`, `item=<item_id>`, `version=<item_version_id>`, `cover=<cover_asset_id or ->`, `assets=<count>`, then for each asset `asset=<ordinal>,<asset_id>,<media_type>,<length>,<etag>,<sha256>,<part_size>,<part_count>` followed by `part=<index>,<offset>,<length>,<sha256>` for each part. Display metadata (title, creators, display names, `created_at`) is excluded. The contract fixture generator computes digests in Python, independently of the Swift code.
- **Rejected before any byte is requested** (JSON Schema plus the Swift `ManifestValidator`): unsupported major version (checked first, so the user gets the update message), wrong schema version, invalid identifiers, a different source than the paired one or a different item than requested, no assets, zero-length asset, zero-length part, duplicate or out-of-order part, overlapping parts, a gap, missing final bytes, parts beyond the asset length, a short non-final part, part sizes that are not whole MiB within limits, weak or malformed ETag, malformed digest, a display name that looks like a path, control characters in metadata, duplicate asset IDs, ordinals that are not array positions, a single item with several assets, a cover that is not an asset, and a digest that does not match. Limits: 16 MiB of manifest JSON, 16,384 parts per asset, 65,536 per manifest, 4,096 assets per item, 512-character titles, 255-character display names, 16 creators.

### Content requests

- The client sends `Range: bytes=<offset>-<offset+length-1>` for exactly one part, `If-Match: <etag>` and `Accept-Encoding: identity`, with the bearer token.
- The server evaluates If-Match before Range (RFC 9110 section 13.2.2): missing If-Match is 428; `*`, a list or a malformed tag is 400; a weak or different tag, or an asset with no current version, is 412 with the current ETag if there is one. One satisfiable range is 206 with `Content-Range: bytes first-last/length`, `Content-Length`, `ETag`, `Accept-Ranges: bytes`; a last byte past the end is clamped; a first byte at or past the end is 416 with `Content-Range: bytes */length`; several ranges are 400 `multiple_ranges_unsupported`; a malformed range is 400 `invalid_range`; no Range is 200 with the whole asset. Responses carry `Cache-Control: no-store, no-transform` and `X-Content-Type-Options: nosniff`, never `Content-Encoding` or chunked framing.
- **The client accepts a part only if** the status is 206, there is no content or transfer encoding, the ETag equals the manifest's, `Content-Range` names exactly the requested bytes and the manifest's total length, `Content-Length` equals the part length, the body is exactly that long (extra bytes are never kept), and the body's SHA-256 equals the part digest. Headers are checked before any body byte is written. The body streams to a temporary file with an incremental hash, so memory does not grow with the part size.

### Failure handling (plan 15.4, 15.5)

| Observation | Recovery |
| --- | --- |
| 200 to a range request, wrong `Content-Range`, wrong or missing `Content-Length`, an encoding, short or long body, wrong part digest, connection lost, timeout, 429, 5xx | Discard this part's received bytes and request this part again (bounded retries with back-off; after four attempts the job pauses with `repeated_part_failure`, or `source_unreachable` for transport failures). |
| 412, 416, changed ETag, 404 for the asset | Fetch the manifest again and reconcile (below). |
| 503 `preparing` for the manifest | Show "Preparing transfer"; ask again every 2 seconds, for up to 30 minutes, then pause with `source_preparing`. |
| 401 | Pause: `reauthentication_required` (pair again). Verified parts are kept. This is also what a revoked token gets: authentication accepts only active devices, so the Mac answers 401 `invalid_token` (review finding R3-02). |
| 403 | Pause: `access_revoked`. To a part request the source answers 403 only for a scope the token lacks (`insufficient_scope`) or a browser `Origin` header, which this client never sends; revocation is 401, above. |
| Pin mismatch | Pause: `source_identity_changed` (pair again, compare the fingerprint). |
| Manifest invalid or protocol major unsupported | Pause: `manifest_invalid`, with the update message for a major mismatch. |
| Final full SHA-256 differs | Pause: `final_digest_mismatch`; every part is forgotten and nothing is handed off. |
| This device's storage is full (ENOSPC) while a part is kept | Pause at once: `insufficient_space` ("Free up space on this iPhone, then resume."); the part is not downloaded again until the person resumes. |
| Another local write error while a part is kept | Request the part again (bounded as above); after four attempts pause with `storage_unavailable`, never `source_unreachable`. |
| The system could not store a background download (the task ends with an out-of-space error in any shape, or an NSURLError file error: cannot create, open, close, write, remove or move the file; `didFinishDownloadingTo` is never called) | Out of space, or less free space than the part: pause at once with `insufficient_space`. Otherwise: retried, then `storage_unavailable`. Never `source_unreachable` (review finding R2-02). |
| Less free space than the bytes still to arrive plus one part for each task the window allows (four by default: the system's download file of each outstanding task), when a job is created or resumed, before the part requests of launch reconciliation, and before every new part request | Pause with `insufficient_space` before the request (plan 15.4 reservation; assembly and import are renames, so there is no assembly copy to reserve). Checked before every top-up since round 2, so space used by other apps mid-transfer is caught too, and before launch reconciliation's requests since round 3 (review finding R3-01: reconciliation, which runs at every launch including each background relaunch, used to request up to a window of parts without the check; `background-host/relaunch-low-space.log`, failing before the fix in `review/round3-before-fix.log`). |
| Transport failures exhaust the retries and the local network is denied to the app | `source_unreachable` is changed to `local_network_denied` ("Turn on Local Network for Sylvia in Settings > Privacy & Security > Local Network, then resume.") after a path check (ADR-0008, review finding R2-03). |

Nothing that fails these checks is ever appended to, or mixed into, verified bytes.

### Staging and resume (phone side)

- Per asset: a sparse `staging.bin` of the asset's full length, `journal.json` (item version, asset, ETag, digest, part size, verified part digests), `incoming/` for bodies being received, and `verified.bin` after the final check. A part body is copied into `staging.bin` at its offset while being hashed, the write is ordered with `F_BARRIERFSYNC`, and only if that hash equals the part digest does the journal (written atomically) record it. In the foreground client the body was already hashed while it streamed into `incoming/`, so this is a second check; in the background client (below) it is the first, so a body with a wrong digest has been written into its own part's region of `staging.bin` before it is rejected. That region is not journalled, parts never overlap, the next attempt overwrites it, and the final full SHA-256 covers every byte, so unverified bytes are never counted as verified or handed off. Storage needed is the asset length plus the parts in flight; the final file is a rename, not a second copy.
- On open (launch, retry, new engine): bodies left in `incoming/` are deleted unread; verified parts are kept only if the current manifest describes the same index, offset, length and digest, and (by default) only if their bytes in `staging.bin` still hash correctly; a stop between the final rename and its journal update is recovered by moving the file back and re-checking its parts.
- **Version change:** after a 412, 416 or changed ETag, the client fetches the manifest again. Parts whose bytes are identical in the new version are kept; the others are discarded and fetched. The final full SHA-256 then decides; a file is never assembled from two versions.
- **Concurrency (a spike decision; the product owner decides for v1, review finding R3-05).** The spike reads plan 6.4 ("two network transfers by default") and 15.4 ("two in-flight transfers and bounded queued parts") per job: at most two connections per host (`httpMaximumConnectionsPerHost`, a setting of the one session that every job shares, so two parts in flight to one Mac) and at most four outstanding part requests per job (the window). Nothing bounds the number of jobs downloading at once, so N jobs started together put up to 4N requests into the system's transfer daemon, each holding the bearer token (ADR-0008). The plan's wording more naturally limits transfers (jobs); the product's job scheduler (plan 6.4) should allow two downloading jobs at a time and queue the rest, or bound outstanding tasks across all jobs. Not built in the spike, because which one is a product decision (report open question 3). *(Decided by the product owner on 22 October 2026: PO-38 (a), the job scheduler lets two jobs download at a time and queues the rest, so at most eight requests carrying a Mac's token wait in the daemon; and PO-09, the 16 MiB parts, two connections per host and four outstanding tasks per job are kept, all tuned after G0.2 device steps 11 and 13. The scheduler is built in M1; nothing of it is built or measured yet.)* Retries re-request only failed parts. "Received" and "verified" byte counts are kept apart; the job is ready only after every asset's full SHA-256 matched.

### iOS background client (G0.2 part 2; plan 6.4, 15.4, 15.5)

`Spikes/G02-Transfer/TransferKit/Sources/SylviaBackgroundTransfer` (iOS and macOS, Swift 6, complete strict concurrency). The foreground engine's rules (verified-only journal, digest-gated handoff, never mixing versions) are kept; what changes is that bytes arrive as whole files from background download tasks.

- **Jobs before work.** `startJob` fetches and validates the manifest (waiting while the Mac answers `preparing`), writes `jobs/<job_id>/manifest.json` and `job.json` (durable: temporary file, `F_BARRIERFSYNC`, rename), and only then creates tasks. Job states: `downloading`, `refreshing` (fetching a new manifest after 412, 416 or a changed ETag), `paused` (with a `PauseReason` and its next step), `assembling`, `ready_for_import`, `imported`, `cancelled`.
- **One download task per part** in `URLSessionConfiguration.background(withIdentifier:)` (`sessionSendsLaunchEvents`, not discretionary, no cache, cookies or credential storage, TLS 1.2 minimum, two connections per host). Each request has exactly one `Range`, `If-Match` with the manifest's strong ETag, `Accept-Encoding: identity` and `Authorization: Bearer <token>`; the token is read from the Keychain for every new task, so a deleted credential stops new requests at once. At most four tasks per job are outstanding (requested or queued); finished tasks are topped up from the delegate. Retries of a failed part use `earliestBeginDate` back-off (1 s per earlier failure), and `willBeginDelayedRequest` cancels a delayed retry whose job no longer wants the part.
- **Task descriptions** are `sylvia-xfer/1 job=<uuid> asset=<uuid> part=<n> attempt=<n>`: identifiers and counters only, parsed strictly (`TaskDescriptor`); anything else is a foreign task.
- **Completion.** `didFinishDownloadingTo` (1) checks the response head with the same `PartResponseValidator` as the foreground client (206, Content-Range, Content-Length, ETag, no encoding); a failed head is discarded without opening the file; (2) moves the file synchronously out of the system's temporary location into the asset's `incoming/` folder; (3) checks its length and copies it into the sparse `staging.bin` at the part's offset while hashing it (the first hash of these bytes: nothing hashes the downloaded file before), orders the write to disk, and journals the part as verified only if the digest matched (see "Staging and resume" for what a mismatch leaves behind). A full disk during the move or the copy is `insufficient_space` at once; another local error is retried, then `storage_unavailable` (review finding R1-05; before, both were reported as transport failures and ended as "Make sure the Mac is awake"). `didCompleteWithError` then applies the recovery table above. Bytes for a part whose job is paused, cancelled or already has that part are discarded.
- **Download tasks cannot reject a bad head before the body.** The system writes the whole response body to its own temporary file before the app sees the response; the head is checked before that file is opened, and while the app is running a body longer than the part is cancelled (`didWriteData`). A misbehaving source could therefore make the system download more than one part's length once per task while the app is suspended; only the paired, pinned and authenticated source can do that.
- **Assembly is journalled.** When the last part is verified the job is recorded as `assembling`, each asset's staging journal records the full SHA-256 check and the rename to `verified.bin` (a stop between the rename and its journal entry is repaired on open), then the job is `ready_for_import`. A final digest mismatch forgets every part and pauses (`final_digest_mismatch`).
- **The full-file check runs outside the lock** (review finding R2-04). Under the coordinator's lock the job is only marked `assembling` and the check is scheduled on a utility queue; the full SHA-256 reads the whole item there, and the result is applied under the lock afterwards: the staging stores' new state is kept if the job still has staging for that version, and the job moves on only if it is still `assembling` (a pause meanwhile keeps the finished file for the resume; a cancel has deleted the staging and the result is dropped). One check runs per job at a time. A background relaunch's completion handler is called only after every running check has published its result, so the app does not tell the system it has finished its events while a check is still running. That does not buy time: the system may still suspend the app before the check ends, in which case the job stays `assembling` and the next launch re-hashes the verified parts and repeats the check from the journal (review finding R3-04 corrected an earlier sentence that said holding the handler kept the system from suspending the app). Nothing requests extra background time (`beginBackgroundTask`, `BGProcessingTask`), so whether a 5 GiB check can finish in a background relaunch on a phone is unmeasured (checklist step 22; open item). At 5 GiB on the host the check took 2.1 to 2.3 s in most runs, 6.8 s in one repeat run at a load average of 69 to 86, and 29 s in a development run whose load average rose to 67 (`review/round3-5gib-dev-run.log`), while `jobViews()` (the transfer screen, on the main thread) kept answering: polls made while the job showed `assembling` took at most 34 ms (asserted under 250 ms; `faults/large-5GiB-background-client.log`, `review/round2-5gib-repeat.log`, `review/round3-5gib-repeat.log`). Before, the check ran under the lock, so the screen would have waited for the whole read, and `assembling` was never even visible. Free space for the reservation is also read before the lock is taken: the "available for important usage" figure is a request to the system (about 20 ms idle on the host, and long enough with the disk busy that the first clean run caught a 425 ms wait, `review/round2-first-clean-run-failed.log`).
- **Part commits still hold the lock.** Copying and re-hashing one 16 MiB part into `staging.bin` (and its write barrier) happens under the lock in `didFinishDownloadingTo`; each `part_verified` event logs its `commit_ms`. On the host: median 11 ms, at most 19 ms in the round 3 clean run, 50 ms in the round 2 repeat runs and 61 ms in a round 3 development run under load, and one `jobViews()` call waited 180 ms in an earlier run (report finding 20). The import's file work (ledger writes, renames, job record, staging deletion) also runs under the lock; since round 3 the `imported` event logs its `import_ms` (4 and 14 ms in the round 3 runs), and the 5 GiB log says what the slowest `jobViews()` call returned, which tells the two apart (report finding 22). On an old phone this may be several times longer per part; checklist step 11 records `commit_ms` and any hang (on device A, since 24 October 2026 the iPhone 13 mini, an A15 phone, so a short `commit_ms` there does not show an A13 phone's: Evidence), and the product should move the commit off the lock if it shows.
- **Exactly-once handoff.** `StubImporter` stands in for the importer (plan 8.1): a ledger keyed by item version records an `importing` intent with a fixed import ID and destination, moves the verified files (a rename), then records `imported`. A stop at any point is completed by the next call; calls after `imported` change nothing and are counted as duplicates. After the import the job's staging is deleted and two receipts (`downloaded_to_phone`, `imported_into_sylvia`) are posted with receipt IDs and a time fixed in the job and the import record, so a retry after a crash is the same receipt and the Mac answers `duplicate: true`.
- **Launch reconciliation** (`ReconciliationPlanner`, run once per launch before any new task is created): jobs, verified parts (re-hashed when the staging stores open), the background session's outstanding tasks and the credentials are compared. Tasks with a foreign description, an unknown or finished job, a part already verified or no longer in the manifest, or a duplicate of another task for the same part are cancelled; one task per wanted part is adopted; missing parts are requested up to the window, after the plan 15.4 reservation (a job without the space pauses with `insufficient_space` and the launch requests nothing for it; review finding R3-01); a job whose credential is missing or revoked is paused (`reauthentication_required`) and one whose Keychain refuses to answer is paused (`device_locked`, a defensive rule: see the deferred launch below), in both cases with its verified bytes kept; complete or interrupted assemblies are finished; jobs ready for import are handed to the importer again; jobs interrupted while refreshing fetch the manifest again. A task whose completion the delegate received before reconciliation ran is never adopted, even if `allTasks` still lists it (the two answers are not ordered); adopting it would hold its part's slot for ever. Found in review on 12 October 2026, covered by `taskCompletedBeforeReconciliationIsNotAdopted`, which fails without the rule (`review/completed-task-adopted-before-fix.log`).
- **Deferred launch (review finding R1-04).** Before the first unlock after a restart the store's files (`NSFileProtectionCompleteUntilFirstUserAuthentication`) cannot be read. The first version read them with `try?` and took an unreadable `sources.json` or import ledger for an empty one, listed unreadable jobs as unknown, and would then have cancelled every outstanding task as belonging to an unknown job and, after the unlock, written the empty lists over the real ones. Now launch is deferred while any store exists but cannot be read: no session is created (so no outstanding task is listed, adopted or cancelled), no job is paused or rewritten, and the stores refuse writes (`StoreUnreadable`, `ImportError.ledgerUnreadable`); a background relaunch's completion handler is called at once; the app starts again on `protectedDataDidBecomeAvailableNotification` or at the next launch. `UIApplication.isProtectedDataAvailable` is only logged, never a reason to defer (review finding R2-01): it is false whenever a phone with a passcode is locked, also after its first unlock, when the stores and the token are readable and background relaunches must take their events (`background-host/locked-after-first-unlock.log`; the round 1 code failed that test, `review/round2-before-fix.log`). A damaged (undecodable) store defers launch too and needs a repair path in the product (the job store's decided by the product owner on 22 October 2026, PO-12 (a); the sources file's and the import ledger's on 23 October 2026, each set aside and recovered, Open items). Host test: `unreadableStoresDeferLaunchWithoutCancellingOrOverwriting` (chmod 000 stands in for the data-protection refusal), `background-host/unreadable-stores-deferred.log`; device: checklist step 15.
- **Launch re-hash outside the lock.** The verified parts are re-hashed when the stores open at launch (and on resume) without holding the coordinator's lock, so the transfer screen's polling is not blocked: 2.7 GB re-hashed in 1.0 to 1.6 s on the host, while the slowest `jobViews()` call during it took at most 3.6 ms (`faults/large-5GiB-background-client.log`, `review/round3-5gib-repeat.log`). A version change still re-hashes the kept parts under the lock, so that the new manifest, the record and the staging stay one step against a concurrent pause or cancel.
- **Progress.** "Received" counts verified bytes plus bytes written by running tasks; "verified" counts only journalled parts. Both are rounded down for display, so "5.2 of 5.2 GB verified" appears only when every byte is verified (`ProgressText`; "3.1 of 5.2 GB verified").
- **Event log.** `events.jsonl` holds identifiers, counts, codes, addresses and app states (no tokens, codes, titles or paths) as evidence and for diagnostics.

### Queue and receipts (Mac side, plan 16.2)

- "Send to device" prepares the item and appends a durable queue entry `queued_on_mac` for one device. Listing the inbox marks entries `observed_by_phone`.
- The phone's background client reads the inbox (`BackgroundTransferCoordinator.inbox`, the harness's "Check inbox"), starts a job with the entry's `queue_entry_id` (kept in `job.json`), and its receipts name the entry, so the Mac's entry moves to `downloaded_to_phone` and `imported_into_sylvia` (round 2 gate gap; host: `background-host/device-inbox.log`; simulator: `simulator/background-device-inbox.log`). When the phone polls is a product decision (plan 15.1 "pull-first"); the harness polls when the person taps the button. *Decided by the product owner on 22 October 2026 (PO-13 (b), not the recommended (a)):* the phone reads the device inbox on launch, on returning to the foreground and when the Inbox is shown, while a paired Mac is reachable, and also periodically in the background when iOS runs the app. The background reads are opportunistic: iOS decides whether and when the app runs, so they add no promise of timely delivery, and plan 15.1 still promises no real-time delivery. A background read follows the client's rules for any launch and request: before the first unlock the stores are unreadable and the client defers (Deferred launch), and the request carries the bearer token like every other (ADR-0008). Not built or measured in Stage 0, where the harness reads the inbox only on request; M6 builds it with the queue and receipts, and how often a phone actually runs it is unknown until then.
- `POST /receipts` with `downloaded_to_phone`, `imported_into_sylvia` or `import_failed` (with a failure code and message). `receipt_id` is the idempotency key: the same ID and same content again returns the stored acknowledgement with `duplicate: true` and changes nothing; the same ID with different content is 409. Another device's entry is 404. Entries never move backwards (a late "downloaded" after "imported" stays imported). An import failure keeps the entry for retry. No receipt deletes or modifies the original. The acknowledgement's body is `receipt-ack.v1` (`Contracts/schemas/receipt-ack.v1.schema.json`: `receipt_id`, `queue_entry_id` and `entry_state`, null for a catalog download that has no queue entry, and `duplicate`), moved on 19 October 2026 from the OpenAPI's inline `ReceiptAck` into a schema with fixtures, and two acknowledgements captured by the host tests (M0 final review, contracts R1-06; `Docs/Stage0/integration-log.md` section 11). Since 20 October 2026 the schema also states that `queue_entry_id` and `entry_state` are both null or both set, as the server writes them (`OutboundQueue.apply` sets the entry's state exactly when the receipt names an entry), with an invalid fixture for each mixed form, and the host tests capture an inbox entry's acknowledgement too (final review round 2, contracts R2-05; tightened before v1's first release, as `Contracts/README.md`'s versioning rule allows; the owner after M0, M6, may revisit it).
- If an original changes after queueing, the entry points at the newest prepared version (or null until one is prepared).
- The three acknowledgements "Queued on Mac", "Downloaded to phone" and "Imported into Sylvia" are separate states; successful HTTP delivery is never treated as an import.

### Discovery and addresses

Bonjour service type `_sylvia-src._tcp` (TXT: `pv`, `sid`). Manual addresses (IPv4, IPv6, DNS names including Tailscale MagicDNS) come from the pairing payload or user entry; nothing depends on multicast or a public port.

## Consequences

- The phone can trust a finished file without trusting the Mac's file system or the network: every byte is checked against a manifest that was itself checked.
- A changing original costs a re-preparation (a clone and a hash) and refetching the parts whose bytes changed; it never costs correctness.
- Sources on a volume that cannot clone (or on a different volume from the state directory) are copied in full when prepared. The companion must account for that space and say "Preparing transfer" while it happens (plan 16.2).
- Hashing happens at preparation, so the first manifest request for a large item waits for a full read and hash of the clone. Beyond 10 seconds the phone is told `preparing` and polls instead of holding a silent request open past its timeout (found in review; `slowPreparationAnswersPreparingAndTheClientWaits`). Preparation time on slower Macs and external drives is not yet measured.
- BoringSSL updates come through swift-nio-ssl releases.
- The background client keeps the foreground engine's rules except one: with download tasks the system stores a response body before the app can see its head (see above). Head checks still happen before the file is opened.
- Every outstanding background task holds the bearer token in its request headers inside the system's transfer daemon until the task ends (ADR-0008). The window of four tasks per job bounds that per job; across jobs nothing does yet (Concurrency, above).
- Re-hashing verified parts at every launch costs a full read of the staged bytes: 1.0 to 1.6 s for 2.7 GB on the host under varying load (Apple M5 Max SSD, `faults/large-5GiB-background-client.log`, `review/round3-5gib-repeat.log`); a phone is slower and is not measured (checklist step 11). It no longer blocks the coordinator's lock; the product may still limit it to launches after an unclean stop.
- A manifest refresh after 412, 416 or a changed ETag uses a foreground request; if the app is suspended first, the job stays `refreshing` and is resumed at the next launch.
- Tasks are topped up from delegate callbacks, so after the app leaves the foreground new part tasks are created in the background. On the simulator such tasks opened no connection while the app stayed suspended (59 s observed, `simulator/relaunch-*.log`), consistent with Apple's statement that transfers started in the background are treated as discretionary. A four-task window therefore gives little background progress; whether to create tasks for more parts while in the foreground (more requests holding the token in the daemon) is decided after the device measurement (checklist step 13; report finding 4).

## Alternatives considered

- **Network.framework with a hand-written HTTP/1.1 server:** system TLS and no third-party code, but a new parser on the network boundary and more Sylvia code to audit; rejected for the spike, revisit only if dependency policy forbids NIO.
- **Whole-file download with URLSession resume data:** cannot guarantee immutable parts or detect a changed source before the end; kept only for ordinary third-party URLs (plan 15.4).
- **Serving the original file with mtime checks:** a change during a read would mix versions inside one part; rejected in favor of clones.
- **Canonical JSON for the manifest digest:** harder to reproduce exactly across languages than the line format.
- **Multipart ranges:** more parsing for no benefit when parts are requested one at a time.
