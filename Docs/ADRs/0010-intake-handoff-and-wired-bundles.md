## Context

The share extension must never say a file was received unless the bytes are durably in Sylvia's hands (I-03), and the main app must never treat a partial copy as a book (I-04) (plan 6.1, 8.1). The Mac companion's cable route needs a bundle format that a partial Finder copy can never pass (plan 8.5, 16.4), and the Finder-visible Documents folder must hold nothing private (plan 16.4). The plan asks for an audited archive implementation tested above 4 GiB; its choice also governs the later `.sylviabackup` container (ADR-0012). Evidence is in `Docs/Stage0/G03-Intake.md`.

## Decision

### 1. Share-extension handoff

**Where.** The App Group container (`group.com.jevidon.sylvia` in the product; `group.com.jevidon.sylvia.spike` in the spike) holds `Intake/Handoffs/<handoff-id>/`. Nothing else is shared between the app and the extension. The inbox is staging class (plan 17.1) and is excluded from device backup: the extension marks it when it creates its first handoff (it can run before the app has ever launched), and the app's bootstrap marks it again.

**What the extension accepts.** Per attachment, in this order: the first registered type that conforms to EPUB, PDF, Markdown, plain text or audio (excluding source code, scripts, executables and playlists), loaded with `loadFileRepresentation(for:openInPlace: true)`; otherwise a `public.file-url` whose extension maps to a supported type. A web URL is refused with the "not a durable file" fallback: URL import belongs to the main app (plan 8.1). A folder offered as a file (an EPUB stored unpacked as a package directory, as iCloud Drive or a Mac's Books library can keep one) is refused with its own reason, "offered this book as a folder", and only the Mac route is offered (section 4). At most 100 attachments per share. Markdown extensions (`md`, `markdown`, `mdown`, `mkd`, `mkdn`) are mapped explicitly because iOS maps only `.md` to the Markdown type, and an app's imported type declaration does not change that (finding F3 in the report).

**Write sequence** (`HandoffSession`, `SylviaImportHandoff`). Each step is a fault-injection point (`HandoffWriteStep`):

1. `checkSpace`: when the size is known, refuse before copying if the item exceeds the per-item limit (20 GiB, plan 8.3) or the volume lacks the size plus a 64 MiB margin (`volumeAvailableCapacityForImportantUsage`); the fallback names the shortfall.
2. `createStagingDirectory`: `Handoffs/<uuid>/` and `items/`, mode 0700, parent synced.
3. Per item, inside the provider's completion handler (the provider may delete the file when it returns) and inside a coordinated read with security-scoped access: `openSource` (non-blocking open, must be a regular file), `createDestination` (`items/<n>[.<ext>]`, `O_EXCL|O_NOFOLLOW`, 0600; the name never comes from the shared file name beyond a sanitized extension), `readChunk`/`writeChunk` with one 1 MiB buffer while hashing SHA-256 (memory independent of file size), `syncItem` (`F_FULLFSYNC`), `closeItem` (checked), `verifyItem` (byte count; source size and modification time unchanged).
4. `syncItemsDirectory`.
5. `writeManifestTemporary`, `syncManifestTemporary`, `renameManifest` (`renamex_np(RENAME_EXCL)` to `handoff.json`: the commit point), `syncHandoffDirectory`.
6. Only then does a `HandoffReceipt` exist (its initializer is private to the commit), and only a receipt lets the UI show "Received".

Any thrown failure removes the handoff directory and shows the fallback (section 4); nothing claims receipt. If the process dies instead, the directory has no `handoff.json` and is incomplete by definition. Provider stalls: if the provider makes no progress for 60 s before delivering a file, the load is cancelled and the fallback shown; once copying has started there is no timeout, only user cancellation. "Progress" is any change in the loading Progress's completed count, total or fraction completed. The Progress that `loadFileRepresentation` returns wraps the provider's own Progress as a child, so while the provider works only `fractionCompleted` moves; the count stays 0 until delivery (measured on macOS Foundation). The first implementation watched the count and so cut off a provider that was still sending: run against that detector, the host test of a provider that reports progress for six times the stall limit and then delivers fails at the first stall interval (`host-stall-detector-before-fix.log`); with the fix it passes. Whether an iCloud download reports its progress through this Progress on a device is checklist step 18. The stall rule acts only before the copy begins: the timeout finishes the share through the same check, under the same lock, that the provider's completion handler passes to begin its copy, and cancels the load only when it did finish the share, so a provider that delivers at the moment the limit is reached is received (review R4-04: the first version checked, then finished unconditionally, so a delivery in between started a copy into a session the caller then discarded, and the share ended as "stopped sending").

**Cancel** (`CancellationSignal`) acts in every phase, so the sheet can always be cancelled, including in the unbounded wait the stall rule allows: before the provider delivers, it cancels the load's Progress and fails the share as cancelled at once; while a coordinated read waits for another writer, it cancels the coordinator (a coordinator cancelled just before its coordinate call returns at once with NSUserCancelledError; a platform test pins this on host and simulator); during the copy the copier checks it before every read; after the last byte the commit checks it before writing the manifest. Once the commit has started, its receipt stands. Cancelling the load reaches the provider's Progress when both are in one process (host); through the share sheet on the simulator it did not reach the sharing app within the ~15 s observed (`simulator-share-sheet-item-provider-observation.log`), so a sharing app may finish a download after the user cancels; checklist steps 9 and 18 record Mail and iCloud on a device. Before this change the three wait tests ran until delivery or the other writer finished, 30-62 s (`host-cancel-before-delivery-before-fix.log`).

**Manifest.** `handoff.json`, contract `import-handoff-manifest` v1 (`Contracts/schemas/import-handoff-manifest.v1.schema.json`): handoff id (equals the directory name), producer, items (stored path, original file name as metadata only, content type, byte count, SHA-256, representation) and total bytes. At most 256 KiB (262,144 bytes), whitespace included, as the schema's description states: the app's scan refuses a larger file, and the extension refuses to commit one and shows the fallback ("The names of the shared files are too long to record in one share"), so a receipt always means the app can read the manifest (review R4-02). 100 items, the share limit, with 255-byte file names and 128-character type identifiers take 87,803 bytes; only names of characters that JSON writes as escapes, such as control characters, with long type identifiers exceed it. Before decoding, the reader checks the whole text (`StrictJSON.swift`): strict JSON (RFC 8259) in UTF-8 without a byte order mark, no member name twice in one object, no unpaired surrogate escape, at most 512 levels of nesting, integers of at most 4,300 digits, no NaN or Infinity. JSONDecoder alone accepted trailing commas, a byte order mark, UTF-16 and UTF-32, did not look inside members it does not decode, and kept the first of two members with the same name where the contract validator keeps the last (report F16). UUIDs must be in the canonical 8-4-4-4-12 form: `UUID(uuidString:)` alone accepted a UUID followed by U+0000 and anything after it. The reader checks every string bound of the contract in code points, as JSON Schema counts them, and reads `created_at` exactly as the contract's `date-time` format accepts it (`RFC3339.swift`; JSONDecoder's `.iso8601` strategy disagreed in both directions, report F16). `original_filename` is bounded in UTF-8 bytes (255), stricter than the schema's code-point bound for non-ASCII names, which the schema's description states with an example; it must hold no "/" and no U+0000 anywhere, tested on bytes, because Swift's Character-based `contains("/")` misses a "/" that a combining mark follows (report F18). The extension's writer replaces each "/" code point of the shared file name with "_" and drops U+0000 (its first version used Foundation's `replacingOccurrences`, which misses such a "/", so the share failed). `producer.kind`, digests and the items' names are compared byte for byte, and the representation is decoded byte for byte: Swift's `String` equality takes canonically equivalent text as equal (review R4-01; section 2).

**Main-app scan** (`InboxScanner`), on launch and on every foreground, serialized:

- A directory with `handoff.json`: read it (size-limited, no symlinks), validate it, require the `items/` listing to equal the manifest, and re-hash every item. Then the commit journal (plan 8.2): `verified` → journal row `accepting` (commit intent) → rename `Handoffs/<id>` to private `Staging/Staged/<id>` (same volume; a cross-volume fallback copies to a `.partial` name and publishes with one rename) → re-check that `items/` still holds exactly the journaled items at their journaled sizes (after the move nothing but the app can reach them; before it, an extension whose commit failed late may have deleted its directory) → journal `staged`, or `needs_review` when another job already holds the same bytes. A crash between any two steps is finished on the next scan; a scan is idempotent (one job per handoff id). A journaled job whose bytes fail the re-check, or fail re-verification during crash recovery, ends as `failed_final` with its directory in `Staging/Rejected/`; it is reported, never retried silently and never staged.
- A directory with a bad or tampered manifest is moved to `Staging/Rejected/` and recorded; it is never journaled. Rejected directories are kept 7 days for "Inspect details", then removed with a cleanup record (`rejected_expired`).
- **Cleanup policy for manifest-less directories:** left alone while the newest modification time anywhere in the tree is less than 1 hour old (a live extension updates it with every 1 MiB chunk; a future time is never stale). Once older, the directory is first claimed with one rename into private `Staging/Abandoned/` and checked again for a manifest: if the extension committed in that window the directory is put back and imported by the next scan; otherwise it is deleted with a cleanup record (name, reason `abandoned_incomplete`, bytes freed, time). Deleting in place instead would leave a window in which a slow but live extension renames its manifest into a directory whose items are being deleted. After a claim, every later step of a still-live extension fails (its paths are gone), so it shows the fallback; the policy can cost a retry, never a false "Received". A crash between claim and delete is cleaned up on the next scan (a claimed directory with a manifest goes back to the inbox). Stray non-UUID entries follow the same age rule (`unexpected_entry`).

**Other routes** (`DropAreaImporter`). Open-in, AirDrop, the document picker and a raw supported file that Finder copied into the drop area take a coordinated, security-scoped snapshot into `Staging/Extracting/<job-id>` (an APFS clone of the open file, hashed after cloning; a streamed copy across volumes), then use the same intent → rename → staged sequence and the same duplicate rule (T08). The document picker opens the chosen file in place (`UIDocumentPickerViewController(forOpeningContentTypes:asCopy: false)`): the app gets a security-scoped URL to the provider's own file, reads it only inside the coordinated read, and never modifies or removes it (I-08). A raw drop-area file has no manifest, and Finder does not coordinate: if the file's device, inode, size or modification time changed between the snapshot and the end of hashing, the import is refused as still being written and nothing is staged; a copy that has paused or stopped is not detected and is staged as it is, for the type's later validation (plan 8.2; report F15). A `.sylviapack` that arrives by open-in or AirDrop goes through the bundle importer instead. A system copy in `Documents/Inbox` is removed when its import ends, whether it succeeded or failed (section 5). On launch `recoverInterruptedImports()` finishes jobs whose intent was recorded (bytes are complete and synced before the intent), marks an intent without bytes `failed_final`, and removes extractions without an intent.

### 2. `.sylviapack` v1

A single-volume ZIP, ZIP64 when sizes or offsets need it, written in one pass by Sylvia's writer. The reader accepts only this exact shape:

- Entry 1 `sylviapack/manifest.json` (stored, at most 16 MiB, whitespace and unknown members included, as the schema's description states), contract `sylviapack-manifest` v1: pack id, generator, files (relative path, size, SHA-256, media type, kind, optional group and order), groups (audiobook or publication, optional title, creators, language, identifiers, member-order basis) and total size.
- Entry 2 `sylviapack/manifest.sha256` (stored, exactly 65 bytes): lowercase hex SHA-256 of entry 1's bytes and a line feed.
- Then one entry `content/<path>` per manifest file, in manifest order. Audio, EPUB, PDF and covers are stored (method 0, no redundant compression); text and Markdown may be deflated (method 8).
- Entries are back to back from offset 0, then the central directory, then (when present) the ZIP64 end record and locator, then the end record in exactly the last 22 bytes. No archive or entry comments, no gaps, no data descriptors, no encryption, no general-purpose flags other than UTF-8 names, version needed at most 4.5, single disk.
- Entries are regular, non-executable files: the writer sets Unix mode 0644; the reader refuses directory entries, symlinks, devices, FIFOs, sockets, any execute or set-id bit, and entries made by hosts other than Unix, macOS or MS-DOS.
- Paths: NFC, relative, 1-15 components, no empty, `.` or `..` component, no backslash, colon or control characters, at most 512 bytes (255 per component), unique after case folding and normalization, and no path is also another path's folder. An entry name is `content/` plus the path, so entry names have at most 16 components and 520 bytes, and every path the manifest rules accept makes an entry name the entry rules accept (the first version allowed 16 components and 1024 bytes for both, so a conforming path at the limit made a pack the reader refused). 512 bytes because extraction joins the path to a container directory (about 180 bytes on a device, 250 on the simulator) and the result must stay below PATH_MAX, 1024 bytes. The byte limits are the rule. The contract's `maxLength` and pattern count code points, so for non-ASCII text they admit longer paths, which writers must not produce and readers refuse: 'é' 100 times, '/', 'é' 100 times, '/', 'é' 100 times and '.epub' (307 code points, 607 bytes) is valid against the schema and refused by the reader (`unsafe_path`), while a 512-byte non-ASCII path of 258 code points is accepted by both and extracts (test "non-ASCII manifest paths ..."). The schema's description gives the same example. Every separator, prefix and dot-component test works on UTF-8 bytes (`PathBytes.swift`), never on Swift `Character`s: a "/" followed by a combining mark (U+0301) or preceded by a prepended mark (U+0600) forms one `Character` with it, and the first version, which split and compared Characters, accepted ".." + "/" + U+0301 + "x" (a ".." component to the file system) and extraction wrote that file into the parent of its extraction directory; it also missed hidden empty components, a hidden leading "/", hidden depth and a hidden file-and-folder conflict (report F18; the schema's pattern refused all of them). As defense in depth, extraction also refuses any target whose standardized path is not inside its directory, compared byte for byte.
- Other manifest fields: the text is checked as in section 1 (strict JSON, no member name twice), an optional member that is present must not be null (the schema admits null nowhere), `pack_id` must be a canonical UUID, every string bound of the contract is checked in code points (generator name and version, media type, group title, creators, language, identifier scheme and value), any `order` below 1 is refused, and `created_at` is read exactly as the contract's `date-time` format accepts it, its instant counted in the proleptic Gregorian calendar as RFC 3339 and Python count it (review R4-03: Foundation's Gregorian `Calendar`, which the first version used, is Julian before 1582-10-15, so 1582-10-10 came out ten days late). A file's `group_id` must match the contract's pattern before its group is looked up (review R4-01: the groups were in a `[String: GroupKind]` dictionary, and Swift's `String` hashing and equality took "WALDEN_" + U+212A KELVIN SIGN for the group "WALDEN_K", so the reader, the writer's self-check and extraction accepted a manifest the schema refuses). Manifest text is compared byte for byte (entry names against the manifest's paths and the archive library's names, digests, `format`), enum values are decoded byte for byte, and only pattern-checked ASCII is kept in sets and dictionaries; the duplicate-path rule alone deliberately treats paths as equal after case folding and normalization, which refuses more.
- The rule for both readers is that they accept nothing their schema refuses, and that where the schema accepts and a reader refuses, the reason is in one of three classes, each stated in the schema's description: rules the schema leaves to readers (byte limits of paths, file names and whole manifests, NFC, uniqueness, sums, group rules, size limits); limits that RFC 8259 and the contracts' 64-bit units leave to readers (a member name given twice, an unpaired surrogate escape, nesting deeper than 512 levels, an integer outside the reader's 64-bit field); and quirks of the Python validator, which lets through what the specifications refuse (`$` matching before a final line feed, a lenient `uuid` check, NaN and Infinity). The rule is checked, not proven: reviews R2-04, R3-01 and R4-01 each found it broken for a class of input no check had tried, the last a canonically equivalent `group_id`, and an earlier revision of this record stated it as a fact. A differential check gives 363 named edge inputs, 3,000 seeded random mutations (including canonical twins of identifiers) and the instants of 42 date-times to the schemas and to the readers on every CI run, and fails on any other outcome; a sensitivity check builds the readers with nine deliberate defects and the differential check catches each, while its round 2 and round 3 versions each passed against the defect their review found (report F16). Against the round 1 readers the first version of the check found 45 disagreements.
- Limits (plan 8.3, configurable): 10,000 entries including the two manifest entries; manifest 16 MiB; central directory 24 MiB; per file 20 GiB audio, 2 GiB PDF, 1 GiB EPUB, 256 MiB text, 32 MiB cover; 500 audio members per group; deflate ratio at most 100:1 for each entry above 1 MiB, and for all deflated entries together at most 100 times their compressed bytes plus 16 MiB; total 200 GiB. The manifest limit was 1 MiB until review R4-02, which held at most 5,636 files even with 4-byte paths and every other field as short as the schema allows, so the entry limit could not be reached; the writer's manifest for 9,998 files with every path at 512 bytes, in 20 audiobook groups with their metadata at its limits, is 9,356,558 bytes, and a 10,000-entry pack of that shape validates (report F19). The aggregate rule closes a bypass found in review: 2,000 deflated entries of 1 MiB of zeros each (a 2.7 MB pack declaring 2 GiB) passed the per-entry rule, which never looks at entries of 1 MiB or less. With it, what extraction can write is bounded by the stored bytes, 100 times the deflated bytes and 16 MiB, and each entry is stopped at its declared size.
- Free space (plan 8.4): before extracting, the reader requires the declared total size plus a 64 MiB margin on the destination volume (`volumeAvailableCapacityForImportantUsage` on iOS) and otherwise refuses with `insufficient_space`, naming the additional bytes needed; nothing is written. An unknown capacity does not block extraction; a write that runs out of space fails and removes everything.

**Validation order** (`PackReader`), each step bounded before the next reads more: open with `O_NOFOLLOW` and require a regular file; strict structure parse with bounded `pread`s (`PackStructure`: end record at the end, entry count and central-directory size limits before reading it, each local header's name bytes, flags, method, CRC-32 and sizes equal to its central-directory record, exact back-to-back layout); names and paths; manifest digest, decoding and semantic rules; entry list equals the manifest (no extra, missing, reordered or size-mismatched entry; storage rules, per-entry and aggregate expansion); the archive library must report the same entries; when extracting, free space; then each entry is streamed through SHA-256 and CRC-32 with a fixed buffer, stopping at the first byte beyond its declared size. **Extraction** happens in the same pass into a new private directory (each target checked to lie inside it, directories created one level at a time without following links, files `O_EXCL|O_NOFOLLOW` 0600, each synced) and the directory is removed on any failure. A truncated or partial bundle fails at the first step in constant time.

**Writer** (`PackWriter`, Mac companion): pass 1 hashes every source and builds the manifest; pass 2 streams the sources into a temporary `.partial-<uuid>` archive, hashing again (a source that changed is an error); full sync; self-validation with `PackReader`; then `renamex_np(RENAME_EXCL)` to the final name. Text and Markdown are deflated; if the self-validation refuses the deflated pack for expansion (text so repetitive that it exceeds the limits above), the writer writes it again with every entry stored, which the reader accepts. The same inputs always take the same path, so output stays deterministic. The writer refuses a manifest over the reader's limit before writing anything. It reaches the entry limit: 9,998 files with 512-byte paths were written and self-validated in 5.3 s on the build Mac (report F19). Its time grows faster than the number of entries, because ZIPFoundation's `addEntry` reads and rewrites the whole central directory for every entry; the product writer (M6) should write the central directory once.

### 3. Archive library

Use **Readium's fork, `readium/ZIPFoundation` 3.0.1 (module `ReadiumZIPFoundation`, MIT)**, pinned `exact: "3.0.1"`, for both `.sylviapack` and the later `.sylviabackup`, always behind Sylvia's own strict structure check. Upstream `weichsel/ZIPFoundation` 0.9.20 is not used in the product.

Reasons: (1) Readium 3.11.0 (ADR-0002) already depends on `readium/ZIPFoundation` `from: "3.0.1"`, which resolves to 3.0.1 at revision `adb49c8b`, the same revision IntakeKit locks; (2) SwiftPM derives the identity `zipfoundation` from both URLs, so upstream 0.9.20 cannot join the app's graph at all (the resolver refuses it); (3) on the evaluated behaviour the two are equivalent: both wrote and read a 4.5 GiB ZIP64 archive correctly, cross-checked by Python `zipfile` and Info-ZIP, with a peak footprint of at most 5.9 MiB; (4) neither library is safe against partial copies on its own (`zip-eval.log`, clean run 2026-10-13T07:40Z; timings indicative, taken while other jobs shared the Mac): on copies of the 4.5 GiB archive cut by 1, 22 or 98 bytes or cut in half, upstream scanned for 45-78 s (50-72 s in the round 3 run, 48-72 s in round 2, 43-75 s in round 1) and then opened each one without error as an archive with no entries (a false acceptance: for the 22-byte, 98-byte and half cuts the payload happened to contain the end-record signature, and for the 1-byte cut it used the incomplete real end record), and the fork did not finish within the 120 s watchdog on any of the four; on a 64 MiB archive both rejected the same cuts, upstream in 1.0-2.5 s and the fork in 42-99 s; both rejected a 4096-byte stub at once. Python `zipfile` rejected every cut. Sylvia therefore never hands a file to the library before `PackStructure` has proved its layout, which rejects every evaluated partial copy in constant time (the host truncation sweep's slowest rejection is in `host-large-pack.log`). The fork's slow backward scan matters only for files that are not valid packs, which never reach it.

### 4. Fallback when the share cannot finish

The extension shows "Not received. Nothing was saved to Sylvia." with the reason and numbered steps (`FallbackRoute`); it never says received. For a provider that cannot supply a durable file (only a link, a temporary preview, an error, nothing within 60 s of no progress) the route is:

1. **Save to Files, then import in Sylvia:** in the source app choose Save to Files (or Export / Open in) to On My iPhone or iCloud Drive; open Sylvia, Import, Files, pick the file; if it shows a cloud icon, wait for the download.
2. **Send it from the Mac:** add it in Sylvia for Mac, then send it over the local network, or Prepare for cable transfer and copy the bundle with Finder (Files, Sylvia); then import from Sylvia's inbox.

When the provider offers a folder (an unpacked EPUB) only the Mac route is offered: whether Sylvia's own Files import accepts EPUB folders is an open product decision (Readium can open unpacked EPUBs; G0.1). *(Decided by the product owner on 22 October 2026, PO-16 (c): in V1 an EPUB stored as a folder is refused on every route, the message asking for a single `.epub` file, unless M6 has room for the Mac companion to pack folders into `.epub` files (option (b)); never accepted as a folder on the phone (option (a)), because the EPUB checks are built for archives. So the fallback offers the Mac route for a folder only if M6 builds that packing; the spike's fallback predates the decision.)* When space is short the Mac route is offered first and the shortfall is named. When the file exceeds the per-item limit no route is offered and the message says so: the same limit applies on every route, so suggesting one would promise an import that cannot succeed. When the shared files' names are too long to record in one share (section 1, the manifest's 256 KiB limit) the message says so and both routes are offered. The strings are Stage 0 copy; the product moves them into the design package's status vocabulary (plan 4.4.6 has no share-extension entries yet). Cancel, in any phase, leads to the same screen with "The copy was cancelled." (section 1).

Step 1's "Import, Files" is the document picker opened in place (section 1, Other routes): in the harness, **Import from Files**, exercised on the simulator (report T08); picking an iCloud file that has not downloaded yet is device checklist step 32.

### 5. Container layout

- `UIFileSharingEnabled` = YES: Documents is Finder's inbound drop area and holds nothing else.
- `LSSupportsOpeningDocumentsInPlace` = NO, declared explicitly: Sylvia always copies into managed storage (I-08) and never edits a user's document in place. Consequences: the Documents folder is not browsable in the Files app (only in Finder's file-sharing pane), and open-in and AirDrop copies arrive in `Documents/Inbox`. Space: the system's Inbox copy is one extra copy of the file while the import runs; Sylvia's own snapshot of it is an APFS clone (`fclonefileat`, hashed after cloning), which takes no further space, and the Inbox copy is removed when the import ends, whether it succeeded or not (the sender keeps the original). Peak use for an open-in of N bytes is therefore N for the system copy, not 2N; across volumes, where no clone is possible, Sylvia streams a copy and needs N more. A copy left in the Inbox by a crash is listed in the drop area as `Inbox/<name>` so the user can import or remove it. On the simulator, opening a file through the system's own document handling (`simctl openurl`) delivered a `Documents/Inbox` copy to the app, which imported it (a bundle through the bundle importer, an EPUB through the single-file importer, the same EPUB again as `needs_review`), rejected a truncated bundle, and left nothing in Documents (`sim-open-in.log`). **Cost found in review round 1:** with this key NO, the iOS 26.5 simulator's Files app lists no app under "Open With" for an EPUB ("No Apps Available"); with the key YES, and nothing else changed, it lists Sylvia and the open-in imports (`simulator-open-with-in-place-experiment.log`). The share sheet route from Files works either way. The value stays NO in the spike until the product owner weighs this (open items); with YES, open-in hands over the original file, which the importer already reads only inside a coordinated, security-scoped read and never writes. *(Decided by the product owner on 22 October 2026, PO-15: NO until G0.3 device step 13; YES if a phone also leaves Sylvia out of "Open With". Step 13 is pending.)*
- An APFS clone copies its source's attributes (clonefile(2)), so a staged clone may keep the source's data-protection class rather than its staging directory's. The in-app layout test records the class a clone gets when the two differ; the device result decides whether the importer must set the class on each clone (device checklist step 24).
- A `.sylviapack` opened in Sylvia (open-in or AirDrop; the app declares itself the type's owner) goes through the bundle importer, the same path as a Finder copy.
- `Library/Application Support/Sylvia/`: `Database/` (SQLite with WAL and SHM), `Knowledge/Notes`, `Knowledge/Retained`, `Media/` (committed originals), and `Staging/` (`journal.json`, `Staged/`, `Rejected/`, `Abandoned/`, `Extracting/`). Staging and the App Group handoff inbox are excluded from device backup: they are staging class (plan 17.1), and their bytes are either still held by their source or about to be committed. Database, knowledge and media are backup-eligible (plan 17.5). The layout audit checks both exclusions. Private directories get `completeUntilFirstUserAuthentication` protection so authorized background work can run after first unlock (plan 18.1); new files inherit it.
- The handoff inbox lives in the App Group container, never in Documents.
- Import from Documents is user-initiated. The app takes an APFS clone of the bundle inside a coordinated read and validates the clone. It cannot know whether an external writer (Finder's file-sharing copy) has finished: that copy is made by the system and gives no file-coordination signal the app can wait for, and an unchanged size or date proves nothing (plan 8.5). What it can prove is whether the bytes it has form a complete, valid pack; a copy still in progress fails validation (the end record is not yet at the end of the file) and the user is told to wait for Finder and retry.
- Inbound bundles in Documents are transport copies, not the library. Once a bundle's job is durably staged (or flagged `needs_review` as a duplicate, whose bytes are staged too), the app removes the bundle from Documents inside a coordinated delete, and only if it is still the file that was validated (device, inode, size and modification time unchanged; Finder may have copied a new file over it meanwhile, which is then kept). This is the cleanup plan 16.4 allows "after successful import", and it means a multi-GiB transport copy is neither kept nor backed up. A rejected or partial bundle stays, backup-eligible like anything the user puts in Documents, until the user removes it in Sylvia or in Finder.
- A raw supported file in Documents (plan 8.5) is imported only when the user taps Import, through the single-file importer (section 1), and it stays in Documents afterwards: without a manifest, an unchanged identity right after the snapshot cannot rule out a copy that is still running, and removing that file would lose the rest of it. The staged APFS clone shares its blocks, so keeping the file costs no space on the device until either copy changes; the file in Documents stays backup-eligible (the staged clone, in Staging, is not). Whether the product offers removal after a raw import is an open item. *(Decided by the product owner on 22 October 2026, PO-37 (c): it is not offered; the file stays in Documents, backup-eligible, until the user removes it, since removing it could cut off a copy still running.)*

## Consequences

- The extension's only job is a durable copy; catalog work stays in the app (plan 6.1). An extension that dies after the commit rename but before showing "Received" leaves a complete handoff that the app imports, so the user may see no confirmation for something that arrives; a retry then lands in `needs_review` as a duplicate rather than as a second book.
- If the final directory sync fails after the rename, the extension discards the handoff and reports failure; a scanner running at that exact moment (possible only when the app is in the foreground at the same time, for example on iPad) could import it. The user is then told "not received" for an item that arrives: the safe direction for I-03. If the discard instead overlaps the scanner's verification, the post-move re-check turns the job into `failed_final` rather than staging a partial handoff. Recorded for the product's iPad review.
- The bundle format is deliberately narrower than ZIP: only Sylvia's writer is expected to produce it. Archives made by other tools (with data descriptors, directory entries or comments) are refused.
- A Finder copy cannot be resumed; a partial copy is refused and the user copies again (plan 8.5 wording kept).
- A raw file copied with Finder can be staged incomplete when its copy paused or stopped (report F15). Staged is not ready (plan 8.2), so each type's validation has to catch a cut file before `ready`; for audio that may not be possible, since a file cut short can still play. Large transfers should use `.sylviapack`. The product owner kept the raw import on 22 October 2026 (PO-37 (a)), accepting this as a residual exception to I-04 for raw audio copied with Finder; the steering to `.sylviapack` is advice, not enforced, and accepting only `.sylviapack` from Finder above a size (option (b)) is revisited if G0.3 device steps 28-30 show a real Finder copy pausing or stopping unseen.
- `.sylviabackup` (ADR-0012) inherits the library choice and should reuse `PackStructure`'s strict layout check.
- Path and file-name rules work on UTF-8 bytes or code points, never on Swift `Character`s (report F18). Swift's `String` compares and searches by grapheme cluster, so `split(separator: "/")`, `hasPrefix`, `contains` and `==` miss a "/" that a combining mark follows. The product's importer, the Mac companion's writer, `.sylviabackup` and any code that builds a path from untrusted text must follow `PathBytes.swift`; the two schemas' descriptions say the same for other platforms.
- The manifest readers check the text before decoding (`StrictJSON.swift`) and do not rely on JSONDecoder to refuse what the contract refuses (report F16). The product keeps that layer, or an equivalent, for every contract it reads from outside the app.
- Swift's `String` equality, hashing and `init(rawValue:)` are canonical equivalence, and so is JSONDecoder's matching of member names and `String` enum values (report F16, review R4-01). Code that compares, hashes or looks up text from outside the app (identifiers, names, enum values) compares bytes, or first proves the text ASCII with the contract's pattern, as `PathBytes.equal` and `decodeExactCase` do. The contracts' own member names, enum values and constants hold none of the three ASCII characters a non-ASCII code point is canonically equivalent to (";", "`", "K"); a test fails if one ever does.
- Dates from outside the app are converted with proleptic Gregorian arithmetic, not Foundation's Gregorian `Calendar`, which is Julian before 1582-10-15 (review R4-03).
- The handoff journal is a JSON file in the spike; the product keeps it in the GRDB database with the same intent sequence (ADR-0003).
- Re-check on each Readium upgrade: the fork's version requirement and whether upstream and fork can coexist. The CI drop-in's dependency probe fails if either fact changes.
- Required-reason APIs (plan 18.2). The design depends on two Apple required-reason API categories, which the product's privacy manifests (app and share extension, `PrivacyInfo.xcprivacy`) must declare:
  - Disk space (`NSPrivacyAccessedAPICategoryDiskSpace`): `volumeAvailableCapacityForImportantUsageKey` in the extension's space check and in bundle extraction. Reasons: E174.1 (check whether there is space to write files) and 85F4.1 (the fallback and import errors show the additional space needed).
  - File timestamp (`NSPrivacyAccessedAPICategoryFileTimestamp`): `stat`/`fstat`/`lstat` modification times for the source-unchanged check while copying a shared or picked file (reason 3B52.1, files the user granted access to), and for abandoned-handoff staleness, the drop-area listing, the bundle identity check and the raw-file re-check (reason C617.1, files inside the app or App Group container). Readium's ZIPFoundation 3.0.1 ships its own privacy manifest declaring file timestamps with 3B52.1.
  - Not used by the intake code: user defaults (only the Stage 0 harness reads UI-test launch arguments through them), system boot time and active keyboards. Stall timing uses Swift's `ContinuousClock`; confirm with Xcode's privacy report on the first archived build that it needs no declaration.

## Alternatives considered

- **Upstream `weichsel/ZIPFoundation` 0.9.20.** Same ZIP64 behaviour, but it cannot be resolved in the same SwiftPM graph as Readium 3.11.0 (identical package identity), and on its own it opened truncated multi-GiB copies without error (as empty archives). Using it would mean vendoring or renaming a dependency, which ADR-0002 rules out without cause.
- **Relying on the library's own end-record search.** Rejected: on truncated 4.5 GiB copies, upstream scanned for 45-78 s and then accepted them falsely (50-72 s in round 3, 48-72 s in round 2, 43-75 s in round 1), and the fork did not finish within 120 s (`zip-eval.log`).
- **A custom container instead of ZIP.** Rejected: ZIP64 is inspectable with standard tools (Finder, `unzip`, Python), which helps support and recovery (I-09).
- **Extension writes straight into the catalog or the database.** Rejected by plan 6.1; it would also need the database in the shared container.
- **Manifest first, items after.** Rejected: a manifest that exists before its bytes cannot distinguish complete from partial.
- **`LSSupportsOpeningDocumentsInPlace` = YES.** Would expose Documents in the Files app and declares in-place editing, which Sylvia never does; it adds nothing for the cable flow, which uses Finder. It would save the system's Inbox copy on open-in, but with the APFS clone that copy is the only extra space an open-in costs, and it is removed when the import ends. Not rejected outright: on the simulator it is what makes the Files app list Sylvia under "Open With" (section 5), so it is an open item for the product owner rather than a settled alternative. *(22 October 2026: the product owner's decision PO-15 keeps NO and switches to YES only if a phone also leaves Sylvia out of "Open With", G0.3 device step 13.)*
- **Keep imported bundles in Documents until the user removes them.** Rejected: a 4.5 GiB transport copy would stay, be backed up, and duplicate what Sylvia already holds; plan 16.4 allows cleanup after a successful import.
- **A time-based "copy finished" heuristic for Finder drops.** Rejected by plan 8.5: unchanged size proves nothing; validation of a complete pack does. The raw-file re-check (section 1) is not such a heuristic: it refuses a file it saw change and claims nothing about one it did not.
