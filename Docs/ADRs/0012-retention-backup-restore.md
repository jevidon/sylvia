## Context

Section 17 asks for a versioned `.sylviabackup` with a manifest, a consistent database snapshot, portable exports, canonical cover thumbnails, retained excerpt audio and digests. Exports must hold retention leases so cleanup cannot remove blobs mid-export. Restore must go into a temporary library, validate paths, digests and schema, check foreign keys and counts, and replace the active library only with confirmation, keeping a recovery copy. Newer, truncated, corrupt or malicious backups must be rejected without touching existing data; Section 18.1 treats archives as untrusted input. Section 18.1 also asks for a deliberate data-protection class applied to the database, WAL, SHM, staging, excerpts and manifests. The single-file container is shared with intake work: the G0.3 workstream chooses the archive implementation in ADR-0010. Persistence rules are in ADR-0003. Evidence: `Docs/Stage0/G05-Recovery.md`.

## Decision

**Retention classes (plan 17.1).** Permanent knowledge (ledger, ratings, recommendations, captures and anchors, notes and revisions, saved AI conversations with their context packs and evidence, retained excerpt audio) is kept until explicitly deleted and is always in a knowledge backup. Each edition's canonical cover thumbnail is kept with it and is always in a backup; other thumbnails are rebuildable cache. Original media is user-managed: removing it changes availability only (ADR-0003) and never touches cover thumbnails. Staging and recovery copies are local safety nets and are excluded from device backup (`isExcludedFromBackup` on `Staging/`, `Staging/Persistence/`, `Recovery/`, `RestoreWork/`); the library itself stays backup-eligible. `Recovery/` follows the retention rule in ADR-0003: at most one pre-migration snapshot (reused by retries from the same pre-state) and one `failed-<id>/` copy, pruned automatically; `pre-restore-<id>/` copies hold the library a confirmed restore replaced and are kept until the user removes them, so the product must list them with their size and a remove action (for V1 the product owner's decision PO-40 (a) of 22 October 2026; an age-based expiry is revisited with the M7 retention controls). Abandoned `RestoreWork/` preparations are deleted at launch, and so is everything in the persistence layer's own `Staging/Persistence/` except a pending put-back's staged and partial copies: every file there is a temporary copy its operation renames into place or removes, so one found at launch was abandoned by a crash or an error (ADR-0003 "Retention of `Recovery/` and `Staging/Persistence/`"). The rest of `Staging/` is intake's (ADR-0010): its import journal and jobs, some the only copy of an item already reported as received, are finished, expired or removed by intake's own journal and rules (plan 8.2, 17.1), never by this cleanup; review round 4 found that the first version of the rule emptied all of `Staging/`. Secrets are Keychain-only and have no column in the schema. Trash rows are exported with their `trashed_at_ms` so they stay identified as trash.

**Retained excerpts, cover thumbnails and leases.** Excerpt audio is content-addressed under `Library/Blobs/excerpts/<sha256>.<ext>`; cover thumbnails under `Library/Blobs/covers/<sha256>.<jpg|png|heic>`, referenced by `edition.cover_thumbnail_sha256` and `cover_thumbnail_extension` (migration `v2-edition-cover-thumbnail`). Creating, deleting, leasing and garbage-collecting blobs all happen inside the single database writer, so "referenced or leased?" and "delete the file" can never interleave with a lease or with the insert that references a new blob. A blob file is flushed before the row that references it commits. Cleanup removes an excerpt blob only if no RetainedExcerpt references it and no unexpired `retention_lease` holds it. The spike never deletes cover blobs (a replaced cover leaves its old blob), so no lease is needed for them yet; a product cleanup of covers must take the same leases.

**Backup bundle (format v1).** A directory bundle `Name.sylviabackup/`:

```text
manifest.json                         urn:sylvia:schema:backup-manifest:v1
database/library.sqlite               consistent snapshot (rollback-journal mode, single file)
export/library.json                   portable JSON: every knowledge table plus asset locations, typed values, units stated
export/markdown/<slug>-<id8>.md       one file per work: quotes (exact text as block quotes), audio moments, current notes, conversations with
                                      evidence (the work's own and those started from one of its captures)
export/markdown/conversations-without-a-work.md   conversations linked to neither a work nor a capture (only when there are any)
blobs/excerpts/<sha256>.<ext>         retained excerpt audio (role retained_excerpt)
blobs/covers/<sha256>.<jpg|png|heic>  canonical cover thumbnails (role cover_thumbnail)
```

The manifest records the manifest and library schema versions and the applied migration identifiers, row counts for every table, included and excluded classes, every excluded original asset (ID, digest, size, type), `complete` (true exactly when `excluded_media` is empty), `encryption: "none"`, creation time (UTC), the originating installation ID, the snapshot boundary (highest ChangeJournal sequence) and the role, size and SHA-256 of every file. It contains no credentials, tokens, absolute paths or titles outside the exports. Format v1 never includes original media, so `excluded_media` lists every asset of the snapshot and `complete` is false whenever the library has any asset.

**Export procedure.** (1) Lease every referenced excerpt blob. (2) Take the database snapshot with SQLite's online backup API through GRDB (`DatabasePool.backup`, one read transaction), so writers keep running and the snapshot has one boundary. (3) Lease any blob the snapshot references that step 1 missed, failing the export if it is already gone. (4) Copy excerpt and cover blobs, each into a new file created with the protection class, and verify each copy's digest. (5) Write JSON and Markdown from the snapshot, never from the live database. (6) Write the manifest. (7) Validate the staged bundle with the same validator a restore uses. (8) Rename the staging directory, created beside the destination, into place, so the bundle appears complete or not at all. (9) Release leases and record an ExportRecord. On any failure the staging directory is removed and leases are released.

**Container layer.** `BackupContainer` (`finalize`, `open`) isolates the outer container. Stage 0 implements `DirectoryBundleContainer` only. The single-file `.sylviabackup` will use the archive implementation ADR-0010 (G0.3; Proposed, approved once Session 10's review of it is recorded, decision D-6; its archive choice decided by the product owner on 22 October 2026 with D02 and D10, its security review pending) chooses for both `.sylviapack` and `.sylviabackup`: `readium/ZIPFoundation` 3.0.1, always behind Sylvia's strict structure check (`PackStructure`). Its `open` must unpack into a restore work directory with the same path rules and present the same tree to `BackupValidator`. A shared or AirDropped single file is not supported until M1 builds that container (Open items), and M1 builds it only once ADR-0010 is approved. (Until 22 October 2026 that sentence read "Until ADR-0010 is accepted, a shared or AirDropped single file is not supported." The ADR workstream then recorded ADR-0010 as accepted that day, a reading of decision D-6 the assembly of the decisions round did not keep, and this paragraph kept that reading until the review of the assembly found it, its findings FID-02 and HON-1: ADR-0010 is Proposed.)

**Restore procedure (replace with confirmation).** The bundle, including its database, is untrusted input.

1. Validate the manifest without touching other files (`BackupValidator.validateManifest`): at most 4 MiB, `format` and `schema_version` checked first, then every rule of the `backup-manifest.v1` contract (enums for storage classes, roles and snapshot method, identifier and path patterns, unique migrations, `complete` exactly when `excluded_media` is empty) and this build's limits (known migrations and tables). Every path must be relative ASCII with no `.`, `..`, empty or backslash components, must match its role's exact location, and must be unique ignoring case; exactly one database is required.
2. Validate the files: each must be a regular file reached without any symbolic link, with the listed size and SHA-256. No unlisted files are allowed (`.DS_Store` excepted), and a directory that cannot be read fails the validation instead of ending the walk early.
3. Check free space for the copies plus a reserve.
4. Copy the database into `RestoreWork/<id>/Library`, opening the source without following links and creating the copy with the protection class, and verify the copy again.
5. Open the copy in SQLite's defensive mode with `trusted_schema=OFF` (both read back). Check `integrity_check`, refuse unknown migrations, require the migrations to match the manifest, and require the snapshot's `sqlite_schema` (every table, index, trigger and view, with its exact SQL) to equal the schema this build's own migrator produces for that migration list, built in memory. Any trigger, view, extra table, dropped index or altered table (for example without `STRICT` or a `CHECK`, or with a different foreign-key action) is rejected here, before anything could fire. Then check row counts against the manifest, `foreign_key_check`, the row values the schema does not constrain (`RowCheck`: every effective date must be a real date of its precision, written in ASCII digits only; every note's revisions must be numbered exactly 1 to its `current_revision`, because an edit inserts `current_revision + 1`; every INTEGER value in every library table must lie within ±(2^53 - 1), so the portable JSON export can always run and no counter the app increments, such as `note.current_revision`, `capture.revision`, `work.metadata_revision`, `edition_asset.timeline_revision` or the journal sequence, can overflow; `sqlite_sequence` must hold only the ChangeJournal's entry, equal to its highest sequence; and every TEXT value must be valid UTF-8 without a NUL character, because GRDB reads TEXT as a C string and the app would show, edit and export different text from what is stored, ADR-0003), and that `excluded_media` names exactly the snapshot's assets (ID, digest, size, type) with `complete` consistent (I-09). Row values are otherwise validated only by the schema's `STRICT` types and `CHECK` constraints, `foreign_key_check` and `integrity_check`; any further invariant the app relies on must be added to `RowCheck`.
6. Run supported migrations on the copy, then repeat the schema, integrity, foreign-key, row and count checks against the current schema.
7. Require the excerpt and cover files to be exactly the blobs the snapshot references (preserved excerpts; editions' cover thumbnails), and copy and verify them.
8. Mark every original as unavailable ("Record only", or "Not on this device · from {source}" when a source is known), drop leases from the source device, and journal the restore. Then repeat the schema, integrity, foreign-key and row checks and check every count again (the journal grows by exactly the rows written, leases are zero), so the library is verified as it will be swapped in.
9. With the user's confirmation only: close the active store, write `restore-intent.json`, rename `Library/` to `Recovery/pre-restore-<id>/Library`, rename the restored library into `Library/`, and remove the intent.

At the next launch, before anything creates `Library/`, an intent left by a crash is reconciled. If the restored library is in place, or can be moved in, the restore completes; if the active library was never moved, the restore is abandoned; if neither is present, the pre-restore copy is moved back. Abandoned preparations in `RestoreWork/` are deleted. An intent that exists but cannot be read (for example before first unlock) or is not valid, including one whose paths do not have the fixed shape for its ID, is never acted on and never ignored: the open fails with nothing changed, so an empty `Library/` is never created over a pending swap and the prepared library is kept. A failed migration's put-back intent (ADR-0003) lives inside `Library/`, so a restore that replaces a library whose put-back is pending (for example from the recovery screen) moves that intent with the old library into its pre-restore copy, and the restored library opens normally. The installation ID is outside `Library/` and is never restored; an installation record that exists but cannot be read or decoded is likewise an open failure, never a new identity. Provider keys and pairing are re-entered.

**Data protection (plan 18.1).** Class C, `completeUntilFirstUserAuthentication`, for every persistent file: the library directory tree, database, WAL and SHM, staging, recovery copies, retained excerpts, cover thumbnails, media, installation file, export bundles and restore work. Approved by the product owner on 22 October 2026 (D17); the security reviewer's approval of the class and its locked-device trade-off, and the class a phone reads back (device checklist steps 1, 3 and 4), are pending. *(26 October 2026: in the product owner's run of step 1 on phone B, on 25 October 2026 UTC, through `DeviceTests`, class C and class B read back on all 53 files and directories, and class B on the files SQLite created in a class-B directory, within a run that failed elsewhere (migration and put-back tests, and a backup rejection's error classification), as the owner recorded it (`Docs/Stage0/evidence/G05-Recovery/device/step-1-hosted-results.md`); steps 3 and 4, and the security reviewer's approval, are pending. Agent-written, from the owner's records.)* Authorized background playback and transfers after first unlock must read media and write the database while the phone is locked, which rules out class A (`complete`) for the library. The trade-off is that these files are readable while the device is locked once it has been unlocked since boot. They are not readable before first unlock, when the app must show a safe unavailable state and never lower the class. How the class is applied:

- Class C is also the default class for new files on macOS and for app files on iOS. A class-C readback therefore cannot, by itself, show that the code applied anything. The discriminating evidence is the same flow run with class B supplied through `StoreOptions.protector`, where every created item must read back class B. That run needs class-B keys, so on the host it skips while the screen is locked; the CI drop-in fails a run whose log lacks its evidence line (unless `G05_ALLOW_MISSING_CLASS_B=1`).
- GRDB does not expose SQLite's `SQLITE_OPEN_FILEPROTECTION_*` open flags. Every directory is therefore created with the class, so files SQLite creates inside it inherit it. This was shown on the host with a class-B control directory: database, WAL and SHM came out class B.
- Sylvia then sets and reads back the class explicitly on the database, WAL and SHM on every open.
- Files Sylvia writes use the matching `Data.WritingOptions` and are read back. Files Sylvia copies (imported media, bundle blobs, restore copies, a snapshot put back after a failed migration) are created new with the class by `FileProtector.copyFile` and read back. `FileManager.copyItem` is not used for them: it keeps the source file's class, and on macOS an existing file's class cannot be changed afterwards (`setAttributes` leaves it unchanged, which the readback catches).
- A mismatch is an error, never a fallback.
- Only classes A, B and C are accepted. Any other class (the newer `completeWhenUserInactive`, a value the protector does not know, or `FileProtectionType.none`) is refused before anything is written, copied, created or changed: on the write and copy paths since M0 assembly (ADR-0015, finding TM-F1), and on the directory path and the class set on existing files since the M0 final fix (final review SEC-06). `DataProtectionTests.unsupportedClassRefused` covers all four paths for those three classes (`Docs/Stage0/integration-log.md` section 11).
- Class A is not usable for the library even if wanted: in a class-A directory, Apple's SQLite creates the `-shm` file with class C (host observation), so the readback fails the open.
- The iOS Simulator's readback is not faithful: directories report none, and files report class C whatever was requested. In simulator builds only, an item reporting no class is accepted; device builds require the readback to match. The class-B run is therefore host and device only.
- On the macOS host the classes are enforced while the screen is locked: class-A files cannot be created and closed class-B files cannot be reopened, while the class-C library keeps saving (`DataProtectionTests.lockedHostEnforcement`, which runs only when the host is locked; it ran in the review-round-2 clean run, `git show 2a37a00:Docs/Stage0/evidence/G05-Recovery/logs/host-tests.log`). This is host behaviour; the iPhone's is the device checklist.

**Encryption.** Version 1 backups are unencrypted, as plan 17.3 proposes. The UI must show the privacy warning and let the user choose the destination; no custom encryption. Approved by the product owner on 22 October 2026 for internal and TestFlight use (D10, PO-22 (a)), to be revisited at the public-release gate (plan 18.4); anyone who has an exported file can read it, so the warning and the destination the user chooses are its protection. The security reviewer's acceptance of this residual risk (ADR-0015 B8) is pending.

## Consequences

- Restoring always replaces the library; merging two libraries is out of scope (plan 17.4).
- Original media must be re-added or re-downloaded after a restore; the manifest lists exactly which assets are missing, and restore refuses a manifest whose list does not match the snapshot.
- Export leases expire (one hour in the spike) so a crashed export cannot pin blobs forever. The product exporter must renew its leases while it runs, or an export slower than the lease (many excerpts to a slow destination) could lose a blob the user deleted mid-export. The spike does not renew; no spike export came near the limit.
- Any later change to a path rule or role is a manifest v2 (Contracts/README.md versioning). Canonical cover thumbnails are part of v1 (role `cover_thumbnail`, class `canonical_cover_thumbnail`), so plan 17.3's contents need no v2.
- Restore compares the snapshot's schema SQL exactly with the schema this build's migrator produces. Both come from the same migration code and the same SQLite, so a legitimate backup matches; a future SQLite that rewrote `ALTER TABLE` output differently would make older backups fail this check (a refusal, never a wrong restore). Re-check on every SQLite or GRDB upgrade by restoring the committed v1 fixture and a current backup (`RestoreTests.referenceSchemaMatchesLibraries`, `restoreOlderBackup`). The spike never runs `ANALYZE` or `PRAGMA optimize`; if the product does, the `sqlite_stat*` tables they create are not in the reference and must be handled explicitly (for example dropped from the copy before the comparison, never trusted), or every such backup would be refused.
- Restore depends on a small C shim (`Sources/SylviaSQLiteShim`) for `sqlite3_db_config`, which Swift cannot call (variadic). It is spike code and links the system SQLite GRDB already uses; it is not a new dependency.
- The JSON export writes integers as JSON numbers and refuses values of 2^53 or more, so JavaScript readers stay exact. 64-bit sizes up to 8 PiB fit.
- An exported bundle on an unprotected destination is no longer covered by device protection; the UI must say so.
- Re-check when ADR-0010 lands: the archive reader must enforce the same path, link, size and digest rules, plus entry-count and expansion limits, before `BackupValidator` runs.

## Alternatives considered

- **Copy the SQLite file and WAL directly.** Unsafe while the database is open (plan 7.4); the online backup API gives one consistent boundary without stopping writers.
- **Export JSON only, no database.** Loses exact types and constraints for restore and needs a separate importer for every table. The database snapshot is authoritative and the JSON is the portable second copy, checked to hold identical values.
- **Trust the snapshot's schema once its migration list is known.** Rejected in review: a crafted database with matching digests could carry a trigger that deletes knowledge during restore, or tables without `STRICT` and `CHECK`. The schema itself is compared.
- **Rebuild the restored library from the portable JSON instead of the snapshot.** Removes the untrusted schema entirely, but needs an importer per table and per schema version. Revisit if the schema comparison proves brittle across SQLite versions.
- **Class A (`complete`) for the library.** Stronger at rest, but background playback and transfers could not touch the database or media while locked, and SQLite's SHM file does not take class A.
- **Class B (`completeUnlessOpen`) for the database.** SQLite opens, closes and reopens database, WAL and SHM files, and a closed class-B file cannot be reopened while locked (seen on the host). Not pursued.
- **Merge restore.** Rejected by the plan: it has no defined conflict semantics.
