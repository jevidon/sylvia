## Decision

### 1. The lock

1. **What it is.** The 15 committed `Package.resolved` files (13 when this record was written; G0.2 committed the copies for `MacIdentityProbe` and `iOS`, merged at M0 assembly), which pin 23 packages, together with `Docs/Licenses/inventory.json`. For each package the inventory records its URL, exact version, full revision, role (section 2), the locks that pin it, the manifests that require it directly and the targets that use it. One version and one revision per package across the repository.
2. **Exact requirements only.** `Package.swift`: `.package(url:, exact:)`. `project.yml`: `exactVersion:` (XcodeGen 2.46.0 also writes `version:` as exact; every other key gives a range, a branch or a revision, `xcodegen-requirements.log`). Python tools: `name==version`. Workflow actions: a commit, or a reasoned exemption recorded in the inventory (none since M0 assembly, which pinned both actions to their release commits). A branch, revision, range or `from:` requirement fails CI.
3. **A lock beside every manifest that reaches a remote package, and the lock covers its manifest.** A project whose only package is local still reaches that package's dependencies, and Xcode writes no lock for it: it commits a copy of the local package's lock, which `sylvia_generate` installs (as `Apps/DesignCatalog` does). Every package a manifest requires, directly or through its local packages, must be pinned in its lock; a lock that misses one is stale and fails CI. Exemptions are allowed only under `Spikes/` (CI rejects one anywhere else) and each states why. There is one since M0 assembly: G0.3's `IdentityProbe`, which cannot resolve by design. (G0.2's `MacIdentityProbe` and `iOS` projects were exempt until G0.2 committed their lock copies, merged at M0 assembly; the G0.2 drop-in checks that each copy equals its source lock.)
4. **Builds use the lock.** Xcode builds pass `-disableAutomaticPackageResolution` (ADR-0002). SwiftPM builds should pass `--force-resolved-versions`, so that a lock that no longer satisfies its manifest fails instead of being rewritten; since M0 assembly every `swift build`, `swift test` and `swift run` call in the drop-ins and the scripts in the repository does, `--show-bin-path` calls included, except the evidence commands under `Docs/Stage0/evidence/*/commands/`, which record how committed evidence was made, and G0.3's frozen copy of its round-2 check (`Spikes/G03-Intake/scripts/sensitivity/check-contract-instances-round2.sh`).
5. **Product code comes only from what git tracks under `Apps/` and `Packages/`.** Nothing a product manifest builds from may resolve outside them: no local package, non-test target source, build-settings (`.xcconfig`) file, referenced Xcode project, header or module-map search path, or symbolic link. Inside them, a shipping (non-test) target may name only content git tracks: never a build product, a package checkout (a package's own `.build/checkouts`) or a generated file, which the product rules cannot read. A path may start with a build-product, SDK or toolchain variable only if it stays in that directory (no `..`, and not Xcode's `SourcePackages` checkouts beside the build products); any other variable fails, because the check cannot evaluate it. A header or module map that a setting or flag names (a prefix or bridging header, `-include`, `MODULEMAP_FILE`, `-fmodule-map-file=`) must be such a tracked file, and is then read as product code whatever it is called. A shipping target passes only the compiler and linker flags the check allows (section 3), and sets none of the build settings that, by Xcode's specifications, replace the compiler, linker, SDK or toolchain or take their inputs from a file (the list in section 3). What a product target links comes from the SDKs, the product roots or the inventory's `binaries`. A reference into `Spikes/` from any product manifest, build-settings file or module map, test targets included, is always an error. Test targets may take fixtures, headers and flags from elsewhere, because they never ship. No Xcode project or workspace is committed anywhere (ADR-0002): the check does not read the package references inside one.

What the roles allow, under `Apps/` and `Packages/`:

Headers and module maps are product code wherever they sit, test directories included, because any product file can include or import them (review round 3).
- A manifest may require **product** and **test** packages directly; **test** packages only from test targets.
- **Product-transitive** packages are never required directly, and product code never reaches their modules: not by any import, include, module map or module alias (a `-module-alias` flag, the `SWIFT_MODULE_ALIASES` setting or a SwiftPM `moduleAliases:` entry), nor by a flag that imports or includes them into every file (`-import-module`, `-include`, a prefix or bridging header), nor by a definition or any other value of a shipping target's manifest or build settings that names one of their public headers (review round 3). - A non-test product target may use a package only on the platforms the inventory allows for it. So the swift-nio packages (macOS only) never enter an iOS target, a rule M6 inherits (ADR-0009). And it may not build a file from a directory named `Tests` or ending in `Tests`, at any depth: that name is kept for test code, so a reader is never misled by it.

Under `Spikes/` any inventoried package may be required, exactly.

### 3. CI enforcement

`Scripts/check-dependency-lock.py`, run by `Scripts/ci.d/12-dependency-lock.sh` (host only; no network, simulator or build). The drop-in, self-test included, took under a minute in each run of this round; `ci-12-dependency-lock.log` and `round3-reproductions.log` each record their run's time with the load averages beside it, and those timings are indicative only, since other agents were building on the Mac. It compares the repository with the inventory and prints one line per finding, `FAIL <category> <where>: <message>`. It fails when:
- **Locks and requirements:** a lock pin or an exact requirement differs from the inventory; a lock lacks a pin the inventory lists, or a package its manifest requires (directly or through a local package); a lock or manifest names a package not in the inventory; a Swift or Python requirement is not exact, or a workflow action is on a tag or branch without a recorded exemption; a committed lock is unregistered, or the inventory's lock, requirement or target-use lists are stale; a manifest that reaches remote packages has no lock and no exemption, an exemption names a manifest outside `Spikes/`, or an exemption is stale; or an Xcode project or workspace is committed anywhere, since the package references, requirements, settings and lock inside one would bypass every rule here (review round 3).
- **Product code (`Apps/`, `Packages/`):**
  - A product manifest requires, or a product lock pins, a spike-only package.
  - It reaches `Spikes/`, or code outside the product roots, by any route section 1 names: local packages, target sources, build-settings files and the files they include, referenced projects, header, library and framework search paths, compiler and linker flags, symbolic links, C-family includes, or module maps. Or, in a shipping target: a path names something under the product roots that git does not track (a build product, a package checkout under `.build`, a generated file), or a header or module map it takes is not a tracked file there; a path that starts with a build-product, SDK or toolchain variable leaves it or reaches Xcode's package checkouts; a path uses any other variable; or a build setting replaces the compiler, linker, SDK or toolchain or takes their inputs from a file (`CC`, `LD`, `LIBTOOL`, `SWIFT_EXEC`, `TOOLCHAINS`, an `SDKROOT` path, the alternate-linker settings, input file lists, header maps, response files, `LD_ENVIRONMENT`, prefix mappings; a SwiftPM system library's pkg-config). The setting lists come from Xcode 27.0's specifications (`xcode-settings.log`); Xcode 27.1's, the pin since 20 October 2026, give the same output line for line (`Docs/Stage0/evidence/M0-Integration/repin-27.1/xcode-settings-compare.log`).
  - A shipping target passes a compiler or linker flag that is not on the allowed list: `FLAGS_ALLOWED` and its patterns in the check (warnings, optimization, language mode and features, `-D` and `-U`, `-ObjC` and the like), with the search-path, header-file, module-map-file, library, framework and module-alias flags allowed and judged by the rules above. The check reads SwiftPM `unsafeFlags`, every build setting whose name contains `FLAGS` and XcodeGen per-file `compilerFlags`, with `-Xcc`, `-Xlinker`, `-Xfrontend`, `-Xclang` and `-Wl,` unwrapped; an input file among the flags fails too. So `-import-module`, `-imacros`, `-ivfsoverlay`, `-fplugin=`, `-load-plugin-library` and any flag nobody has reviewed fail without having to be listed (review round 3).
  - A product manifest requires a transitive-only package directly.
  - Product code reaches one of its modules. The check reads the raw text, not a lexer's view of it: in any Swift or C-family file, the word `import` followed (after white space, comments and an optional import kind) by the module's name, which covers every Swift import declaration however it is written, `@import`, `#pragma clang module import`, `_Pragma` and C++ `import`; in a C-family file, any mention of one of its public headers (so any `#include`, `#import`, computed include or `__has_include` of it), of a framework-style path into it (`<Zip/...>`) or of its Swift module's generated header (`Zip-Swift.h`), with line splices joined and trigraphs read both ways; a module map naming one of its public headers; or a `-module-alias` flag, the `SWIFT_MODULE_ALIASES` setting or a SwiftPM `moduleAliases:` entry for one of its modules. And, in a shipping target: a flag that imports one of its modules into every file (`-import-module`), a definition that names one of its modules, or any value of the manifest or of a build-settings file it uses (settings, flags, definitions, scripts) that names one of its public headers, which a prefix or bridging header, `-include` or a computed include could reach. No comment, string, regex literal, raw identifier or flag can therefore hide an import. The cost: a comment or string in product code, or a manifest value, that names such an import or header is reported too, and must be reworded.
  - A non-test product target uses a test-only package (XcodeGen target templates and build tool plugins included), takes its sources from a test-named directory or builds a file in one at any depth, or can build a package for a platform the inventory does not allow.
- **Binaries:** a product manifest's binary target, framework, bundle or Carthage dependency, a library or framework it links by name that no iOS or macOS SDK provides, or a committed Mach-O file or static library under the product roots, is not inventoried (`binaries`), or an inventoried one is stale or has another digest.
- **Licenses and assets:** a license text copy differs from the digest read at the pinned revision; a package's license data were recorded at another revision than it pins (so a version bump that does not re-read its license fails); a bundled component's text is missing; a font or license file under `Apps/` or `Packages/` is not inventoried or has changed.
- **Tools:**
  - `Scripts/tools/requirements.txt` or a workflow action differs from the inventory.
  - The Xcode pin in `Scripts/lib/env.sh` differs from it, or another record of the pin does: the Xcode guard of `.github/workflows/ci.yml` (the build of its `Build version` line, its candidate `Xcode_<version>.app` and any `Xcode <version> (<build>)` in its text, its comment lines not read; a workflow without such a guard line fails too), `CLAUDE.md`'s toolchain line or ADR-0001's toolchain table (since 20 October 2026, review TC-08: until then a re-pin that missed one of them passed every local check).
  - With `--toolchain`, as CI runs it: the installed Xcode build, Swift version or XcodeGen version differs, each compared whole on the line of the tool's output that states it, which the failure quotes (since 20 October 2026, review TC-02: the check searched the output for the pinned text, so a build that only extends the pin, `27A9275a` for `27A9275`, passed, and a failure quoted the output's first line, `Xcode 27.1`, rather than the build), or the tools virtualenv holds anything other than exactly the pinned packages at their versions and pip, which must be there at any version, or the check does not run in it.
- **Documents:** `third-party-inventory.md` or this ADR lacks a package's name and pinned version, or the acknowledgements draft differs from what the inventory generates.

It also **warns**, printing `WARN` without failing, when the virtualenv's pip is below 26.2.0, the first release outside every pip advisory found (GHSA-qwm4-qh6w-59xr, section 5). Nothing in the repository pins pip: `bootstrap.sh` makes the virtualenv with `python3 -m venv`, which installs the pip that Python bundles (26.1.2 with Python 3.14.6) and never upgrades it. A failure would therefore fail every freshly bootstrapped virtualenv whose Python bundles an older pip, as Python 3.14.6 does, on something no tracked file controls; the GitHub workflow's virtualenv is made the same way, from whatever Python the runner has. A virtualenv made that way passes the drop-in with this warning (`round2-reproductions.log`), and the reviewed version of the check failed it. Pinning pip in `requirements.txt` (requested, open items) makes pip an exact pin like the others; until then, whether CI should fail instead of warning is the security reviewer's call (section 7). The warning is not visible in a passing `Scripts/ci.sh` run: `ci.sh` prints a drop-in's log only when the drop-in fails, so its console shows "pass", and the warning is in `.build/ci-logs/12-dependency-lock.log` (where the check prints it last, before its summary line) and in the output of the check run directly (review R3-05, `round3-reproductions.log`). A one-line change to `ci.sh` that prints a passing drop-in's `WARN` lines is requested from its owner (open items); the same log shows it printing this warning on a copy of the tree.

Its **self-test** runs first, on a synthetic repository:
- 239 mutated copies, each of which must be reported with its own category and message (228 until 20 October 2026, when the review of the re-pin round added eleven for the toolchain rules above: a build, Swift version or XcodeGen version that only extends the pin, a version line missing, and each record of the pin changed or missing).
- 30 allowed changes, none of which may be reported, and none may warn except the three written to warn (a pip below the minimum, a pre-release of it, and a version it cannot compare). Among them: a test importing a transitive module; a single test target that takes all of `Tests/`, as SwiftPM 5.9 and later allows; a spike using a test package; a source file named `Notice.swift`; SDK libraries linked by name; a library linked only on Linux; build-settings files and module maps that stay inside the product roots; `import` as an argument label, member name or raw identifier; flags product targets may pass; a tracked prefix header, bridging header and module map; a test target passing any flag; a referenced project generated from a tracked `project.yml`.
- Mechanical coverage: every one of the check's 111 failure branches (109 until 20 October 2026) (each `self.fail(` call in the script) must be reached by the mutation written for it, and both warning branches (each `self.warn(` call) by the allowed change written for it. A branch that nothing reaches fails the self-test, so this claim cannot silently become untrue.

The toolchain branches run there against a fake toolchain; `check --toolchain` then checks the real one. `round1-reproductions.log`, `round2-reproductions.log` and `round3-reproductions.log` run the reviews' reproductions, and the further routes the fixes close, against copies of the committed tree; the second and third also show that each route compiles against a stand-in module, and that limits below stay unreported.

**What the check cannot see**, and so does not claim:
- Code reached by symbol rather than by import or include: an `extern` prototype, `dlsym` or `@_silgen_name` in product code that calls a function a transitive package links in, such as Minizip's.
- A header or module name the C preprocessor assembles by token pasting or stringizing, so that it never appears whole in the text (a computed `#include` or `_Pragma` whose argument a macro builds from pieces).
- Declarations reached through a module that re-exports them with `@_exported import`, which is use through the parent package: at the pinned revisions swift-nio's NIOFS and `_NIOFileSystem` re-export five SystemPackage types (FilePath, FileDescriptor, Errno, FilePermissions, CInterop), and no product package re-exports any other transitive-only module. Swift's member lookup also finds extension members declared in a module that is loaded only transitively, unless the MemberImportVisibility feature (SE-0444) is on; marmelroy/Zip declares no extension of another module's type (its one extension is of its own `Zip` class), so this reaches none of its functions.
- Paths that build scripts and scheme actions compute. A script naming `Spikes/` or a transitive-only package's public header is caught; other paths in scripts, and names a script assembles from pieces, are not judged (`round3-reproductions.log` shows one).
- Build settings outside the lists drawn from Xcode 27.0's specifications, which Xcode 27.1's match (`xcode-settings.log` prints every setting there that reaches the compiler or linker, with how the check reads it). The others are read only for a transitive-only package's header names and for paths into `Spikes/`.
- What the compiler and linker take from the environment rather than from a tracked file (`CPATH`, `C_INCLUDE_PATH`, `LIBRARY_PATH` and the like).
- The requirements of packages behind an exempted (unlocked) Spikes project.
- Anything a build fetches or runs that no tracked file names.
- How the workflow's Xcode guard compares the build: the check reads the build, the Xcode application and the version the guard names, not the shell around them, so a guard that searched its output instead of comparing the whole line (`grep -qx`) would pass it.

**License texts and the pinned revision.** CI ties each recorded digest to the pinned revision through `read_at`. The byte-level comparison with the files at that revision is done by the update procedure (`read-licenses.py` and `run-all.sh`, which compares every committed text with what it copies, extracts or fetches today). CI cannot repeat it, because a clean run has no package checkouts and the check uses no network.

### 6. Update procedure

To add, upgrade or remove a package (or a vendored asset, Python tool or workflow action), in **one commit**:

1. Record the reason and the role in the owning ADR (a new package needs the justification ADR-0002 asks for).
2. Change the exact requirement in every manifest that declares it.
3. Re-resolve every lock that pins the package, so it holds one version everywhere: `sylvia_resolve <dir>` for an Xcode project, `swift package resolve` for a package, and refresh any copied lock (`Apps/DesignCatalog`). Check that no other pin moved unintentionally.
4. Read the license at the new revision: `Docs/Stage0/evidence/M0-dependencies/commands/resolve-locks.sh`, then `read-licenses.py --copy Docs/Licenses/texts`. For a package that ships, also run `vendored-headers.py` (it fails on an origin note or vendored-code directory it has not been told about: match each to the inventory, then list it in the script), `copyright-lines.py` (and match every new holder to a notice), `font-names.py`, `privacy-manifests.py` and `extract-notices.py`. For Readium also run `readium-js-closure.py` with `fetch-npm-licenses.py`, and `readium-css-provenance.py` (where its stylesheets come from, and their license there); for a transitive-only package, `transitive-modules.py`. Record the new digests, `read_at`, modules, headers and embedded components in `inventory.json`.
5. Search advisories for the new version with `advisories-search.py` (OSV and the GitHub Advisory Database at the version, the repository's published advisories, NVD by name), and for the code it vendors with `vendored-advisories.py`, updating that script's versions, revisions and keywords when the vendored code changes. Each search fails on an advisory it has no verdict for: judge it against the pinned source as `advisories.md` does, and record the verdict in the script and in `advisories.md`.
6. If what links or bundles may have changed, run `linkage.sh`.
7. Update `inventory.json` (including `used_by_targets`: `check-dependency-lock.py used-by-targets` prints them from the manifests), `third-party-inventory.md` and the owning ADR's version, and regenerate the acknowledgements: `sylvia_python Scripts/check-dependency-lock.py acknowledgements --write`.
8. Run `Scripts/ci.sh dependency-lock`, `commands/run-all.sh` (which regenerates every log above and compares every committed text with the source), and the drop-ins of the gates that use the package. For Readium that is `31-g01-epub.sh`, which also re-checks the sanitizer and the archive identity probe of ADR-0010.

A toolchain change follows ADR-0001 and updates the inventory's `toolchain` and `SYLVIA_XCODE_BUILD_PINNED` together, and runs `xcode-settings.py` to see whether the new Xcode passes a setting to the compiler or linker that the check's setting lists should hold. Done once so far, on 20 October 2026, for the re-pin from Xcode 27.0 (27A266a) to 27.1 (27A9275), the product owner's decision of PO-35 as ADR-0001 records the reading of the owner's reply: the inventory's toolchain and host-tool rows, `Scripts/lib/env.sh`, the workflow's Xcode guard and `third-party-inventory.md` changed together; `xcode-settings.py` gave the same output as under 27.0, so the lists need nothing new; the drop-in, which had failed its toolchain line alone since Xcode updated itself on 18 October 2026, passes (`Docs/Stage0/evidence/M0-Integration/repin-27.1/`). `linkage.sh`, which step 6 above asks for when what links may have changed, was not run: it resolves packages, which can fetch from git remotes, which that change did not do; so section 4's account of what ships is Xcode 27.0's measurement until it is run under 27.1 (open items). Since the review of that change, the same day, the check also compares the workflow's guard, `CLAUDE.md`'s toolchain line and ADR-0001's table with the inventory (section 3), so a toolchain change that misses one of them fails.

A product target that needs a compiler or linker flag outside the allowed list gets it through a reviewed change to the check: add it to `FLAGS_ALLOWED` (or to `FLAGS_WITH_NAME`, with a rule for its argument) and a self-test case. A flag that brings a file, directory or module into the build is judged by the path and module rules instead, and never added to the list as a plain flag.

## Consequences

- Any dependency change now touches the inventory in the same commit, or CI fails. That friction is the point: nothing reaches a lock unrecorded.
- Every Readium upgrade must re-check what Readium bundles (fonts, scripts and their npm closure, vendored code), not only its version.
- The acknowledgements cannot drift from the inventory: CI regenerates and compares them.
- The check reads every `Package.swift` with `swift package dump-package`, so it needs Xcode. It reads only the files git tracks, so build products never affect it, and its number (12) runs it before the build drop-ins.
- Product code cannot share sources with spikes or anything else outside `Apps/` and `Packages/` (section 1). Code meant for both has to move into a package under `Packages/` and be checked as product code.
- Product code cannot keep a directory named like test code, and a comment or string in product code, or a value in a product manifest, that names `import Zip` or a Minizip header fails CI: the price of an import check that no lexer quirk can fool.
- A product target can pass only the compiler and linker flags the check knows; a new one is a reviewed change to the check with a self-test case (section 6). It cannot point a setting at an untracked directory under the product roots or use a variable the check cannot evaluate: generated files go under a build-product directory such as `$(DERIVED_FILE_DIR)`, and a prefix or bridging header or a module map must be a tracked file.
- Headers and module maps under `Apps/` and `Packages/` are product code wherever they sit, so a test helper header cannot name a transitive-only package's headers either.
- It cannot see transitive requirements that reach an exempted (unlocked) Spikes project; the exemptions say why each is acceptable and are flagged as stale when a lock appears.

## Alternatives considered

- **Keep the table in this ADR only** (the integration version). Rejected: nothing checked it, and it missed vendored code, fonts, scripts and notices.
- **Derive the inventory from the locks automatically.** Rejected: roles, obligations and decisions need review; CI compares the reviewed record with the repository instead.
- **An off-the-shelf license scanner or OSV-Scanner in CI.** Not installed; they would send the dependency list to a service on each run, and the license files here are read at the pinned revision anyway. The version-exact advisory search runs instead at each dependency change and milestone (section 5). Worth revisiting once the repository is hosted.
- **Vendoring package sources.** Rejected by ADR-0002; the lock and the revision digests give the same reproducibility.
- **Read imports with a lexer that skips comments and literals** (the third version). Rejected in review round 2: any construct it lexes differently from the compiler hides an import that compiles. Reading the raw text reports a few harmless mentions instead.
- **Enumerate the flags that bring code in** (the fourth version). Rejected in review round 3: compilers and linkers have more such flags (`-import-module`, `-include`, `-imacros`, `-ivfsoverlay`, `-fplugin=`, `-load-plugin-library` ...) than a list keeps up with, and each one missed is a route. The allowed list fails closed instead.
- **Fail CI on a pip below its advisory floor.** Not chosen while nothing pins pip: it would fail every fresh virtualenv on a version no tracked file sets. Pinning pip removes the question (section 7 item 9).
