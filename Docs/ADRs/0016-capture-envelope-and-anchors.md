## Decision

### 1. Two schemas, one rule set

- `anchor.v1` is a discriminated union on `kind`: `epub`, `pdf`, `text` (TXT and Markdown) and `audio`. `capture-envelope.v1` holds an ordered `anchors` array of it (by `$id`). The anchor is a schema of its own so that it can be validated, and kept by M1, on its own. It describes a selection, not a reading or listening position: an EPUB, PDF or text anchor needs the selected text and an audio range a length (rule A1), so the "current anchor" of plan 7.2's Progress needs a position form of its own (open items). The context-pack contract's evidence items do not use it either: they locate text by extracted-paragraph ordinals (`position`), and refer to a capture by its ID (section 9).
- Every anchor carries `schema_version` (1), `kind` and `work_id`; every known kind also carries `edition_id`, the asset ID or IDs, and the SHA-256 of the asset bytes it was taken from (`asset_sha256`). An anchor is exact only for those bytes; a different digest is a different asset, and cross-edition relocation always needs confirmation (plan 7.5; section 7).
- Units follow `Contracts/README.md`: text offsets are always `{"unit": "unicode_scalar", "start", "end"}` half-open ranges; native UTF-16 ranges appear only inside the adapter-opaque `reader.locator`; audio positions are integer asset-local milliseconds; timestamps are RFC 3339 UTC ending in `Z`; IDs are lowercase UUIDs (Swift writers lowercase `uuidString`); digests are lowercase hex SHA-256. (Until 19 October 2026 this sentence credited the lowercase ID rule to the README, which then said only "UUID strings"; the README now states the canonical lowercase form and lists the contracts that differ, M0 final review contracts R1-07.) Every string is a sequence of Unicode scalar values (rule U1), so scalar offsets are well defined.
- **No nulls.** An optional field is omitted when unknown. Missing information stays missing: a PDF without `/PageLabels` has no `page_label`, an EPUB selection that is ambiguous in Sylvia's extraction has no `text_offsets`, a capture with no precise location has no anchor, an unknown edition has no `edition_id`. Nothing is invented to fill a field.
- Readers tolerate unknown optional fields (README). Credentials have no field anywhere: the property names the context-pack contract treats as secrets, in any letter case, are rejected at the top level of both payloads and inside `generated_answer.endpoint` and `transcript`, the objects that describe a provider.
- **Every pattern is ECMA-262 and Python.** JSON Schema's regular-expression dialect is ECMA-262, and JavaScript validators such as Ajv compile a `pattern` with the `u` flag; this repository's validators use Python's `re`. Every pattern in both schemas is valid in both, and the checker verifies that for every contract document on each CI run with an ECMA-262 grammar check of its own, which agrees with node on every contract pattern and on a corpus of 84 valid and invalid patterns (`commands/check-patterns.py`). The secret-name pattern therefore spells each letter's cases out instead of using the context-pack contract's inline `(?i)`, which no JavaScript validator compiles (review finding L2-R2-01; the context-pack and provider-config contracts are asked to follow). Each letter's class holds every character Python's case-insensitive match accepts for it, the dotted and dotless I (U+0130, U+0131), the Kelvin sign (U+212A) and the long s (U+017F) included, so the pattern refuses exactly the names the context-pack pattern refuses in Python (292 spellings compared in Python and node); the checker derives it from the context-pack pattern on each run and compares. Two dialect differences remain, both on Python's side and both shown by `check-patterns.py`: Python's `$` also matches before a final newline, so the Python-based CI accepts an ID, digest or token followed by a newline that an ECMA-262 validator refuses; and Python's `\s` includes U+001C-U+001F and U+0085 but not U+FEFF, which matters only to the failure-reason guard (section 4). The fix belongs in the shared validator, an ECMA-262 engine for `pattern` (requested), not in each pattern.
- Each member of a top-level `allOf` (and of `retained_excerpt`'s) has a `title` naming the rule, for example `typed-quote-has-no-reader-anchor`; the checker uses it to name the rule an invalid fixture breaks.

### 2. Capture kinds are the design package's strings

`kind` maps one-to-one onto the five capture markers of plan 4.4.5 with exactly the strings `Packages/Design` resolves: `text_quote` → Quote, `note` → Note, `audio_capture` → Audio, `generated_answer` → Generated, `word` → Word, matched exactly and case-sensitively. The design package proposed four of these strings "for the capture-envelope schema"; this ADR adopts them rather than introducing others, because the design package already renders every other string, including `quote`, `audio` and `generated`, with the Pending marker (its tests assert that `quote` is not recognized). `Scripts/check-spike-anchors.py` compares the schema's known kinds with `capture_kind_mapping` in `Contracts/design/marginalia.v1.json` on every CI run, so neither side can change alone. The object that holds a kind's own data is named like the kind (`word`, `generated_answer`); an audio capture has `retained_excerpt` and, optionally, `transcript`.

### 3. Anchor kinds

| Kind | Portable part | Opaque part | Source |
| --- | --- | --- | --- |
| `epub` | `asset_id`, `asset_sha256`, `resource_href`, `resource_media_type`, `exact_text`, `prefix`, `suffix`; optional `text_offsets` (`unicode_scalar` over Sylvia's extraction: `basis`, `extraction_version`, `block_index`, `start`, `end`), `progression`, `total_progression`, `position`, `segment {index, count}` | `reader {adapter, adapter_version, locator}`: Readium's Locator JSON verbatim | ADR-0004 section 3; G0.1 `PortableEPUBAnchor`, envelope proposal and samples |
| `pdf` | `asset_id`, `asset_sha256`, `exact_text` (the reader's composition of the segments, rule A3), `extraction {extractor, adapter_version, platform}`, `segments[]`, one per contiguous range per page in document order: `page_index`, optional `page_label`, `page_rotation` (0, 90, 180, 270), `page_box` (CropBox, points), `text`, `text_range`, `prefix`, `suffix`, `line_rects` normalized to the box in unrotated space, `page_text_sha256` | `reader {adapter, locator}`: PDFKit's UTF-16 ranges | ADR-0005; G0.1 `PDFAnchor` and samples |
| `text` | `asset_id`, `asset_sha256`, `media_type` (`text/plain` or `text/markdown`), `exact_text` (the source text at `text_range`, Markdown markup included), `prefix`, `suffix`, `text_range` into the decoded source text (Markdown source, not rendered output), `source_text {extraction_version, text_sha256}` | optional `reader` | plan 9.3 and 7.5; designed by analogy with EPUB and PDF (no spike produced one) |
| `audio` | `timeline_revision` (display only), `ranges[]`: each `{asset_id, asset_sha256, start_ms, end_ms}`, half-open, file-local, in timeline order at capture time | none | ADR-0006 decision 11 and its open item; G0.4 `AudioRange` |

- **One EPUB anchor per resource, one PDF anchor per selection, one audio anchor per selection.** This follows what the readers return. Readium renders each resource in its own web view with its own locator, so a quotation that continues into the next chapter is several EPUB anchors with `segment`. PDFKit returns one selection across pages, so a PDF anchor holds its pages as segments. An audio selection across files is one anchor with one range per member, each bound to that member's digest.
- **EPUB `text_offsets` locate the selection with its whitespace collapsed**: each maximal run of Unicode White_Space characters replaced by one U+0020, leading and trailing ones removed. That is what the G0.1 adapter looks for in the extraction (`CaptureBuilder.offsets`), because the rendered selection (`getSelection().toString()`) and the extraction can differ in whitespace. `exact_text` itself stays verbatim. ADR-0004 section 3 proposes the offsets only as "optional `text_offsets` in Unicode scalars over Sylvia's extraction"; the G0.1 envelope proposal (`evidence/G01-EPUB/anchor-samples.json`, `envelope_proposal`) describes them as "where exact_text sits in Sylvia's own extraction", which for a selection that starts or ends on a space, or spans a run of whitespace, would be a different number.
- **An EPUB anchor names the reader release.** `reader.adapter_version` is required for EPUB (Readium's locator format changes between releases); `$defs/reader` requires `adapter` and `locator` for every kind that has a reader locator.
- **A text anchor locates source text, Markdown markup included.** `text_range` indexes the decoded source text Sylvia retains (plan 9.3: offsets "against a retained original text representation", so a renderer change never rewrites a quote), and `exact_text` is that text at the range, so any client checks one against the other with the retained bytes and no renderer (rule A2). A selection made in rendered Markdown is therefore stored as the source span the reader maps it to, with the markup inside it: `text-markdown-with-reader-locator.json` stores `for *absolute freedom* and wildness`, and `a2-markdown-exact-text-without-its-markup.json` shows the rendered words alone refused, since they are two scalars shorter than the range. A quotation selected there is that span (rule C2). How the reader maps a rendered selection to a source span is the adapter's own (its locator stays in `reader`); whether a client shows such a quotation with its inline markup rendered is an open item for M3 and design. No spike has a TXT or Markdown reader, so this is designed, not observed.
- **PDF geometry:** every line rectangle lies within its page box (rule A7: x + w <= 1 and y + h <= 1, with 0.000001 of tolerance for the 6-decimal rounding of each component), so a writer clamps a box that reaches past the CropBox (the part outside is not displayed); every segment has at least one rectangle. ADR-0005 normalizes to the CropBox, but the G0.1 builder does not clamp, and could emit a segment without a rectangle for a range PDFKit draws no box for. Neither case occurs in the ten samples (largest x + w 0.849077, largest y + h 0.968347).
- **The audio digest is that of the imported asset of record.** A derived playback copy (ADR-0006 decision 17, the proposed import remux) has the same timing and does not change it, whichever storage option the product owner chooses there.
- **Re-anchoring order** (plan 7.5): the reader locator, then exact text with its prefix and suffix inside the same asset, then offsets when the extraction version or page-text digest matches; ambiguous matches give "Location needs review"; an anchor that cannot be resolved is kept unchanged and the capture is still shown. An EPUB `position` is Readium's synthetic position and is never shown as a page number, and `resource_href` is treated as fallible (G0.1 EPUB finding F1).

### 4. Capture envelope

Required: `schema_version`, `capture_id`, `work_id`, `kind`, `source_snapshot`, `anchors`, `notes`, `provenance`, `created_at`, `updated_at`, `revision`. `edition_id` is required whenever an anchor of a known kind is present and omitted when the edition is unknown.

- **`quoted_text`** is the immutable captured wording with a required `quoted_text_origin`: `selection` (equal to the anchors' exact text, rule C2), `user_entered` (typed by the user: a printed book, or "Type what you heard"), `machine_transcript` (equal to `transcript.raw_text`), `corrected_transcript` (equal to `transcript.corrected_text`; the raw text is kept). Per kind: a `text_quote` has it, selected or typed, and never an audio anchor; a `word` has it by selection, with `word {headword, source_sentence?}` (the sentence contains the word, rule C2) and no dictionary definition field (plan 9.3), and the user's own meaning (plan 7.2) is one of its notes; a `note` and a `generated_answer` never have it; an `audio_capture` has it only from a labelled transcript of its retained excerpt or the user's own typing (I-04; A.1: never fake text to fit an audio capture into a quote).
- **A typed quotation is never attached to an EPUB, PDF or text anchor** (rule `typed-quote-has-no-reader-anchor`). Such an anchor's `exact_text` would locate other words than the typed ones (I-05), and nothing could check one against the other. A typed record of a printed book has `anchors: []` and keeps its page in `source_snapshot.location_label` (section 7). A writer that offers "edit quote" on a selected quotation keeps `quoted_text_origin: selection` and the anchors; plan 11.1 keeps the original, and v1 has no field for a cleaned-up correction yet (open items).
- **`notes[]`**: the user's own words, each note `{note_id, current_revision, revisions[{revision, body, format plain|markdown, saved_at}], trashed_at?}`, with every revision kept (plan 7.3, 11.1) and no two notes sharing an ID (rule C6). A `note` capture has at least one.
- **A note on the whole work is a `note` capture with no anchors** (plan 11.1: notes may be work-level), holding that note, with source kind `work` and no edition (`note-on-the-whole-work.json`). G0.5 recovery keeps such a note as a `note` row without a capture; the checker maps its two into such captures (deviation `note-without-capture`, section 8.3). **A note on an AI conversation** (plan 7.2: a Note has a Work and an optional capture or conversation) **has no form in v1**: neither a `note` capture nor a `generated_answer` can name the conversation a note annotates, so a v1 export cannot carry one, which plan 17.3 requires of every acknowledged knowledge item. G0.5 recovery has one (deviation `note-on-conversation`); M1 and M5 decide its form (open items).
- **`source_snapshot`**: `title`, `author_display` (may be empty), `source_kind` (a token; v1 writes `local_epub`, `local_pdf`, `local_text`, `local_markdown`, `local_audio`, `physical` and `work`, the last for a note on the whole work), optional `edition_identifiers`, and `location_label` with a required `location_label_origin`: `app` (derived by Sylvia) or `user` (typed for a printed book, not verified; addendum 4.3). A manual record keeps its page this way without pretending it is an anchor.
- **`retained_excerpt`** (required on an audio capture, absent on the other known kinds) has four states:
  - `pending` ("Moment saved · preserving audio"): the anchor and notes are durable and the export has not finished.
  - `preserved` ("Audio excerpt saved"): the excerpt names its content-addressed file (`blob_sha256`, `file_extension`, `media_type`, `byte_count`; ADR-0012) and the timing actually exported: `format`, `duration_ms` read back from the written file, `sample_rate_hz`, `frame_count`, and `actual_ranges[{asset_id, start_ms, end_ms, clip_start_ms, source_format}]` in the anchor's order. `clip_start_ms` is where the range sits in the excerpt (plan 7.2's clip-local offsets), so a position in the excerpt, a transcript segment's for example, maps back to its source file and time.
  - `failed` ("Excerpt not preserved · Retry", with `failure {reason, attempts}`): the capture and its notes stay.
  - `removed`: the user removed the excerpt audio (plan 17.2, "Remove excerpt audio"; plan 10.2: excerpts "can be removed separately by the user"). The record of what was exported stays (digest and timing, so a transcript still names its clip and a transcript quotation stays valid), with `removed_at`; the file is no longer kept or backed up, and nothing exports it again unless the user asks, because the state is not `pending`. The design package has no phrase for this state yet (open items).

  Only a preserved or removed excerpt names a file and its timing (`$defs/excerpt_file_fields`). Its timing is code-checked. Each actual range is non-empty, names the anchor's asset at its position, overlaps the anchor's range there, and starts and ends within 500 ms of that range's start and end (rule C4): plan 19.2's capture boundary budget ("within 500 ms of intended boundary"; ADR-0006 decision 14 measured the decoder's recorded start at most 47.9 ms from the true content position for every codec it tested, and the G0.4 probe's actual ranges equal the requested ones). So "preserved" means the file holds every requested range within the budget, not merely some audio near it (review finding R2-02: an actual range overlapping the request by 1 ms was accepted before). The excerpt is the actual ranges back to back, so the first starts at `clip_start_ms` 0 and each later one where the previous one ends (within 1 ms), `frame_count` / `sample_rate_hz` equals their total length (within 1 ms per range), and `duration_ms` is within 4,096 sample frames plus 1 ms of the written frames (rule C9: AAC-LC adds 2,112 priming and up to 1,023 padding frames, which a reader that ignores the edit list counts).

  **A failure reason is built from an error code and at most a bare file name**, never from a platform error's free text, because backups carry it (plan 17.3) and an AVFoundation error description can name a file URL or path (G0.4 records `"\(error)"`). The schema's guard against a path that slips through anyway is a heuristic: it refuses a file URL (`file:/`, not inside a word), an absolute, home-relative or UNC path at the start of a word (a `/`, `~/` or `\\` at the start or after white space, a quotation mark or backquote, an opening bracket, `<`, `>`, `=`, `:`, `,`, `;` or `|`) and a drive path (`C:\`). It does not catch a path after any other character (`x)/private/...`, `+/private/...`), a path whose leading slash was dropped (`Users/name/...`, which reads like a relative path), another user's home (`~name/...`) or a percent-encoded URL; the schema lists these, and `commands/check-patterns.py` shows them allowed in Python and node alike. A bare file name or a path relative to Sylvia's own storage is allowed, since it locates nothing outside Sylvia's container.
- **`transcript`** (audio only): G0.5's `TranscriptRecord` fields (`raw_text`, `segments` in clip-local milliseconds, `language`, `provider_kind` `openai_compatible_transcription`, `host`, `model`, `created_at`, `corrected_text`, `discarded_segment_count`), with the clip named by `clip_sha256`, the digest of the excerpt file that was transcribed. A segment never runs backwards, and a segment of a transcript of this capture's excerpt ends at most 1,000 ms past the excerpt's duration (rule C7; G0.5 drops segments further past the clip). The display label comes from the design package, not from the record.
- **`generated_answer`** (generated answers only): `conversation_id`, `message_id`, `context_pack_id` (the ContextPack holds the exact evidence), the `question` and `answer_text` as saved, `answer_state` (`complete`, or `interrupted` or `cancelled` after some answer text, both shown as "Interrupted · partial answer" and never as complete, I-04), and the `endpoint` identity without credentials. Its `provenance.surface` is `conversation`. Section 9 maps it to the context-pack contract.
- **`provenance`**: `surface` (`reader`, `player`, `quick_capture`, `manual_entry`, `conversation`), optional `entry_point` (for example G0.4's `intent.control@<bundle id>`, ADR-0007), and the command's `idempotency_key` (plan 11.1).
- **`revision`**: 1 at creation, plus 1 for each later durable change to the capture itself (anchors, quoted text, retained excerpt, transcript, trash). Note edits are counted in each note's revisions. Because plan 10.2 writes the anchor first and the export's outcome after it, the state implies a lower bound (rule C8): 1, plus 1 for a preserved excerpt, plus `failure.attempts` for a failed one (each attempt's outcome is a durable write), plus 2 for a removed one (preserved, then removed), plus 1 for a transcript (made from a preserved excerpt), plus 1 while trashed. In the G0.4 probe the store made exactly 2 writes for each preserved or failed record (one attempt).
- **Timestamps** are the device's wall clock. A clock change can put a later change at an earlier time, so no rule compares timestamps and nothing is rejected or reordered by them; revisions give the order.

### 5. Rules checked in code

JSON Schema cannot compare fields, so `Scripts/check-spike-anchors.py` checks these on every fixture and on adapted spike output; the schemas' descriptions list them too. A client in another language reimplements them, with the checker as the reference. They presuppose a schema-valid document. Every branch of every rule has a semantic-invalid fixture that only it detects: on each CI run the mutation pass removes each check, each operand of a compound check and each revision increment of the checker in turn and requires a fixture outcome to change (section 10).

| Rule | Statement |
| --- | --- |
| U1 | Every string and property name is a sequence of Unicode scalar values: no unpaired surrogate escape. |
| A1 | Every range has start < end (`text_offsets`, `text_range`, audio ranges). |
| A2 | A scalar range covers its text: a PDF `text_range` has as many scalars as its segment's `text`, a text `text_range` as many as `exact_text`, and an EPUB `text_offsets` as many as `exact_text` with whitespace collapsed (section 3). |
| A3 | A PDF anchor's `exact_text` is its segments' texts in document order, with nothing or one U+000A between two segments on one page and one U+000A between two on different pages: the reader's own composition of the pieces (ADR-0005: PDFKit puts pieces on one page next to each other, keeps the line break after a piece that ends at a line's end, and joins pages with one U+000A). A reader restores segment by segment and keeps `exact_text` as the quotation; it never rebuilds it from the segments. The rule refuses a text no such composition gives (another separator, two line feeds, pieces out of order, no line feed where the page changes); it cannot tell PDFKit's kept line break from a claimed "\n" join, which only the reader's restore check, with the page text, refuses (ADR-0005, `quotationMismatch`). Until 19 October 2026 the rule required the "\n" join, which refused 6 of the 11 composed selections G0.1 PDF stores exactly (section 11). **How to check it, in linear time** (a client that reimplements the rule must not backtrack over the line feeds; section 11): every character a boundary can add is U+000A, so the texts' other characters must appear in `exact_text` exactly as in their concatenation; between two of those characters (a gap) `exact_text` holds the concatenation's own U+000A count plus at least one for each page change that falls in that gap and at most one for each boundary that falls in it. |
| A4 | PDF segments are in document order: page index non-decreasing; on one page, ranges increasing and not overlapping. |
| A5 | An EPUB `segment.index` is below `segment.count`. |
| A6 | Audio ranges name distinct assets; every range after the first starts at 0 ms (a cross-file selection is contiguous on the timeline at capture time); the total is at most 120,000 ms (plan 10.2). |
| A7 | A PDF line rectangle lies within its page box: x + w <= 1 and y + h <= 1, within 0.000001. |

The **v1 writer profile** is one more requirement on what a v1 writer emits: only the five capture kinds and the four anchor kinds. It is checked on spike output and on every valid fixture except those named `unknown-kind-*`, which show what a later writer may emit and a v1 reader accepts.

### 6. Unknown kinds (compatibility rule)

A v1 writer emits only the five capture kinds and four anchor kinds (`$defs/known_kind` in each schema). A v1 **reader** accepts any lowercase token as a kind:

- An unknown **capture kind** is shown with the Pending marker and its raw `kind` token as the label (plan 4.4.5, A.1), never as a Quote, even when it has `quoted_text`. The design package already does this (`Marker.resolve(captureKind:)`). The reader keeps the whole record unchanged, including fields it does not know, through display, export, backup and restore; offers no action that depends on the kind (no Ask about the quotation, no editing of quoted text, no excerpt playback); may show its notes, whose structure it knows; treats an unknown location origin as unverified; and lets the user remove it only through the ordinary explicit delete.
- An unknown **anchor kind** is kept unchanged and never re-anchored, rewritten or drawn; the capture holding it is still shown, located by its known anchors, or only by its `source_snapshot.location_label` when it has none. A selected quotation is compared (rule C2) only with its EPUB, PDF and text anchors: beside them a later anchor is not compared, and the quotation must still equal their text (`c2-quote-differs-from-its-epub-anchor-beside-a-later-kind-anchor.json`, the review's example R2-03, is refused); a selection located only by later kinds is accepted without a comparison and shown as stored (`unknown-kind-anchor-only-on-a-selected-quote.json`). A v1 reader cannot read the text a later anchor locates, and refusing such a record would make every new anchor kind a breaking change, which the versioning rule below excludes.
- **What keeps a later writer's record readable by v1.** A record stays valid for a v1 reader only while it keeps v1's definitions:
  1. `schema_version` is 1;
  2. every field v1 defines keeps its v1 shape and values on every kind, a later one included, with one exception: a capture of an unknown kind may use new values in the four fields of `$defs/known_kind_values` (`quoted_text_origin`, `provenance.surface`, `source_snapshot.location_label_origin`, a note revision's `format`), each still a lowercase token. So a later kind that reuses `retained_excerpt`, `transcript`, `generated_answer` or `word` uses them as v1 defines them (no new excerpt state, provider kind or answer state) and is checked by the same code rules (`unknown-kind-reusing-the-excerpt-and-transcript.json`; without its excerpt, its transcript quotation breaks C5), and a later kind that needs another shape adds a field of its own;
  3. an anchor of a v1 kind validates as `anchor.v1`, and a capture holding one names its edition; an anchor of a later kind may be located without an edition (addendum 4.3: a clip located in a retained clip while the edition is unknown), and `anchor-names-edition` applies only to anchors of known kinds;
  4. no property name matches the secret pattern.
  A later writer that needs anything else adds a field, uses a new kind, or bumps `schema_version`. The fixtures `unknown-kind-with-a-new-excerpt-state.json` and `unknown-kind-anchor-of-a-known-kind-without-capture-edition.json` show records that break rules 2 and 3 being refused.
- **A record v1 cannot read is refused, never silently dropped or partly imported.** That covers a newer `schema_version` and any record that breaks the rules above. Plan 17.4 makes restore validate before it replaces anything and reject newer unsupported schemas without altering existing data, so a restore that meets such a record stops before changing anything and names it; a future portable import or sync must do the same. In V1 itself the only way a record from a newer writer reaches the app is a restore.
- Adding a capture or anchor kind later is an additive change inside v1 (README versioning rule). A capture kind also needs a marker through plan 4.4.9 change control and its string in the design package's mapping; the CI check keeps the two in step. Removing a kind or changing a field's meaning is a v2.

### 7. Missing and relocated locations

A capture never gets an invented location. A note on a whole work, a quote typed from a printed book or a capture whose edition is unknown has `anchors: []`; a typed page is a `location_label` with origin `user`; an edition that is not known is left out (`edition_id` omitted) rather than guessed. Loss of a precise location later (re-anchoring fails) leaves the anchor as stored and the capture visible; it is never deleted or attached to another passage (plan 7.5).

**Cross-edition relocation** (plan 7.5: always confirmed; addendum 4.3: offer candidate connections "without moving the original locator or replacing it") is decided as follows. `edition_id` and `anchors` record where the capture was made and are never moved, rewritten or replaced, by a relocation or anything else; rule C1 keeps `anchors` to that one edition. A relocation the user confirms is recorded beside them, as an optional field holding, for each confirmed edition, that edition's ID, the anchors there (of the same work, validating as `anchor.v1`) and when it was confirmed. No spike or plan section specifies the relocation flow (what is offered, how a candidate is scored, whether a declined candidate is remembered), so v1 does not define that field's name and shape yet: M3 adds it when it builds relocation, as an additive optional field, which v1 readers keep unchanged as an unknown optional field (open items). A relocated location never takes the place of the original as the capture's provenance: the quotation's exact text and its original edition-specific anchor stay what I-05 asks for.

### 10. Tooling and its place

Three tools keep the contracts honest, and `Scripts/ci.d/11-capture-anchor-contracts.sh` runs all three on every change:

- `Scripts/check-spike-anchors.py`: the related contracts, the patterns, every fixture's expected outcome, the spike output and the G0.5 recovery comparison (sections 5 and 8).
- The fixture generator, `make-contract-fixtures.py`: every fixture is written by it, from spike output where it exists, and the drop-in requires the committed fixtures to equal its output byte for byte.
- The mutation pass, `mutation-pass.py`: it deletes each protected schema constraint (a `required` entry, an `enum`, a single `enum` value in an `if` condition or a `not`, a numeric `type`, a bound, a rule) and disables each branch of each code rule in turn, and requires each to change a fixture outcome. A new constraint or rule therefore needs a fixture that breaks it alone, or CI fails.

The generator and the mutation pass are tools of the contracts, not Stage 0 evidence: the owner after M0 changes a fixture or adds a constraint through them. They live beside the checker, in `Scripts/contracts/` (review findings R1-11, R2-05). Written in `Docs/Stage0/evidence/M0-contracts/commands/`, they were moved there at M0 assembly (14 October 2026), as `Docs/Stage0/M0-contracts.md` requested, and the drop-in's `tools=` line now names that directory. Both find the repository root themselves, so nothing else in them changed but their usage lines. The evidence commands (the G0.4 probe and head check, the negative controls, the pattern check and the clean run) stay with the evidence.

- **A3 in linear time** (20 October 2026; the final review's second round, contracts R2-01; integration log section 12). The revised A3 built a regular expression from the escaped segment texts joined by an optional line feed (a required one at a page change) and matched it with Python's backtracking matcher. When segment texts are, or begin or end with, U+000A, each optional line feed can match two ways, so refusing a text no composition gives took time exponential in the number of segments: about 3.6 times longer per two more segments, 4.5 s at 30, for a schema-valid anchor whose segments are each one line feed, while the schema allows 10,000. A restore or import that ported the checker would hang on such a file instead of refusing it. The checker now decides A3 with the counting rule section 5 states (`pdf_composition_holds`), which gives the same outcome as the expression on every case of a bounded exhaustive set (754,747 cases) and on 200,000 random ones, and decides anchors of 10,000 one-line-feed segments in about 0.04 s; the checker runs that check at the schema's limit on every CI run, in a subprocess with a 60 s limit, and a copy of the checker with the expression put back fails it at that limit (`evidence/M0-Integration/final-fix-2/a3-linear-check.log`). Real anchors were never affected (the G0.1 PDF builder stores no trailing line break), the rule's outcome is unchanged, and the mutation pass still notices each of its two branches (61 code-rule checks). Agent-written, not reviewed.

## Consequences

- M3 and M4 can build their capture transactions, readers and exporters against fixed portable shapes; M1 maps them to tables (sections 8.3 and the open items); M5 links saved answers through `generated_answer` and the context-pack contract (section 9).
- Every reader and the audio importer must compute and keep asset SHA-256 digests before a capture can be written; G0.4 has no importer yet.
- Writers use the design package's kind strings, lowercase UUIDs, omit unknown values, clamp PDF rectangles, read an excerpt back and check its timing before calling it preserved, count the excerpt's changes in the capture's revision, and never attach a typed quotation to a reader anchor. The G0.1, G0.4 and recovery spikes each differ somewhere here (section 8).
- The text kind and the `generated_answer`, `word`, `transcript` and removed-excerpt parts are designed from the plan, G0.5's types and the context-pack contract, not from captures a spike wrote. The first M3, M4 and M5 implementations must be checked against these fixtures and may need additive changes.
- An excerpt's digest identifies one export, not an audio range: probe runs of the same ranges produced AAC files of the same size with different digests (`g04-capture-records/context.json`; the earlier run at commit `7b239b1`; the head check's runs). A retry or a re-export after a range edit always yields a new blob, so a transcript of the earlier clip no longer satisfies C5.
- Validation needs both the schemas and the code rules. A schema change that adds a constraint, and a code rule or a branch of one, needs a fixture that breaks it alone: the mutation pass fails CI otherwise (section 10). A new pattern must be valid ECMA-262 and Python; the checker refuses any other in any contract, two recorded exceptions apart.
- A Python-based validator, this repository's included, accepts an ID, digest or token followed by a newline that an ECMA-262 validator refuses, until the shared validator uses an ECMA-262 engine for `pattern` (requested). Writers never produce such a value; the difference matters to a server or importer that validates untrusted input with Python.

## Alternatives considered

- **Closed `kind` enums.** Rejected: a reader would reject a capture from a later writer for its kind alone, which the plan (A.1: show it as Pending) and the addendum (never silently discard) rule out. The writer profile keeps v1 writers to the known kinds.
- **Opening every v1-defined field for unknown kinds** (any excerpt state, provider kind or edition rule on a later kind). Rejected for v1: a reader cannot tell what a known field means when its values change, and README makes a changed meaning a new version. A later kind keeps v1's definitions or brings its own fields (section 6); the edition rule is opened only for anchors of later kinds, which v1 never interprets.
- **Kind strings equal to the marker names (`quote`, `audio`, `generated`),** as G0.5 recovery uses and as an earlier draft of this contract had. Rejected: the merged design package resolves `text_quote`, `audio_capture` and `generated_answer` and renders the others as Pending, so every quote, audio capture and answer would have been shown as Pending. Changing the design package instead would replace A.1's `text_quote` and a tested mapping for no gain.
- **One EPUB anchor with segments, like PDF.** Rejected for v1: each EPUB resource has its own Readium locator, and the spike stores one per anchor; folding them would put several opaque locators in one anchor for no gained capability.
- **Global-timeline audio positions.** Rejected by plan 7.5 and ADR-0006: a reorder would rewrite stored captures.
- **A `manual` anchor kind for typed pages.** Rejected: there are no asset bytes to anchor to; the label with its origin says exactly what is known.
- **A typed quotation at a reader anchor** (`user_entered` with an EPUB, PDF or text anchor). Rejected: the anchor's text and the typed words could differ with nothing to say which is the quotation, and an "edit quote" that switched the origin would drop the original selection (plan 11.1).
- **Recording a cross-edition relocation by replacing the anchors, or by adding the new edition's anchors to `anchors`.** Rejected: the first loses the original locator (addendum 4.3), the second mixes editions in one list whose offsets are edition-specific (C1).
- **Keeping nulls as the PDF spike writes them.** Rejected: two spellings of "unknown" make equality and digests ambiguous across clients.
- **Timestamp order as a validity rule** (`created_at` <= `updated_at`, revisions saved in order), as an earlier draft had. Rejected: a device clock can move back, so a valid record would be refused, and refusing a record at restore would refuse the user's knowledge.
- **Validating only hand-written fixtures.** Rejected by the purpose of this work: the checker runs the contract against what the spikes wrote.
- **Exempting from C2 every selection that holds a later anchor kind,** as the first round's checker did without saying so. Rejected (review finding R2-03): a v1 reader would show a Quote with an EPUB highlight on a passage the quotation differs from (I-05). **Refusing a selection located only by later kinds** is rejected too: v1 cannot read the text a later anchor locates, and refusing would make every new anchor kind a breaking change (section 6).
- **Markdown offsets into the rendered text,** as EPUB's offsets index Sylvia's extraction. Rejected: plan 9.3 asks for offsets against the retained original so renderer changes do not rewrite quotes, and source offsets can be checked with no renderer; the price is that a quotation crossing markup keeps it (section 3).
- **Keeping the context-pack contract's inline `(?i)` in the secret-name pattern.** Rejected (review finding L2-R2-01): no JavaScript validator compiles it, so no JavaScript client could load either schema.
- **Working around Python's `$` in each pattern** (`$(?!\n)`, or a `maxLength` beside each fixed-length pattern). Rejected: it obscures every pattern, in this contract only, for a difference that belongs to the validator; the shared validator is asked for an ECMA-262 engine instead.
- **A C4 bound tighter than the plan's 500 ms,** such as G0.4's measured 48 ms. Rejected for v1: plan 19.2 sets the budget, and a tighter bound would refuse excerpts the plan accepts; a codec with a larger decoder offset gets a correction of its own (ADR-0006 decision 14).
- **A separate record for a note on the whole work.** Rejected: every saved thought is one envelope with one marker (4.4.5), a `note` capture with no anchors already says exactly what is known, and the earlier draft's statement that such notes were "outside this envelope" contradicted its own fixture (review finding R2-04).
