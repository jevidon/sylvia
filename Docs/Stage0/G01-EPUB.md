# G0.1 EPUB capture with Readium: Stage 0 report

Gate G0.1, EPUB half (plan Section 21.1). Spike `Spikes/G01-EPUB`; decision record ADR-0004 (Proposed); device and human steps `Docs/Stage0/device-checklists/G01-EPUB.md`.

**Short answer.** Readium 3.11.0 can do what plan 9.1 needs: selection with exact text and context, an Ochre fill-plus-underline highlight, Literata as the default face with the user's size and spacing, locator restoration through reflow, rotation and relaunch, in-place footnotes, and extraction that maps search hits back to the passage. It cannot be used as shipped for safety: on its own it runs publication scripts, lets a publication reach the network, serves archive entries the manifest does not declare to any navigation that is not a link tap (a form submission, for example), opens content-encrypted chapters, and crashes on deeply nested markup. It also stores the wrong resource in a selection's locator just after a jump. The adapter in ADR-0004 fixes each of these, and every fix has a test, including tests built from the review's bypasses of the first sanitizer (comment and prefixed-root tricks that let event handlers run, nesting hidden from a text scanner that crashed the app, a quadratic regex) and from the second review's form navigation to undeclared and unsanitized entries. The sanitizer now parses each document and writes it out again instead of editing its text, and checks the result in every parser that reads it; the adapter serves only what the manifest declares, each resource by its declared media type, and limits the web view's document loads to the reading order. Nothing has been run on a physical device yet.

**M0 item review record.** Every author and review round of `m0-int-minors-g01-epub`, the M0 item that took this gate's remaining review findings, handed over on 24 October 2026 from the orchestrating session's workflow journals (agent reviews; human sign-off pending): its one review, round 4, accepted `d3170541` with five minor findings, R4-01 to R4-05, left open at the merge and not written up in this report: [`evidence/M0-Integration/item-reviews/minors-g01-epub.md`](evidence/M0-Integration/item-reviews/minors-g01-epub.md).

### What Readium 3.11.0's locator contains

- **Selection:** `href`, `type`, `title`, `locations.{progression, totalProgression, position}`, `text.{before, highlight, after}`. No CSS selector, partial CFI, DOM range or fragment. `before` and `after` are raw DOM text (tabs and newlines included). The `href` and `locations` are copied from the navigator's current location, not taken from the selection (finding F1), so `progression` and `position` describe the page shown, not the quote.
- **Reading position:** the same without `text`.
- **Content iterator and search hit:** adds `locations.cssSelector` and `text`; no `position`.
- **Units:** Readium's locators carry no character offsets. Its JavaScript and the DOM count UTF-16 code units. Sylvia's `text_offsets` count Unicode scalars over Sylvia's extraction and are converted at the adapter boundary (`TextOffsets`); seven non-BMP letters before a point make the UTF-16 offset 7 higher, as tested.
- **`position`** is Readium's synthetic unit (about 1,024 characters). It must not be shown as a page number (plan 7.5).

## Findings that change the plan's scope or approach

**F1. Readium's selection locator can name the wrong resource.** Readium 3.11.0 builds the selection locator from `navigator.currentLocation` plus the selected text (`EPUBNavigatorViewController.spreadView(_:selectionDidChange:frame:)`) and ignores the resource that its own JavaScript reports. Just after a jump, `currentLocation` still names the previous resource. In this spike's first full run the Greek quotation from book 7 was stored with `href` book 1 ([`observations/run-0352-anchor-samples-before-selection-check.json`](evidence/G01-EPUB/observations/run-0352-anchor-samples-before-selection-check.json)), and the test did not catch it. In the clean run's regression test Readium named the wrong resource in 3 of 3 jump-then-select captures. **Change:** captures must go through `ReaderSession.captureSelection()`, which checks the resource against the document holding the selection, rebuilds the locator when they differ (text kept, the other resource's progression dropped) and returns nil if the selection changed meanwhile; the adapter corrected all 3, and each corrected locator reopened and decorated the passage. Worth reporting upstream. A quotation saved with the wrong resource would break I-05 (source fidelity) silently, so the reanchoring rules of 7.5 must also treat `href` as fallible.

**F2. Readium does not stop publication scripts or remote resources, and a text-level sanitizer does not either.** Plan 8.3 says publication scripts and remote resources are disabled. Readium 3.11.0 does not do that itself (T13 above). **Change:** the safety controls are Sylvia's, in the adapter (ADR-0004 section 4): a container that serves only declared resources, a sanitizer on every document a web view can render, a CSP, a WebKit content rule list on every web view (network, and since F14 document loads outside the reading order), and `file:`-only asset retrieval. The rule list alone blocks requests but leaves scripts running, so the sanitizer and CSP are required. The first version of the sanitizer edited the HTML text with regular expressions, and review showed that is not enough (finding R1-02): a comment containing `<head>` before the real head put the CSP inside the comment, and a namespace-prefixed root (`<h:html>`) got no CSP at all; in both, the publication's `onload` and `onerror` handlers ran through the adapter, and the sanitizer's statistic still reported the CSP as injected for the first. The sanitizer now parses the document as XML, writes it out again in a canonical form (no comments, no prefixes, everything escaped, scripts, handlers and script URLs removed in every namespace, the CSP first in a head it controls), and serves it only after checking, in libxml2 (WebKit's XHTML parser), in `SwiftSoup.parse` as Readium calls it and in SwiftSoup's HTML5 parser (WebKit's `text/html` path), that the CSP is the first child of the first head and that no script, handler or script URL is left; `cspInjected` is that check. In `g01-csp-bypass.epub` (the review's two inputs plus `<!-->` in a `text/html` item, which WebKit's HTML parser reads as a whole comment followed by a live script) Readium alone ran a script or handler in all three chapters and the adapter ran none ([`safety.json`](evidence/G01-EPUB/safety.json) key `csp_placement_bypasses`). These controls are product code with their own tests and must be re-run on every Readium upgrade.

**F3. Documents that are not HTML can run scripts.** An SVG page in the spine and a spine item declared `application/xml` whose root is XHTML both ran their scripts under Readium alone, and an HTML-only sanitizer does not reach them (a page CSP can only be declared by an HTML `meta` element). **Change:** the adapter parses such documents and writes them out canonically too (processing instructions, including an `xml-stylesheet` that could apply XSLT, are dropped); it serves them only when nothing had to be removed, judged on the parse (so `javascript&#58;` counts as `javascript:`), and otherwise shows a placeholder, reporting the resource as `unavailable_active_content` (`testNonHTMLReadingOrderDocumentsRunNoScript`). The check is conservative: an SVG page with a harmless `onclick` is withheld. Since review R2-01 the same applies to every declared resource of a document type a web view renders (not only reading-order items), and form controls, `action`/`formaction` attributes and any element in the XHTML namespace count as active content in such a document (F14).

**F4. Deep nesting crashes Readium, and nesting has to be measured on the parse.** Readium's content iterator and search service overflow the stack (SwiftSoup `Node.language()` recursion) on 10,000 nested elements; the UI tests reproduce both crashes in a separate process. The first adapter measured depth with its own byte scanner, and review showed two ways past it (finding R1-01): spans after `<!-->` (one comment to an XML parser, live elements to SwiftSoup's tokenizer) and `<span></x>` repeated (the scanner popped on any end tag; SwiftSoup ignores unmatched ones), each 10,000 deep and each crashing the app through the adapter. **Change:** depth is now measured by the parsers: libxml2 stops at the first element deeper than 256, before any tree exists, and the served document is parsed again by `SwiftSoup.parse` exactly as Readium's content iterator calls it, and by SwiftSoup's HTML5 parser, each required to nest no deeper than 256. Because the served text is the canonical re-serialization, the comment-wrapped spans are not in it at all, and the unmatched end tags are not well-formed XML, so that chapter is withheld. In `g01-nesting-bypass.epub` extraction, Readium's search and the navigator run in the test process without a crash, and the out-of-process UI tests finish the iterator and search walks. A chapter at exactly 256 levels still renders, extracts and is searchable. Real fixtures nest 8-11 deep. Worth reporting upstream.

**F5. Readium reads a whole ZIP entry into one buffer, and trusts the declared size.** Reading the honest bomb's 200 MiB chapter took one 209,715,200-byte buffer and about 200 MiB of extra memory; the lying bomb's chapter stopped at its declared 4,096 bytes. **Change:** preflight limits on declared sizes are what bound memory: any markup or style entry above 16 MiB is rejected (largest real markup entry is under 1 MiB). The 16 MiB and 256 MiB values are spike proposals for the product owner (*decided on 22 October 2026: accepted as configurable V1 defaults, rechecked against more real books in M3, PO-02 (a), as recommended; this note was added after the review of the decisions round's fix, its finding FID2-02*). Within that allowance the sanitizer's own work must be bounded too; the first version's script pattern was quadratic (review finding R1-04: 21.5 s for 128 KiB of `<script ` tokens, hours at 16 MiB). The parser-based sanitizer is linear in the input for every pattern measured (host, debug build, 1 to 16 MiB, [`sanitizer-timing.tsv`](evidence/G01-EPUB/sanitizer-timing.tsv)), but the cost per byte depends on the markup, mostly in the two SwiftSoup verification parses. The previous version of this report named element-dense markup as the slowest per byte (4.2 s for 2 MiB); review finding R2-02 showed that attribute-dense markup is about three times slower (about 6 s per MiB at 256 attributes per element, so 4 MiB already passed the 20 s budget on the Mac). The caps now bound the work per document: at most 100,000 elements, 256 attributes on one element and 100,000 attributes in all (namespace declarations count as attributes; the real fixtures have at most 1,109 in one document). The slowest documents that are still served are the ones just under the caps. These figures are measurements on a shared, loaded Mac, not bounds: an earlier version of this report gave one run of each as "at most", and review R3-01 measured the same test up to 2.7 times slower on a rerun. Each is now timed three times, and the load average is written at the top of [`sanitizer-timing.tsv`](evidence/G01-EPUB/sanitizer-timing.tsv). In the committed CI run (host, debug build, 1-minute load average 75 at the start of the timing test and 77 at its end, 18 processors, other agents building and testing on the Mac): 0.82 MiB with 256 attributes on each of 394 elements (99,588 attributes) took 13.2, 8.4 and 6.2 s; 1.34 MiB of 99,995 elements with one attribute each 4.7, 4.5 and 4.2 s; 99,995 elements without attributes 2.1, 2.2 and 2.6 s. A rerun at a load of 35-73 ([`observations/run-1013-0623-host-sanitizer-timing.tsv`](evidence/G01-EPUB/observations/run-1013-0623-host-sanitizer-timing.tsv)) took 4.8-5.0, 4.2-4.7 and 2.0 s; earlier single runs took 4.8, 4.5 and 2.2 s (the previous committed run) and 6.7, 6.0 and 5.9 s (review R3-01's rerun). So the margin to the 20 s budget on this Mac is between about 1.5 and 4 times, depending on load. Among the uncapped patterns the slowest, escaped `<script` tokens in text, took 5.3 s at 16 MiB in the committed run. Inputs past a cap were refused in 0.2-1.5 s, before SwiftSoup sees them. The time on a phone is not measured; a phone that takes more than 20 s withholds a legitimate document near the caps (it stays safe, but the reader shows a placeholder). The hosted test `SanitizerAtCapsTimingTests` times the same three documents three times wherever the hosted tests run and fails if a run passes 20 s; on the simulator (which runs on the Mac's processor, so this is not a phone figure) the three documents took 5.1, 4.6 and 5.1 s; 5.7, 4.7 and 5.1 s; and 2.7, 2.1 and 2.1 s, all served, at a load average of 43-62 ([`sanitizer-at-caps-simulator.json`](evidence/G01-EPUB/sanitizer-at-caps-simulator.json)), and device checklist step 11 runs it on the phone (`sanitizer-at-caps-device.json`). **Background CPU:** a worker that runs over the 20 s budget cannot be stopped; it finishes in the background and its result is discarded, and later reads of that document get the placeholder at once (host test `budget`). At most two sanitizer workers run at once per open publication, each holding its slot until its thread really finishes, and a read waits for a slot within its own 20 s budget (host test `workerLimit`). So a publication with many slow documents keeps at most two threads busy (64 MiB stack reservation each), each for at most as long as one document takes; while they are busy, other documents of that publication can be withheld for want of a worker and are tried again on their next read.

**F6. A single navigation can be undone, depending on timing.** A single `go(to:)` into a just-preloaded resource was undone 0 of 3 times in the first run, 5 of 5 in a later one, 2 of 5 in an earlier clean run (commit `2f20df2`), 4 of 5 in the previous one (commit `223a242`) and 5 of 5 in this report's clean run ([`navigation-race.json`](evidence/G01-EPUB/navigation-race.json), [`observations/`](evidence/G01-EPUB/observations/README.md)). The adapter repeats the jump after 600 ms and kept the passage on screen in every attempt of every run. **Cost:** each navigation takes about 600 ms longer to be final. A fix in Readium would remove that cost.

**F7. The decoration race that motivated the redraw logic was not reproduced.** An earlier agent saw duplicate highlight boxes after back-to-back theme changes; in this spike's runs Readium alone left a duplicate 0 of 3 times each time (this report's clean run, and `observations/run-0352-decoration-race.json`) ([`decoration-race.json`](evidence/G01-EPUB/decoration-race.json)). The adapter's clear-and-redraw after settings changes and its duplicate repair are tested (`testRapidSettingsChangesConverge`, `testDuplicateRenderingIsRepaired`) but are defensive, not proven necessary.

**F8. One gesture cannot select across resources.** Each resource is its own web view. A quotation that continues into the next chapter is stored as ordered anchors (`segment`), and its text is joined without loss; the UI needs a way to extend a quotation into the next chapter. Whether a finger can extend a selection past a page edge within one resource in paginated mode is checklist step 3.

**F9. After a reflow, Readium keeps the progression, not the text.** After a font size or line-spacing change, the highlighted passage was often not on the page Readium restored (`visible_before_navigate` false in 4 of 13 steps), although it was always drawn on the right text and the saved locator always reopened it. If the product should keep the first visible sentence in view through a settings change, the adapter has to re-navigate to the text of the last position; this spike did not do that.

**F10. `text_offsets` is not always available.** It is null when a selection spans paragraphs or is ambiguous in the extraction. The anchor still has the verbatim locator and exact text with context, which is what 7.5 reanchors with first; offsets are a third, optional signal.

**F11. Script evaluation can fail while a page is being replaced.** Right after a jump, WebKit reported `InvalidTransition { phase: idle, targetPhase: failed(deinit) }` for a script sent to the outgoing page. Adapter code that evaluates scripts must treat a failure as "unknown", as `captureSelection()` does by returning nil.

**F12. Note text must not go through an HTML renderer outside the web view.** The harness first rendered note HTML with `NSAttributedString`'s HTML importer, which can load remote resources; it now shows plain text. The product's note popover needs its own safe rendering.

**F13. The sanitizer narrows the compatibility subset to well-formed XHTML, and changes markup but not text.** A content document that is not well-formed XML with an XHTML `html` root, uses a named entity outside the XHTML 1.x DTDs, declares entities, or is not UTF-8 (Readium's resource transform decodes UTF-8 only and passes an empty string otherwise) is shown as a placeholder and reported as `unavailable_unsupported_markup`. All 195 XHTML documents in the five real fixtures are served, and for each the served text and element sequence equal the original's, both read with SwiftSoup's XML parser (host, [`sanitizer-real-books.txt`](evidence/G01-EPUB/sanitizer-real-books.txt)); in WebKit, `document.documentElement.textContent` of all 191 reading-order documents is identical with and without the sanitizer (simulator, `SanitizerFidelityTests`, [`sanitizer-fidelity-webkit.json`](evidence/G01-EPUB/sanitizer-fidelity-webkit.json)). That WebKit comparison found a defect the first host check could not, because it read both sides with the same parser: Foundation's `XMLParser` drops a U+FEFF at the start of each string it reports, and Standard Ebooks put U+FEFF (a word joiner) right after inline elements, so 9 were lost in one Middlemarch chapter. The sanitizer now escapes U+FEFF around the parser, with a host test. Every served document starts with an XML declaration, and SwiftSoup (inside Readium's content iterator) then parses it with its XML tree builder; before, the one real document without a declaration (a Project Gutenberg cover page) was parsed as HTML. The extraction version is now `sylvia-sanitizer-2`. Since review R2-01 the subset also excludes content the manifest does not declare (never served) and XHTML content declared as generic XML (a spine item declared `application/xml` whose root is XHTML is withheld even when it has no script, because such a document cannot carry the page CSP; F14). None of the five real fixtures has either: apart from `META-INF/` and the OPF, the only archive entry outside their OPF manifests is Standard Ebooks' `onix.xml` record (referenced by a metadata link), which the reader never needs.

**F14. Readium lets a page navigate to any archive entry by any means other than a link tap.** Review R2-01 found that the adapter as it stood still ran publication scripts after one tap: Readium 3.11.0's spread view cancels only `.linkActivated` navigations, its navigator serves any archive entry the web view asks for (an undeclared `evil.html` as `text/html`, by its extension), and the adapter sanitized only declared HTML, SVG and non-HTML reading-order items. A form in a script-free spine item declared `application/xml` (served with no CSP, because a page CSP needs an HTML document) navigated the web view to the undeclared entry and to a declared non-spine XML resource, and both scripts ran. The ADR's statement that an undeclared entry is never rendered was wrong. **Change** (ADR-0004 section 4 items 4 and 5): the adapter's container serves only manifest-declared entries and treats each by its declared media type (HTML sanitizer with CSP; every other document type through the non-HTML sanitizer, where form controls and XHTML elements now count as active; known passive types unchanged; anything else empty), and the per-publication content rule list blocks every document load outside the reading order. `SafetyTests.testNonLinkNavigationsReachOnlySanitizedDeclaredDocuments` reopens `g01-form-navigation.epub` for each of ten actions (form button `click()`, the navigation a finger tap on the button produces, in the XHTML chapter and in the XML item, and a reader-owned `location.href` standing in for any other non-link navigation, aimed at the undeclared entry, the declared non-spine XML and XHTML resources and markup declared `image/png`) under four configurations. Readium alone ran the target's script in all 8 positive controls; the full adapter, the container with its sanitizers alone, and the rule list alone ran none and never left the publication. Read through Readium's API, the adapter serves no undeclared entry (nor the OPF or `META-INF/`), serves the non-spine XML as a placeholder and the non-spine XHTML with the CSP and no script ([`safety.json`](evidence/G01-EPUB/safety.json) key `non_link_navigations`). The finger tap itself is checklist step 13 (pending-device). Worth reporting upstream: Readium could cancel every navigation of a spread's web view away from the resource it loaded.
