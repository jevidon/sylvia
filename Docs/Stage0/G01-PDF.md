# G0.1 PDF capture with PDFKit: Stage 0 report

Workstream G0.1, PDF half. Spike: `Spikes/G01-PDF/`. Decision record: `Docs/ADRs/0005-pdf-reading-and-anchors.md` (Proposed). Device steps: `Docs/Stage0/device-checklists/G01-PDF.md`. Evidence: `Docs/Stage0/evidence/G01-PDF/`.

**Summary.** PDFKit supports what the plan asks for PDF anchors. Multiline, cross-column, cross-page and rotated selections (0, 90, 180, 270, inherited rotation, offset CropBox) become portable anchors (page index, printed label, Unicode scalar range, normalized line rectangles, rotation). After a JSON round trip and a fresh open they restore with identical text, and the rebuilt selection's line rectangles equal the stored ones (this shows the restore is deterministic; where the rectangles are drawn is checked separately against PDFKit's page transform, a live `PDFView`, offscreen pixels and screen captures). Two capture defects were found and fixed after M0 integration. PDFKit reports a selection that ends with a line's last character with the following line break in its range, so such an anchor quoted the text but stored the break, and it could not be restored; the builder now drops the break, and these selections restore exactly, including the last word of a line long-pressed in the harness (rows 8a and 22a). The guard added with that fix assumed PDFKit joins a selection's pieces with "\n", and so refused selections composed of two or more pieces on a page (review finding R4-01); the builder now checks each new anchor by restoring it, and composed selections restore exactly (row 8b, finding 15). Highlights live in Sylvia's own records and are drawn as an Ochre fill plus underline over the page without touching the file; the overlay is safe while PDFKit draws tiles on background threads (stress tests, also under the Thread Sanitizer). A new highlight appears after `PDFView.setNeedsDisplay()` alone. A highlight whose page text changed since capture is relocated by its exact text and context, drawn where the text is now and saved, so it restores exactly next time; anchors captured on iOS 26.5 restore exactly on the iOS 27.0 simulator runtime, and the two runtimes extract every page of the fixtures identically (32 pages; the password-protected and truncated files open on neither). Text drawn with rotated text matrices and columns drawn in a scrambled order (generated, not real-world PDFs) are extracted and anchored and restore exactly, but on rotated-matrix lines the overlay is wrong: its underline lies on the baseline side only for upright text (row 10c, failed; finding 12). Image-only pages report "No selectable text on this page". Password-protected and truncated files fail with specific errors and no unlock attempt. With Sylvia's link delegate installed, no link, outline item or other PDF action opens anything on its own, including actions chained with /Next and additional actions (/AA) at document, page, link and form-field level, and neither a file's open action nor a page-open trigger runs (with or without the delegate); without it, PDFKit's default opens a link's URL, including an /AA mouse-up URL that PDFKit presents as the link's own action, so the delegate is required. All of this is proven on the simulator only. A person's finger selection, alignment judgement, VoiceOver, pointer hover on an iPad and device open time have not been run on a device and are pending.

**Environments.** Simulator: iPhone 17 (iPhone18,3), iOS 26.5 (23F77), and for the cross-OS restore check only, iPhone 17 on iOS 27.0 (24A434). This round's runs (after M0 integration) used simulators named `Sylvia-M0-minors-g01-pdf`, created new for the clean run; the gate's earlier rounds used `Sylvia-M0-g01-pdf`. Xcode 27.0 (27A266a), Swift 6 language mode with complete strict concurrency and warnings as errors (0 Swift warnings). Host: macOS 26.6.2 (25G83) on the build Mac (Apple M5 Max), Python 3 standard library (fixture generator, crash-report summaries). No physical device was used.

## Findings that change the plan's approach

1. **PDFKit opens link URLs by itself unless a delegate takes over.** The control tests show PDFKit's default tap handling opening a URL (the canary arrived) without any Sylvia code asking. The reader must always install the link delegate (`pdfViewWillClick(onLink:with:)`) and route through a policy; this is required, not optional hardening.
2. **A /Launch action arrives as a `file:` URL.** PDFKit presents `/Launch /F /bin/sh` as a URL action whose URL is the launch path resolved against the PDF's own location. A policy that only blocks "launch" by type would miss it; Sylvia's policy allows only `http`, `https` and `mailto` (after confirmation) and blocks everything else, including `file:`.
3. **PDFKit does not enforce the "no copying" permission.** For an encrypted file that opens without a password but forbids copying, `allowsCopying` is false yet `PDFPage.string` and selections still return the text. If Sylvia is to respect the flag, it has to do so itself. The spike disables text features on such files; this needs a product decision (Open questions).
4. **`PDFPage` subclasses cannot have Swift stored properties.** PDFKit creates pages from `pageClass` without running Swift initializers: a stored property with a default of 20823 reads 0 on a page PDFKit made (`pdfkit-page-class-initializers.txt`). With the overlay rectangles in a stored mutex, the harness crashed 8 times during development, on the main thread and on PDFKit's tile-render queue (`overlay-stored-property-crash.txt`, summarized from the system crash reports with `Spikes/G01-PDF/Tools/summarize_crash_reports.py`). Per-page overlay data goes in a mutex-guarded associated object. The page-class, overlay-pixel and overlay-concurrency tests (with the Thread Sanitizer run) must stay in the product suite.
5. **PDFView caches page tiles; `setNeedsDisplay()` is enough to show a new highlight.** When only the overlay changes, PDFView does not redraw the page by itself (0 draws in 3 s). `PDFView.setNeedsDisplay()` redraws the visible tiles through the overlay on PDFKit's tile threads and keeps the selection, page and scale (`overlay-redraw-invalidation.txt`); on screen the new highlight appears at once, and does not without the call (`ui-touch-highlight-relaunch.txt`, control `ui-redraw-control.txt`). The harness uses this, and dismisses the saved selection so its tint does not cover the new highlight. Only draw calls and screen pixels were checked, on the simulator; the cost on a device was not measured.
6. **Printed labels must come from `/PageLabels` only.** PDFKit returns "1", "2", ... for files without `/PageLabels`; storing those would claim a printed page number the publication does not have (the plan's rule for EPUB "page 183" applies here too).
7. **The extraction version must include the OS build.** PDFKit's text extractor ships with iOS. Page-text digests in each anchor detect a changed extraction; ranges are trusted only when the digest matches. On the iOS 27.0 simulator runtime the text of every page that the ten sample anchors touch was identical to iOS 26.5's, so they restored exactly, and so was the text of every other page of the fixtures (row 24); when the text does differ, the reader relocates the highlight, draws it and saves its new location (row 24a).
8. **Only CropBox text is extracted.** Text drawn outside the CropBox (for example printer's marks) is invisible to selection and search. This matches what the reader shows and needs no change, but it is why anchors are normalized to the CropBox.
9. **Several non-URL actions are performed by PDFView, not by Sylvia.** Named NextPage and LastPage change the page, and ResetForm changes in-memory form values, with no delegate call (other relative named actions such as GoBack were not exercised). /GoToR, Find and GoToPage reach the delegate; JavaScript, SubmitForm and Print do nothing on iOS: no page change, no delegate call, no form change and nothing presented (`links-nonurl-actions.txt`, each outcome asserted; the "nothing presented" check has a control, `presented-ui-control.txt`). None opens anything or writes the file. ADR-0005 describes this as PDFKit's behaviour rather than as Sylvia's enforcement.
10. **PDFKit ignores /Next, and presents some /AA mouse-up actions as an annotation's own action.** For the shapes tested (row 18b): PDFKit never performed an action named by /Next, with the delegate in every chain and without it in every chain run without it (all but the https one, whose URL would open Safari). For a link without /A, it presents the /AA mouse-up action as the link's own when the /AA is {U} or {U, E}, and a tap then reaches `pdfViewWillClick(onLink:with:)`; without the delegate PDFKit's default opens that URL. With mouse-down also or only in the /AA ({D, U}, {U, D}, {D}) it presents nothing and a tap runs nothing. A separate widget whose /AA holds only mouse-up also has that action presented, but a real tap on the field starts editing instead of running it. No document, page, link or field trigger runs when a file is opened, its pages change, fields are set or typed into, or the file is closed. For the open action and page 0's open trigger of `actions-chained.pdf`, both GoTo actions to page index 2, this is seen as the view staying on page 0, with and without the delegate; `actions.pdf`'s open action and page-open action (canary URIs) reach neither the delegate nor the harness, with or without it. The interceptor of finding 1 therefore covers every presented action; a reader that left PDFKit's default in place would open the URL of such a link. Shapes not in the fixture are untested.
11. **A selection that ends with a line's last character is reported with the line break in its range.** `PDFSelection.range(at:on:)` covers the "\n" that follows the line while `string` stops before it. This is asserted on three lines (`labels-multipage.pdf` page index 3, the left column of `two-column.pdf` and the `/Rotate 90` page of `rotated.pdf`) for a range to the line's end, the last word, the whole line, a drag ending 6 pt past the line's end and two lines ending at a line's end, on every line of `text-layout.pdf`'s rotated-text page but the last, and at the end of a selection across two pages (row 8a); other pages and fixtures were not checked. An anchor built from the reported range quoted the text without the break but stored the break; restore then never matched (not found, or "Location needs review": the control in `LineEndSelectionTests`), so a highlight ending at a line's end (the last word of a line, a whole line or paragraph) would have been saved and drawn and then not restored on the next open. The previous rounds missed it because every sample ended mid-line. `PDFAnchorBuilder` now drops such trailing breaks (rows 8a and 22a, ADR-0005). The guard added with this fix, which required the segments' texts joined by "\n" to equal the quotation, was itself wrong for composed selections and has been replaced (finding 15). The product's capture must keep the trimming, the restore check of finding 15, `LineEndSelectionTests` and `ComposedSelectionTests`.
12. **Highlights on text drawn with a rotated text matrix are drawn wrongly.** Sylvia's anchor stores PDFKit's axis-aligned line boxes and draws the underline along each box's bottom edge, which is right only for upright text. On vertical lines the underline becomes a block over the first or last glyphs, on upside-down lines it runs along the tops of the glyphs, and a slanted line's box covers its neighbours (row 10c). PDFKit gives each line's reading direction (its first and last characters' boxes, checked in `TextLayoutTests`), so storing a per-line direction in the anchor would let the overlay put the underline on the baseline side of vertical and upside-down lines; slanted lines would need quadrilaterals, which PDFKit's selection API does not provide. This changes the proposed envelope, so it is a decision for contract consolidation and M3 (open question 7), not a change made in this spike.
13. **PDFKit presents outline actions like link actions.** `PDFOutline.action` gives an outline item's /A (a URI item as `PDFActionURL`); performed through `PDFView.perform(_:)` it reaches the delegate, and without the delegate PDFKit's default opens it (row 18b). The product's table of contents must navigate to an item's destination and send any other action through `LinkPolicy` with the delegate installed (open question 8).
14. **PDFKit orders page text by its own layout analysis.** Columns drawn in a scrambled order come out in reading order, but a column drawn from its bottom line up loses the break between its first two lines, and two downward lines come out in reverse reading order (row 13a). Anchors index the extracted text and still restore exactly; quotations and search see what PDFKit extracted. Whether real PDFs show this is open question 5.
15. **A selection's text is PDFKit's composition of its pieces, not the pieces joined by one separator.** For a selection made of several ranges (`PDFSelection.add`), PDFKit puts the pieces on one page next to each other with nothing between them, keeps the line break after a piece that ends at a line's end when another piece follows on its page, and joins pages with one "\n" (11 shapes, row 8b). The guard added for finding 11 assumed a "\n" between every two pieces: it refused 6 of those shapes, every one with two or more separate pieces on a page except where the expected "\n" was the kept line break, and it would have accepted a selection claiming the "\n"-joined text, which its ranges cannot give back. Found by the gate's review (R4-01), confirmed by a temporary probe test on the iOS 26.5 simulator (removed before any commit) and now covered by `ComposedSelectionTests`. The builder now checks a new anchor by restoring it with the same extraction, exactly as the resolver's exact step does (each range rebuilt into a selection on its page, combined in document order): every range must give back its segment's text and the combined text must be the quotation, or the anchor is refused (`quotationMismatch`). A relocated composed record is rebuilt the same way, so it is drawn and saved. The composed selections here are built in code; whether a person's touch selection in the reader can produce one was not checked (a product feature that combines selections, such as search hits, would). For the portable envelope this means `exact_text` cannot be derived from the segments by a join rule (open question 4).

No release-scope change is needed: the plan's PDF approach (PDFKit, Sylvia-side records, overlays, per-page status, no OCR) holds on the simulator. Finding 12 changes how a highlight is drawn on some layouts, not what Sylvia captures.

## Limits of this evidence

- All fixtures are generated by the spike: standard Helvetica, simple layouts. This round added generated rotated text matrices and scrambled and bottom-up stream order (row 13a). Real-world PDFs with embedded or CID fonts, ligatures, right-to-left or vertical scripts, tagged structure or real-world column layouts were not tested. A small public-domain real-world PDF corpus should be added before the reading work of M3 relies on extraction quality (open question 5).
- On-screen checks are simulator screen captures. At fit-to-width zoom the underline is under 1 pt and antialiased; the pixel thresholds were set for that (at least 20 % of underline-band pixels within 24 of #8A5410; fill band at least 30 % #F1E4C8 and at most 5 % white). Offscreen renders at 2 px/pt match the tokens exactly.
- `drawHierarchy` snapshots of a PDFView do not include PDFKit's tiles on the simulator (blank page), so live-view checks use XCUITest screen captures and a draw-call record instead.
- Simulated touches (XCUITest coordinates) are not a finger: the handle-drag offsets in row 2a may differ on a device.
- The UI tests type a digit into each form field. Letters were rewritten by the keyboard's autocorrection when editing ended, and not the same way every run ("Secondy" became "Secondhand" or "Seconds"); turning autocorrection off in the simulator's keyboard preferences did not stop it. A digit after a word was left alone in every run. On a newly created simulator the keyboard first shows its "slide to type" introduction; the test dismisses it and says so in its evidence.
- Cross-OS evidence comes from two simulator runtimes (iOS 26.5 and 27.0) on the build Mac, not from an OS update on a device. PDFKit extracted the text of every page of the ten fixtures that open (32 pages) identically on both, and the other two open on neither (row 24), so the relocation path ran on a simulated change (row 24a).
- Composed selections (row 8b) are built in code with `PDFSelection.add`; how PDFKit composes the text of other shapes (for example pieces on three or more pages) was not checked, which is why capture checks each anchor by restoring it rather than by a join rule.
- The line-end behaviour (row 8a) is asserted on the lines and shapes listed there; other pages and fixtures were not checked, and a drag that ends further past a line's end can select other text (recorded on `two-column.pdf`).
- Mouse enter and exit (/AA /E and /X) need a pointer, which XCUITest cannot move on iOS; checklist step 8 asks for an iPad with a trackpad or mouse.
- The action findings hold for the shapes in the fixtures; PDFKit's rule for which /AA actions it presents was not derived beyond them.
- The accessibility audit and element checks are not VoiceOver: they do not show that VoiceOver users can make a selection.
- The Thread Sanitizer checks the overlay's own data; it cannot see inside PDFKit's tile renderer beyond the calls into Sylvia's code.
- Timing numbers come from the simulator on an M5 Max while other jobs shared it (load recorded in `large-pdf-timing.txt` and `ci-clean-run.log`); they say nothing about the plan's device budget.
- Dark appearance: PDF pages are drawn on white in both appearances, so the light Ochre values are used. Whether Sylvia should offer a darkened page in Night mode, and how highlights would look on it, was not examined (design question for G0.6).
