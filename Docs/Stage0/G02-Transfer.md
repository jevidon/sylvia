# G0.2 Transfer security and background: report

Part 1: pairing, the Mac source service, the transfer contracts and host fault tests. Part 2: the iOS background transfer client (background `URLSession` with the pinned identity, launch reconciliation, the iOS harness app) and what App Transport Security allows.

- **Dates:** part 1 on 7 October 2026; part 2 on 7 and 12 October 2026; round 1 and round 2 review fixes on 12 October 2026; round 3 review fixes on 13 October 2026 (NZDT). **Branch:** `m0-g02-transfer` (squash-merged into `m0-integrate` at M0 integration); round 3 on `m0-int-minors-g02-transfer`, from the integration commit `b354dc7`.
- **Decisions:** ADR-0008 (pairing and transport security), ADR-0009 (transfer protocol, manifests and resumability), both Proposed. Part 2 added sections "iOS client: trust in background sessions" and "App Transport Security" to ADR-0008 and "iOS background client" to ADR-0009.
- **Code:** `Spikes/G02-Transfer/TransferKit` (iOS and macOS: protocol core `SylviaTransferCore`, foreground client `SylviaTransferClient`, background client `SylviaBackgroundTransfer`), `Spikes/G02-Transfer/SourceService` (macOS: source service library, `sylvia-source`, `sylvia-fetch`, the test-only `sylvia-test-source`, host tests), `Spikes/G02-Transfer/iOS` (XcodeGen project: harness app `G02TransferHarness`, bundle ID `com.jevidon.sylvia.spike.transfer`; hosted tests; XCUITests; the never-shipped ATS probe app `G02TransferATSVariant`), `Spikes/G02-Transfer/MacIdentityProbe` (XcodeGen project, round 1: a signed macOS app hosting a test of the Mac identity store in the data protection keychain; never shipped).
- **Contracts:** `Contracts/openapi/source-service.v1.yaml`; schemas and fixtures for `transfer-manifest`, `pairing-payload`, `pair-request`, `pair-response`, `capabilities`, `catalog-page`, `device-inbox-page`, `receipt`, `error` (v1). Part 2 changed no contract.
- **How to reproduce:** `Scripts/fixtures/fetch.sh`, then `Scripts/ci.sh g02-transfer` (`Scripts/ci.d/40-g02-transfer.sh`; it generates the 5 GiB file and the simulator files itself). Per-step logs: `Docs/Stage0/evidence/G02-Transfer/ci/`. Clean run after the round 3 fixes, started after every build product of this workstream was deleted and this job's simulator was recreated, as `SYLVIA_G02_SIMULATOR=Sylvia-M0-minors-g02-transfer Scripts/ci.sh contracts g02-transfer`: `evidence/G02-Transfer/ci-clean-run.log` (it names its commit, `41b93e7`, and the load average, 132 at the start and 26 at the end; the contracts drop-in passes; 21 of the G0.2 drop-in's 22 steps pass and `mac-identity-signed` is listed as not run because this Mac cannot sign for the team; host and simulator). Only documents and evidence summaries changed after it. Two earlier clean runs failed one step each and are kept: `review/round2-first-clean-run-failed.log` (finding 19) and `review/round3-first-clean-run-failed.log` (finding 22).
- **Environments:** **host** = macOS 26.6.2 (25G83), Apple M5 Max, Xcode 27.0 (27A266a), Swift 6.4. **simulator** = iPhone 17, iOS 26.5 (23F77), simulator `Sylvia-M0-g02-transfer` (round 3: `Sylvia-M0-minors-g02-transfer`, same device type and runtime); the simulator shares the Mac's network stack, so its "LAN" and "Tailscale" connections never leave the Mac. **device** = nothing was run on a device; every device result below is pending.

Paths below are relative to `Docs/Stage0/evidence/G02-Transfer/` unless they start with a repository folder.

## Findings that change the plan's scope or approach

1. **Background `URLSession` works with the SPKI-pinned self-signed identity for local addresses (simulator).** For 127.0.0.1, ::1, `localhost`, a LAN IPv4 address and a `.local` name, background download tasks connect, the system sends each new connection's server-trust challenge to the app's task-level delegate, the pin is checked there and nothing else overrides trust. This answers part 1's open question on the simulator. A device must confirm it (checklist steps 2, 13).
2. **Tailscale addresses and MagicDNS names fail under App Transport Security (negative gate result, simulator).** For a 100.64.0.0/10 address and a `*.ts.net` name ATS applied in full on the iOS 26.5 simulator: after the delegate accepts the pinned key, ATS still requires a certificate that default trust accepts, and the connection fails (-1200). A phone must confirm it (checklist steps 6 and 23). `NSAllowsLocalNetworking` does not cover these hosts. Plan 15.1 and XFER-04 promise an explicitly entered Tailscale address or MagicDNS name, so with the current design and no ATS key that promise cannot be met. Section 15.2 asks for a changed approach before release promises. Measured options (ADR-0008): (a) a scoped `NSExceptionDomains` entry for `ts.net` and `100.64.0.0/10` with `NSExceptionAllowsInsecureHTTPLoads` (works in the probe build; it also allows cleartext to those hosts, so the client must refuse non-HTTPS itself; plan 14.3 allows a narrow validated exception, the security reviewer decides); (b) a publicly trusted certificate for the MagicDNS name (`tailscale cert`), not tested because it publishes the machine name in Certificate Transparency logs and needs the owner's decision; (c) drop the Tailscale route from v1 and change XFER-04. The spike recommends (a) for v1, subject to the security review; the harness stays without any ATS key until that decision.
3. **ATS gives no protection on the LAN on the iOS 26.5 simulator.** Cleartext HTTP to loopback, private addresses and `.local` names loads with no ATS key at all (`ats/ats-probe-none.log`; simulator only: checklist step 23 runs the same probe on a phone, round 3 finding R3-06). The client builds only `https` URLs from endpoints (`PairingPayload.Endpoint.baseURL`) and the pin is the only trust decision; the product must keep that as an explicit rule and test, not rely on ATS. (iOS 17 extended ATS to IP addresses and added CIDR keys to `NSExceptionDomains`, per Apple's iOS 17 release notes as quoted by Apple DTS in developer forum threads 731217 and 747421; private and loopback addresses were still treated as local here.)
4. **Background progress depends on when iOS runs the app, and on where a task was created (simulator).** In both relaunch runs (`simulator/relaunch-*.log`, raw event lines): after the kill, tasks created in the foreground kept running in the system's daemon; about 4 s later the system relaunched the app in the background once, delivered the finished parts, and the app answered the trust challenges of the foreground-created tasks that were still waiting for a connection (keep-alive run: parts 4 and 5, `app_state=background_relaunch`). The two tasks the app created during that background relaunch (parts 6 and 7 in the keep-alive run) opened no connection in the following 59 s; they connected only when the app was next opened. The system also did not wake the app again in those 59 s to deliver parts 4 and 5, which had finished. Apple documents that transfers started while the app is in the background are treated as discretionary ("Downloading files in the background"), which matches what was seen; the simulator cannot tell it apart from a system that waits for the app before a handshake. Consequences: until checklist step 13 shows otherwise, the honest promise is "continues in the background when iOS allows it and resumes from verified parts whenever Sylvia runs" (plan I-10), not uninterrupted completion; and a design that tops up a small window of tasks from background callbacks makes little progress in the background. Options to measure on the device: create tasks for more (or all) remaining parts while the app is in the foreground, which puts more requests carrying the bearer token into the daemon at once (plan 6.4 asks for bounded queued parts), or the certificate alternative of finding 2, which does not change discretionary scheduling.
5. **Download tasks store the body before the app sees the head, and hold the token.** The system writes the whole response to its own file before `didFinishDownloadingTo`; the head is checked before the file is opened, and an over-long body is cancelled only while the app runs. Each outstanding task keeps its `Authorization` header inside the system's transfer daemon until it ends; the four-task window bounds that per job, and revocation or pause cancels the tasks (ADR-0008, ADR-0009). The number of jobs downloading at once is not bounded in the spike, so N jobs started together can hold 4N requests (round 3, finding R3-05; open question 3).
6. **Review of the earlier part-2 work found one defect, now fixed.** Launch reconciliation could adopt a task whose completion the delegate had already received (`allTasks` and the delegate's events are not ordered); that task would have held its part's slot and the job would never finish. Fixed in `BackgroundTransferCoordinator` (`completedBeforeReconciliation`); the regression test `taskCompletedBeforeReconciliationIsNotAdopted` fails without the fix (`review/completed-task-adopted-before-fix.log`: job stuck in `downloading`) and passes with it (`background-host/completed-before-reconciliation.log`). Two smaller problems were fixed in the CI drop-in and project: the trust guard failed on Swift comments that name an ATS key, and the hosted test bundles linked the TransferKit products a second time, which made Xcode print dependency warnings.
7. **"Stale or expired" credentials take the revocation path.** Tokens have no expiry in this protocol (ADR-0008); a token the Mac no longer accepts answers 401 and the job pauses with `reauthentication_required`, keeping verified bytes. A missing token (deleted Keychain item) does the same. If tokens gain an expiry, it is the same path.
8. **A slow first manifest request would have timed out on the phone** (part 1). The protocol answers 503 `preparing` with `Retry-After` after 10 seconds and the client polls; the background client does the same before it creates a job.
9. **Clones need the source and the state directory on the same APFS volume** (part 1). Otherwise preparation is a full copy (`fcopyfile`), which costs space and time; the companion must account for it.
10. **The macOS identity key's protection class depends on code signing** (part 1). Unsigned tools use the login keychain; the signed companion must be re-checked.
11. **Part 1 review fixes** (details in `PROGRESS.md`): the approval cut off by the idle limit (`review/idle-limit-cut-off-approval-before-fix.log`), a race between version invalidation and opening the snapshot, a check-then-use race when cloning, and the slow-preparation timeout. Each has a test.
12. **The CLI's "imported into Sylvia" receipt comes from a stand-in, and so does the harness's** (`StubImporter`). The handoff is exactly once and the receipts are idempotent, but the meaning of "imported" must be re-tested with the real importer (M1).
13. **One-Mac and simulator address tests do not prove network paths.** The simulator shares the Mac's network stack, so LAN, Tailscale and MagicDNS traffic never leaves the Mac, and there is no local-network permission prompt. Cross-device paths, Wi-Fi loss, Mac sleep and the permission prompt are device steps.
14. **Round 1 review: stopping the Mac source while a phone connected could crash it (blocker, fixed).** Connections wrapped for async use but released before being served trapped the process in NIO; the host suite crashed in 2 of 7 review runs, so the earlier "all steps pass from a clean state" was not reproducible. Each connection is now wrapped and handed to its serving task in one step (ADR-0009, "Connection lifecycle"); a 200-stop stress test trapped on the old code and passes now (`review/stop-*.log`), and the host suite was repeated (`review/sourceservice-repeat.log`). The test cleanups are now awaited instead of being left to a detached task.
15. **Round 1 review: before the first unlock the client would have acted on empty stores (fixed).** Unreadable `sources.json`, import ledger and job records were read as empty; reconciliation would have cancelled every outstanding background task and a later pairing or import would have overwritten the real files. Launch is now deferred until every store is readable, and unreadable stores refuse writes (ADR-0008, ADR-0009). (The round 1 fix also waited for `isProtectedDataAvailable`; round 2 removed that, finding 18.) The ADR's earlier description (a `device_locked` pause) described a state that cannot occur and was corrected.
16. **Round 1 review: a full phone was reported as an unreachable Mac (fixed).** Local move and write failures were classified as transport errors: four 16 MiB re-downloads, then "Make sure the Mac is awake". A full disk now pauses at once with `insufficient_space`, other local errors end in `storage_unavailable`, and jobs reserve the remaining bytes plus one part for each task the window allows before any request (plan 15.4). The full-volume host test also found that a stored `URL` caches the free-space figure it read first; the client now asks through a fresh URL each time.
17. **Round 1 review, smaller fixes.** The captured-payload check no longer passes on files left from an earlier run (R1-02); the simulator background script no longer leaves plain-HTTP control servers listening on the loopback, LAN and Tailscale addresses (they were started in a subshell, so their PIDs were lost; R1-03); ADR-0009 now says that the background client writes a part into its own unverified region of `staging.bin` before its digest decides (R1-06); the test source waits for SIGTERM without leaking a continuation (R1-08); device checklist steps 1 and 3 can now be run as written (a Keychain-only test command; a pre-pairing address field in the harness; R1-09); paste and link pairing run on the simulator (R1-10); the Mac identity store falls back to the login keychain only when asked to (R1-11); the 5 GiB numbers are described as one run's values (R1-07). A test that compared request counts right after stopping a coordinator could count a request still in flight; it now waits for that request first (`changedSourceKeyPausesBeforeAnyRequestIsSent`, failed once in this round's runs). The new paste test failed once in a clean run after falling back to Command-V when the edit menu did not appear (a code in the field, no connection to the source); the fallback was removed, the test retries the edit menu and requires the field to hold exactly the code, and three runs then passed (`review/pairing-entry-repeat.log`). The relaunch UI test failed once because the new pre-pairing address row pushed "Pair" below the fold and the test only scrolled down; it now looks up and down.
18. **Round 2 review: the round 1 fix deferred every launch while a phone was locked (major, fixed).** It waited for `UIApplication.isProtectedDataAvailable`, which reports class A protection and is false whenever a phone with a passcode is locked, also after its first unlock. A background relaunch while locked would then have created no session, so finished parts and trust challenges would not have been delivered, no new part task created and the system's completion handler never called, until the next unlock; device steps 8 and 13 would have measured a stall caused by the app. The client now defers only when a store file exists and cannot be read (what class C files report before the first unlock), logs `isProtectedDataAvailable` without using it, releases a background relaunch's completion handler when it defers, and keeps the unlock notification as a retry trigger. A host test with protected data reported unavailable and readable stores failed on the old code and passes now (`review/round2-before-fix.log`, `background-host/locked-after-first-unlock.log`).
19. **Round 2 review, smaller fixes.** R2-02: a background download the system could not store (the task ends with an error; for a background session the system writes the body before the app sees it) was still reported as a network failure; it is now classified as this phone's storage, and the reservation runs before every request (rows under 15.4). The first clean run after these fixes failed: the per-request reservation read the volume's "available for important usage" capacity with the coordinator's lock held, a request to the system that took about 20 ms idle on this host and longer with the disk busy, and the 5 GiB test caught `jobViews()` waiting 425 ms (`review/round2-first-clean-run-failed.log`); free space is now read before the lock is taken. R2-03: a denied local network permission was reported as an unreachable Mac although a code comment said the iOS client checked it; the client now checks the connection path's unsatisfied reason after a network failure and gives the Settings next step (pairing, address check, catalog and inbox calls, paused transfers); the denial itself needs a device (steps 4, 18). R2-04: the final full-file SHA-256 ran under the lock the transfer screen polls; it now runs on its own queue (5 GiB row). R2-05: ADR-0008 now records that another app can claim the `sylvia://` scheme and receive the invitation, recommends in-app scanning or pasting, and puts it in the security review's scope (step 12). R2-06: checklist step 1 expects the Swift Testing result line, code signing for the team is a prerequisite of every phone step, and step 8 uses the device inbox, which the harness now reads (round 2 gate gap; inbox row). Two host tests could race in this round's repeat runs and were tightened without weakening what they check: the 5 GiB test compared the parts the relaunch kept with the stopped coordinator's log after a fixed 500 ms and once read 161 where 162 were journalled (it now waits until the stopped coordinator has gone quiet), and the local-network test sometimes moved the Mac's address before part 3 was requested (the tests now wait for the part 3 request, not for a state that is also seen just before it).
20. **A part commit still holds the coordinator's lock.** Copying and hashing one 16 MiB part into staging, with its write barrier, happens under the lock in `didFinishDownloadingTo`; each `part_verified` event now logs its `commit_ms`. On the host: median 11 ms, at most 19 ms in the round 3 clean run at a load average of about 100 (`faults/large-5GiB-background-client.log`), at most 50 ms in the round 2 repeat runs (`review/round2-5gib-repeat.log`) and 48 ms in the round 3 ones (`review/round3-5gib-repeat.log`); in an earlier repeat run, before `commit_ms` existed, one `jobViews()` call waited 180 ms. Since round 3 the import's file work, which also holds the lock, logs its time too (`import_ms`: 4 ms in the clean run). Not a review finding; an old phone may take several times longer per part, so checklist step 11 records `commit_ms` and any hang, and ADR-0009 lists moving the commit off the lock.

21. **Round 3 review fixes (all minor).** R3-01: launch reconciliation, which runs at every launch including each background relaunch, created its part requests without the plan 15.4 reservation that every other request passes, although this report and ADR-0009 said "before every request". It now reads free space before taking the lock and pauses a job that lacks the space before its launch requests; the host test failed on the round 2 code (`review/round3-before-fix.log`) and passes now (`background-host/relaunch-low-space.log`). R3-02: device step 10 expected the `access_revoked` message, but the Mac answers a revoked token with 401 and the phone pauses with `reauthentication_required`, as ADR-0008 and the host and simulator evidence say; the step now expects that text. R3-03: step 13 sent the source's output into `source.log`, so the person could not see the code or compare the fingerprint before approving, and the file held the invitation secret; the checklist now has one "logging source" command line (output on the terminal and, redacted line by line, in `source.log`) for every step that needs a request log, and CI runs it on a pseudo-terminal (`cli-logging-source-recipe.log`). R3-04: ADR-0009 said holding the background-events completion keeps iOS from suspending the app during the full-file check; it does not, and the ADR, the code comments and a new device step 22 now say what is and is not known.
