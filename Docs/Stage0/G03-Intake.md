## Fallback route

When the share extension cannot finish safely it shows **"Not received. Nothing was saved to Sylvia."**, the reason, and numbered alternatives. It never shows "Received" without a committed manifest. For a provider that cannot supply a durable file (it offers only a link or a temporary preview, returns an error, deletes the file before the copy, or makes no progress for 60 s before delivering), the route is:

1. **Save to Files, then import in Sylvia.** In the app you shared from, choose Save to Files (or Export, or Open in) and save to On My iPhone or iCloud Drive. Open Sylvia, choose Import, then Files, and pick the file. If it shows a cloud icon, wait until it has downloaded.
2. **Send it from your Mac.** Put the file on the Mac and add it in Sylvia for Mac. Send it over the local network, or choose Prepare for cable transfer and copy the bundle in Finder (Files, then Sylvia). Open Sylvia and import it from the Inbox.

When the provider offers a folder (an EPUB stored unpacked as a package directory) the reason says so ("offered this book as a folder ... not as a single file") and only the Mac route is offered, because whether Sylvia's own Files import accepts EPUB folders is an open product decision. When space is short, the Mac route comes first and the message names the shortfall. Over the per-file limit, no route is offered, because the same limit applies to every route. The strings are Stage 0 copy; plan 4.4.6 has no share-extension entries yet (finding F7).

## Findings that change the plan's scope or approach

**F1. Neither ZIP library can be trusted to detect a partial copy.** On copies of a 4.5 GiB ZIP64 archive cut by 1, 22 or 98 bytes, or cut in half, upstream ZIPFoundation 0.9.20 scanned for 43-75 s and then opened each one without error, as an archive with no entries. That is a false acceptance: for the 22-byte, 98-byte and half cuts, payload bytes happened to contain the end-record signature; for the 1-byte cut, the library used the incomplete real end record. Readium's fork 3.0.1 did not finish within the 120 s watchdog on any of the four. On a 64 MiB archive, both libraries rejected the same cuts: upstream in 1.0-3.7 s, the fork in 39-87 s. Python `zipfile` rejected every cut (`zip-eval.log`, host, clean run). Consequence: plan 8.5's "use an audited archive implementation" is not enough by itself. Sylvia parses the archive's structure strictly with bounded reads before any library sees it (`PackStructure`). That check rejects every evaluated partial copy in constant time. The price is that `.sylviapack` is deliberately narrower than ZIP: only Sylvia's writer is expected to produce it. The same check should guard `.sylviabackup` (ADR-0012).

**F2. The brief's default archive candidate cannot be used alongside Readium.** SwiftPM gives `weichsel/ZIPFoundation` and `readium/ZIPFoundation` the same package identity (`zipfoundation`). Readium 3.11.0 requires the fork at 3.0.1..<4.0.0, so the resolver refuses upstream 0.9.20 in the same graph (`zip-dependency-probe.log`, `zip-eval.log` section 1). On ZIP64 above 4 GiB the two behave the same: each wrote and read a 4.5 GiB archive, cross-checked by Python `zipfile` and Info-ZIP, with a peak footprint of at most 5.9 MiB (`zip-eval.log`). ADR-0010 therefore picks the fork, `readium/ZIPFoundation` 3.0.1 (MIT), which is already in the lock. This adds no new package. Both facts are now checked on every CI run (step 8).

**F3. Markdown file types.** On the iOS 26.5 simulator, only `.md` maps to `net.daringfireball.markdown`. `.markdown` and `.mdown` resolve to dynamic types, even when the app imports the type with those extensions (`simulator-markdown-type-import.log`, `sim-app-tests.log`). Intake maps the Markdown extensions explicitly. Providers that label Markdown as plain text are still accepted through `public.plain-text`. Device behaviour is unverified.

**F4. Extension memory: bounded, but the limit is undocumented and unmeasured.** The copy routine's footprint does not grow with file size: 4.6 MiB on the host for 4.5 GiB. In the real extension on the simulator, the footprint rises over the first 2 GiB copied (the per-GiB series goes 26, 40, 45 MiB) and then stays flat at 45 MiB to the end of an 8 GiB file; the 8 GiB + 1 run's peak, 47.9 MB, is 14.9 MB above the 64 MiB run's and 278,504 bytes below the 4 GiB + 1 run's. The cause of the early rise was not investigated; it does not continue. Apple documents no number. Its App Extension Programming Guide says only that "Memory limits for running app extensions are significantly lower than the memory limits imposed on a foreground app" (https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionCreation.html). On the simulator, both `os_proc_available_memory()` and `task_vm_info.limit_bytes_remaining` report 0, meaning no limit is enforced, so the comparison has to be made on a device (checklist steps 14-15). Until it is, the plan should not assume any particular margin below the limit.

**F5. What the app can and cannot know about Finder's copy.** Finder's file-sharing copy into Documents is made by the system. Nothing shows it takes part in file coordination, so `NSFileCoordinator` cannot be used to wait for it, and an unchanged size or modification date proves nothing (plan 8.5). The app can prove that the bytes it holds form a complete, valid pack. It takes an APFS clone of the file inside a coordinated read and validates the clone. A copy still in progress fails, because the end record is not yet at the end of the file. The host test of a writer still copying showed exactly that: rejected at half, accepted after completion. A test with a coordinated writer showed the coordinated snapshot waiting for it (`host-intakekit-tests.log`). Consequence for 16.4: the UI tells the user to wait for Finder, then import. A rejected partial copy should be described as "still copying or incomplete; wait for Finder and try again", not as corrupt. After a durable import the bundle is removed from Documents, but only if it is still the file that was validated (device, inode, size and modification time unchanged), so a newer copy Finder wrote meanwhile is kept. The device check of a cancelled Finder copy is pending (step 22).

**F6. `LSSupportsOpeningDocumentsInPlace` = NO, and what it costs.** Sylvia never edits a user's document in place (I-08), so the key is declared false. With that setting, Documents does not appear in the Files app; it is visible only in Finder's file-sharing pane. Open-in copies arrive in `Documents/Inbox`: on the simulator, a file opened through the system's document handling arrived there and was imported, and the copy was removed whatever the outcome (`sim-open-in.log`). Found in review round 1: with NO, the simulator's Files app lists **no app** under "Open With" for an EPUB ("No Apps Available", in every run, including the clean run's `sim-app-tests.log`); in an experimental build with the key YES and nothing else changed, it lists Sylvia, and the opened file is imported (`simulator-open-with-in-place-experiment.log`). Sharing from Files into the extension works with NO. The spike keeps NO; the choice is now a product-owner question with a visible cost on both sides (open question 2). Plan 16.4's "choose Files -> Sylvia" refers to Finder's Files tab, which works either way.

**F7. Share-extension status strings are missing from the vocabulary.** Plan 4.4.6 has no entries for the extension's "Received" and "Not received" states. Those states must stay distinct from "Saved" and "Ready" (I-03, I-04). Owner: G0.6 design package.

**F8. A crash between the commit rename and the "Received" message.** The handoff is complete and the app imports it, but the user saw no confirmation. A retry is flagged as a duplicate (`needs_review`) rather than creating a second book. This is the safe direction for I-03; product copy for the Inbox should say "arrived from Share" so the user is not surprised.

**F9. Per-kind limits inside a bundle.** Plan 8.3's "1 GiB EPUB expanded content" is applied in the pack as a 1 GiB limit on the EPUB file. The EPUB's own expansion is the reading adapter's check (G0.1). The other limits use the plan's numbers. Text, cover and total-bundle limits, and the aggregate expansion allowance (16 MiB), are spike proposals for the product owner (ADR-0010 open items).

**F10. Abandoned handoffs.** A manifest-less handoff is removed after 1 hour without modification. Before deletion, it is claimed by a rename, so a slow but live extension cannot commit into a directory that is being deleted. An extension that waits more than an hour on a provider loses its partial copy and shows the fallback: a retry, never a false "Received". The product owner should approve the 1-hour value and the 7-day retention of rejected handoffs.

**F11. Late import, seen once.** Before scans were instrumented, one UI run imported a 4 GiB handoff about 5 minutes after the share (`simulator-late-import-observation.log`). The bytes were intact and imported once; the cause is unknown. In every instrumented run since, the import followed the share within seconds, including the clean run. Kept open; the device runs record scan timing.

**F12. Automation scope.** The end-to-end UI tests share from the harness app's own share sheet and from the Files app's On My iPhone provider (in place, through the file provider), and the system's open-in hand-off is driven with `simctl openurl`. On the iOS 26.5 simulator the Files app offered the extension only after the harness had been launched once since installation; on a fresh install before that, it offered no third-party extension at all (`simulator-files-app-observation.log`), so the test launches the harness first. Not automated, because the simulator has no such provider or cannot reproduce the condition: Safari downloads, Mail attachments before download, Books, iCloud placeholders, AirDrop, data protection and the extension memory limit. They are in the device checklist, not inferred.

**F13. The first stall detector cut off providers that were still sending.** The Progress that `loadFileRepresentation` returns wraps the provider's own Progress as a child: while the provider works only `fractionCompleted` moves, and `completedUnitCount` stays 0 until delivery (measured on macOS Foundation). The first implementation watched the count, so any provider that took longer than the 60 s stall limit to deliver, such as an iCloud download of a large file, would have been cancelled with a "stopped sending" fallback while it was still sending. Run against that detector, the new host test of a provider that reports progress for six times the stall limit fails at the first stall interval (`host-stall-detector-before-fix.log`); the detector now treats any change of count, total or fraction as progress and the test passes (`host-intakekit-tests.log`, `sim-intakekit-tests.log`). Whether an iCloud download reports its progress through this Progress on a phone is checklist step 18, which needs a placeholder that takes longer than 60 s to download.

**F14. Imported bundles leave Documents; staging-class data leaves backups.** A bundle in Documents is a transport copy (4.5 GiB in the cable flow). Once its job is durably staged, the app removes it (plan 16.4 allows cleanup "after successful import"), so it is neither kept twice nor backed up. A rejected or partial bundle stays until the user removes it, backup-eligible like anything the user puts in Documents. The App Group handoff inbox is staging class (plan 17.1) and is now excluded from device backup by the extension (which can run before the app) and again by the app; the layout audit checks both exclusions. An APFS clone copies its source's attributes, so a staged clone may keep the source's data-protection class; the in-app test records which class a clone gets, and the device result decides whether the importer must set it (checklist step 24).
