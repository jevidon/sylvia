## Fallback route

When the share extension cannot finish safely it shows **"Not received. Nothing was saved to Sylvia."**, the reason, and numbered alternatives. It never shows "Received" without a committed manifest. For a provider that cannot supply a durable file (it offers only a link or a temporary preview, returns an error, deletes the file before the copy, or makes no progress for 60 s before delivering), the route is:

1. **Save to Files, then import in Sylvia.** In the app you shared from, choose Save to Files (or Export, or Open in) and save to On My iPhone or iCloud Drive. Open Sylvia, choose Import, then Files, and pick the file. If it shows a cloud icon, wait until it has downloaded.
2. **Send it from your Mac.** Put the file on the Mac and add it in Sylvia for Mac. Send it over the local network, or choose Prepare for cable transfer and copy the bundle in Finder (Files, then Sylvia). Open Sylvia and import it from the Inbox.

When the provider offers a folder (an EPUB stored unpacked as a package directory) the reason says so ("offered this book as a folder ... not as a single file") and only the Mac route is offered, because whether Sylvia's own Files import accepts EPUB folders is an open product decision. When space is short, the Mac route comes first and the message names the shortfall. Over the per-file limit, no route is offered, because the same limit applies to every route. When the shared files' names are too long to record in one share (only names and type identifiers near their limits, full of characters that JSON writes as escapes, come near the app's 256 KiB limit for `handoff.json`), the reason says so ("The names of the shared files are too long to record in one share. Share fewer files at a time.") and both routes are offered (review R4-02; F19). A provider that delivers at the moment the 60 s stall limit is reached is received, not cut off (review R4-04). The strings are Stage 0 copy; plan 4.4.6 has no share-extension entries yet (finding F7).

Cancel leads to the same screen, with the reason "The copy was cancelled.", in every phase: while the sharing app is still delivering the file (an iCloud download, a Mail attachment being fetched), while a coordinated read waits for another writer, during the copy, and after the last byte until the commit starts (review R2-01; G1, G9). The user is never left with a Cancel button that does nothing.

Step 1's import exists in the harness as **Import from Files**: the system document picker, opening the chosen file in place (security-scoped access, read inside a coordinated read, never modified), then the same single-file importer and journal as open-in and the drop area. It is exercised on the simulator from On My iPhone, where the picked file's identity and bytes are the same before and after each import (`sim-app-tests.log`, T08; review R3-05); picking an iCloud file that is not downloaded yet is device checklist step 32.

## Findings that change the plan's scope or approach

**F1. Neither ZIP library can be trusted to detect a partial copy.** On copies of a 4.5 GiB ZIP64 archive cut by 1, 22 or 98 bytes, or cut in half, upstream ZIPFoundation 0.9.20 scanned for 45-78 s and then opened each one without error, as an archive with no entries (50-72 s in the round 3 clean run, 48-72 s in round 2, 43-75 s in round 1). That is a false acceptance: for the 22-byte, 98-byte and half cuts, payload bytes happened to contain the end-record signature; for the 1-byte cut, the library used the incomplete real end record. Readium's fork 3.0.1 did not finish within the 120 s watchdog on any of the four. On a 64 MiB archive, both libraries rejected the same cuts: upstream in 1.0-2.5 s, the fork in 42-99 s. Python `zipfile` rejected every cut (`zip-eval.log`, host, clean run; timings under the load recorded in `ci-clean-run.log`, indicative only). Consequence: plan 8.5's "use an audited archive implementation" is not enough by itself. Sylvia parses the archive's structure strictly with bounded reads before any library sees it (`PackStructure`). That check rejects every evaluated partial copy in constant time. The price is that `.sylviapack` is deliberately narrower than ZIP: only Sylvia's writer is expected to produce it. The same check should guard `.sylviabackup` (ADR-0012).

**F2. The brief's default archive candidate cannot be used alongside Readium.** SwiftPM gives `weichsel/ZIPFoundation` and `readium/ZIPFoundation` the same package identity (`zipfoundation`). Readium 3.11.0 requires the fork at 3.0.1..<4.0.0, so the resolver refuses upstream 0.9.20 in the same graph (`zip-dependency-probe.log`, `zip-eval.log` section 1). On ZIP64 above 4 GiB the two behave the same: each wrote and read a 4.5 GiB archive, cross-checked by Python `zipfile` and Info-ZIP, with a peak footprint of at most 5.9 MiB (`zip-eval.log`). ADR-0010 therefore picks the fork, `readium/ZIPFoundation` 3.0.1 (MIT), which is already in the lock. This adds no new package. Both facts are now checked on every CI run (step 8).

**F3. Markdown file types.** On the iOS 26.5 simulator, only `.md` maps to `net.daringfireball.markdown`. `.markdown` and `.mdown` resolve to dynamic types, even when the app imports the type with those extensions (`simulator-markdown-type-import.log`, `sim-app-tests.log`). Intake maps the Markdown extensions explicitly. Providers that label Markdown as plain text are still accepted through `public.plain-text`. Device behaviour is unverified.

**F4. Extension memory: bounded, but the limit is undocumented and unmeasured.** The copy routine's footprint does not grow with file size: 4.6 MiB on the host for 4.5 GiB. In the real extension on the simulator, the footprint rises over the first 2 GiB copied (the per-GiB series goes 26, 33, 45 MiB) and then stays flat at 45 MiB to the end of an 8 GiB file; the 8 GiB + 1 run's peak, 49.1 MB, is 17.6 MB above the 64 MiB run's and 1,015,808 bytes above the 4 GiB + 1 run's (638,952 bytes above it in the round 3 clean run, 1,130,496 in round 2, 278,504 bytes below it in round 1: the plateau moves by up to about a megabyte between runs, not with the file size). The cause of the early rise was not investigated; it does not continue. Apple documents no number. Its App Extension Programming Guide says only that "Memory limits for running app extensions are significantly lower than the memory limits imposed on a foreground app" (https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionCreation.html). On the simulator, both `os_proc_available_memory()` and `task_vm_info.limit_bytes_remaining` report 0, meaning no limit is enforced, so the comparison has to be made on a device (checklist steps 14-15). Until it is, the plan should not assume any particular margin below the limit.

**F5. What the app can and cannot know about Finder's copy.** Finder's file-sharing copy into Documents is made by the system. Nothing shows it takes part in file coordination, so `NSFileCoordinator` cannot be used to wait for it, and an unchanged size or modification date proves nothing (plan 8.5). The app can prove that the bytes it holds form a complete, valid pack. It takes an APFS clone of the file inside a coordinated read and validates the clone. A copy still in progress fails, because the end record is not yet at the end of the file. The host test of a writer still copying showed exactly that: rejected at half, accepted after completion. A test with a coordinated writer showed the coordinated snapshot waiting for it (`host-intakekit-tests.log`). Consequence for 16.4: the UI tells the user to wait for Finder, then import. A rejected partial copy should be described as "still copying or incomplete; wait for Finder and try again", not as corrupt. After a durable import the bundle is removed from Documents, but only if it is still the file that was validated (device, inode, size and modification time unchanged), so a newer copy Finder wrote meanwhile is kept. The device check of a cancelled Finder copy is pending (step 22). A raw file, which has no manifest, cannot be proved complete at all (F15).

**F6. `LSSupportsOpeningDocumentsInPlace` = NO, and what it costs.** Sylvia never edits a user's document in place (I-08), so the key is declared false. With that setting, Documents does not appear in the Files app; it is visible only in Finder's file-sharing pane. Open-in copies arrive in `Documents/Inbox`: on the simulator, a file opened through the system's document handling arrived there and was imported, and the copy was removed whatever the outcome (`sim-open-in.log`). Found in review round 1: with NO, the simulator's Files app lists **no app** under "Open With" for an EPUB ("No Apps Available", in every run, including the clean run's `sim-app-tests.log`); in an experimental build with the key YES and nothing else changed, it lists Sylvia, and the opened file is imported (`simulator-open-with-in-place-experiment.log`). Sharing from Files into the extension works with NO. The spike keeps NO; the choice is now a product-owner question with a visible cost on both sides (open question 2). Plan 16.4's "choose Files -> Sylvia" refers to Finder's Files tab, which works either way.

**F7. Share-extension status strings are missing from the vocabulary.** Plan 4.4.6 has no entries for the extension's "Received" and "Not received" states. Those states must stay distinct from "Saved" and "Ready" (I-03, I-04). Owner: G0.6 design package.

**F12. **F13. The first stall detector cut off providers that were still sending.** The Progress that `loadFileRepresentation` returns wraps the provider's own Progress as a child: while the provider works only `fractionCompleted` moves, and `completedUnitCount` stays 0 until delivery (measured on macOS Foundation). The first implementation watched the count, so any provider that took longer than the 60 s stall limit to deliver, such as an iCloud download of a large file, would have been cancelled with a "stopped sending" fallback while it was still sending. Run against that detector, the new host test of a provider that reports progress for six times the stall limit fails at the first stall interval (`host-stall-detector-before-fix.log`); the detector now treats any change of count, total or fraction as progress and the test passes (`host-intakekit-tests.log`, `sim-intakekit-tests.log`). Whether an iCloud download reports its progress through this Progress on a phone is checklist step 18, which needs a placeholder that takes longer than 60 s to download. *(M0 final fix, 19 October 2026: the two stall tests used the wall clock, a provider thread stepping every 100 ms against a 500 ms timeout, and failed in 2 of 13 full-suite runs under Xcode 27.1 while the suite's other tests ran in parallel (final review CC-02). The detector now reads an injected stall clock (`StallClock`, the continuous clock by default, so the product's 60 s timeout and its behaviour are unchanged), and the tests drive it by hand (`ManualStallClock`): the slow-but-moving provider is received after 3.0 s of that clock, the provider that stops is cut off 1.65 s after it started, within the 1.5-2 s the test asserts, and a third test checks that the load's Progress follows the provider's. The suite alone passed 5 of 5 runs and the whole host suite 3 of 3 at one-minute loads up to 22, and a copy with the F13 defect put back fails both stall tests: `Docs/Stage0/evidence/M0-Integration/final-fix/g03-stall-tests.log`.)*

**F14. Imported bundles leave Documents; staging-class data leaves backups.** A bundle in Documents is a transport copy (4.5 GiB in the cable flow). Once its job is durably staged, the app removes it (plan 16.4 allows cleanup "after successful import"), so it is neither kept twice nor backed up. A rejected or partial bundle stays until the user removes it, backup-eligible like anything the user puts in Documents. The App Group handoff inbox is staging class (plan 17.1) and is now excluded from device backup by the extension (which can run before the app) and again by the app; the layout audit checks both exclusions. An APFS clone copies its source's attributes, so a staged clone may keep the source's data-protection class; the in-app test records which class a clone gets, and the device result decides whether the importer must set it (checklist step 24).

**F15. Raw files copied with Finder: imported, but never proved complete.** Plan 8.5 allows a raw file copied through Finder, imported at the user's request with coordination and validation. Before review round 2 the harness offered such a file only Remove, and Import would have sent it to the bundle importer to fail as `truncated_or_not_a_pack` (R2-05). The drop area's Import now takes a raw supported file through the single-file importer: an APFS clone inside a coordinated read, hashed, then the same journal and duplicate rule as every other route (host tests; `ImportRoutesUITests` on the simulator, with a file the harness places in Documents in place of Finder). What the importer can know: if the file's device, inode, size or modification time change between the snapshot and the end of hashing, the copy is evidently still running, and the import is refused ("the file changed while it was being imported ...: wait until the copy has finished, then import again"), with nothing staged. What it cannot know: a copy that is paused, or has stopped, looks finished, and its bytes are staged as they are (host test: a writer stopped at half; 2,097,152 of 4,194,304 bytes staged). Staged is not ready (plan 8.2), so the type's later validation has to catch a cut file, and for audio it may not: an MP3 or CAF cut short can still play. Consequences: the product should steer large transfers to `.sylviapack` (the companion's cable flow already does), word the raw import as "wait until Finder has finished", and decide whether imported raw files are offered for removal (open question 8). Device checklist steps 28-30 record a real Finder copy, including one still running and one cancelled.

**F16. Readers and contracts: what the checks show, and where they stop.** The rule for both manifest readers is that they accept nothing their schema refuses, and that when a schema accepts and a reader refuses, the schema's description states why. Three of four review rounds found it broken. R2-04: unchecked string bounds on the generator, group metadata and identifiers, and any `order` on a non-audio file, accepted; non-ASCII text counted in bytes, refused. R3-01: an explicit null in any optional member accepted, a member name given twice read as the first of its values where the validator keeps the last, and refusals of schema-valid input undocumented. R4-01: a file `group_id` canonically equivalent to its group's ("WALDEN_" + U+212A KELVIN SIGN, whose group is "WALDEN_K") accepted by the reader, the writer's self-check and extraction, although the schema refuses it; and R4-02 found two more undocumented refusals, the manifest size limits (F19). The previous revisions of this report said the readers "accept nothing their contracts refuse". That was a claim about every input, R4-01 refuted it, and this revision withdraws it. What the checks show is narrower:

- *Text.* The readers check the whole text before decoding (`StrictJSON.swift`: RFC 8259 in UTF-8 without a byte order mark, no member name twice in one object, no unpaired surrogate escape, at most 512 levels of nesting, integers of at most 4,300 digits, no NaN or Infinity), refuse an explicit null in every optional member, accept only canonical UUIDs, and test separators on bytes (F18). What JSONDecoder and `UUID(uuidString:)` do on their own is recorded on host and simulator by the test "platform facts behind the strict reader" (`host-intakekit-tests.log`, `sim-intakekit-tests.log`): JSONDecoder accepts a trailing comma in an object or an array, a UTF-8 byte order mark and UTF-16 text, does not look inside members it does not decode (invalid UTF-8, an unpaired surrogate escape and a malformed number pass there), and keeps the first of two members with the same name; `UUID(uuidString:)` accepts a UUID followed by U+0000 and anything after it. Without the text check, the pack reader also accepted UTF-32 text and, inside a member it does not decode, an unescaped control character, a bad escape, a leading zero and an integer of 4,301 digits (`contract-differential-sensitivity.log`, case `text-not-checked`).
- *Equality (review R4-01).* Swift compares `String`s by canonical equivalence: `==`, `Set`, `Dictionary`, `init(rawValue:)`, and JSONDecoder's matching of member names to coding keys and its decoding of `String` enums all take U+212A for "K" (test "platform facts (recorded): ==, init(rawValue:) and JSONDecoder's member names and enum values all take U+212A for K", host and simulator). JSON Schema compares code points. The readers now compare manifest text byte for byte (`PathBytes.equal`: entry names against the manifest's paths and the archive library's names, digests, `format`, `producer.kind`, the handoff's item names), check a file's `group_id` against the contract's pattern before looking its group up, decode enum values byte for byte (`decodeExactCase`), and keep only pattern-checked ASCII text in sets and dictionaries; the duplicate-path rule alone treats paths as equal after case folding and normalization, deliberately, and so refuses more, never less. JSONDecoder's member-name matching is outside the readers' code, so two tests bound it: a scan of every code point finds exactly three non-ASCII code points canonically equivalent to ASCII text, U+037E (";"), U+1FEF ("`") and U+212A ("K"), in Foundation's canonical decomposition and in Swift's `==` alike; and no member name, enum value or constant in either schema holds ";", "`" or "K" (the test reads the schema files). Another spelling of a contract name would have to decompose to it code point by code point, so there is none. The same audit found the share extension's writer cutting "/" out of shared file names with a Character-based operation (F18).
- *The differential check* (`contract_differential.py`, run by `check-contract-instances.sh` in CI step 5) gives the bytes of each input to the schemas, judged as `Scripts/validate-contracts.py` would judge a fixture, and to each reader on its own files (review R3-02), through the functions PackReader and InboxScanner use, size limits included. In the clean run: 363 named cases (pack 230, handoff 133), each with its expected outcome (287 the same verdict from schema and reader; where the schema accepts and the reader refuses, 31 for a rule the schema leaves to readers, 20 for a reader limit and 25 for a validator quirk); 3,000 seeded random mutations, 312 of which wrote a canonical twin into the pack manifest (whose base for mutations has group ids that hold "K"), none accepted by a reader and refused by its schema, and every reader refusal of a schema-valid one for a reason in a class whose cause the input holds; and the instants of 42 accepted `created_at` values, each equal to Python's proleptic Gregorian instant within 1 ms: 0 failures (`host-contract-instances.log`).
- *Its sensitivity.* `check-differential-sensitivity.sh` (not run by CI; `contract-differential-sensitivity.log`) builds the readers with one deliberate defect at a time, nine in all, and the check fails against each and names the cases each affects: dates read with `.iso8601` in the pack reader and in the handoff reader, nulls read as absent, the text check skipped, UUIDs taken from `UUID(uuidString:)`, separators tested with Swift's Character-based operations (F18), a file `group_id` looked up without the pattern check (R4-01), `created_at` converted with Foundation's Gregorian Calendar (R4-03), and both manifest size limits removed (R4-02). Two earlier versions of the check, committed byte for byte under `Spikes/G03-Intake/scripts/sensitivity/` (review R4-05), pass against the defect their review found: the round 2 check against `.iso8601` pack dates (R3-02), and the round 3 check against the unchecked `group_id` lookup (R4-01). Against the round 1 readers the round 2 check had found 45 mismatches (`contract-instances-before-fix.log`).
- *Where it stops.* Every result above holds for the inputs tried. Rounds 3 and 4 each found a class of input no check had tried, and another may exist. Each class found so far is now a named case, a random mutation where one fits, a contract fixture and a sensitivity defect.

When a schema accepts and a reader refuses, the reason is in one of three classes, each stated in the schema's description: rules the schema leaves to readers (byte limits of paths, file names and whole manifests, NFC, uniqueness, sums, group rules, size limits); limits that RFC 8259 and the contracts' 64-bit units leave to readers (a member name given twice, an unpaired surrogate escape, nesting deeper than 512 levels, an integer outside the 64-bit field); and quirks of the Python validator, which lets through what the specifications refuse ((b) below). Facts that matter beyond G0.3: (a) JSONDecoder's `.iso8601` strategy disagrees with JSON Schema's `date-time` in both directions on macOS 26.6: it refused a lowercase `t` and `z` and the offsets `+23:59` and `-23:59`, and accepted 30 February, 29 February in 1900 and in 2025, hour 24, second 60, year 0000, an offset without a colon, and a trailing space or line feed (`contract-differential-sensitivity.log`, case `pack-dates-iso8601`; first found in `contract-instances-before-fix.log`), so the readers use a parser that mirrors the validator (`RFC3339.swift`); (b) the repository's validator matches `pattern` (Python's `re`) and `date-time` (rfc3339-validator's regular expression) with `$`, which in Python also matches before a final line feed, so a `sha256`, `stored_path`, `group_id`, path or `created_at` ending in a line feed passes `Scripts/ci.sh contracts` although ECMA-262 and RFC 3339 refuse it, and its `format: uuid` check (Python's `UUID()` and `int()`) accepts extra hyphens, "urn:" anywhere in the text, and a "+", an underscore, a space or a non-ASCII digit in place of a hexadecimal digit; the Swift readers refuse all of these (requests to the validator's owner, below); (c) paths and file names are bounded in UTF-8 bytes, which no schema can express, so the two schemas state the rule with an example that is valid against the schema and refused by readers; (d) a reader built on JSONDecoder alone accepts text the contract refuses, so any product reader of a manifest that comes from outside the app needs the text check or an equivalent (ADR-0010 consequences); (e) Swift's `String` equality is canonical equivalence, so product code that compares, hashes or looks up text from outside the app (identifiers, names, enum values) must compare bytes or first prove the text ASCII (ADR-0010 consequences); (f) Foundation's `Calendar(identifier: .gregorian)` is Julian before 1582-10-15: the first `RFC3339.date(from:)` converted with it and put 1582-10-10 ten days late (after 1582-10-15) and 0001-01-01 two days early (review R4-03; `host-round4-before-fix.log`); instants are now counted in the proleptic Gregorian calendar, as RFC 3339 and Python count them (test "created_at: the first of every month from 0001 to 9999 lies exactly one proleptic Gregorian month after the previous one": 119,987 consecutive months, none off).

**F17. Cancel frees the extension, not necessarily the sharing app.** Cancel cancels the extension's own load. On the host, where provider and reader share a process, that reaches the provider's Progress ("provider saw the cancel: true", `host-intakekit-tests.log`). Through the real share sheet on the simulator it did not: the sharing app's provider kept going for the 15 s or so it was observed (`simulator-share-sheet-item-provider-observation.log`). The extension does not depend on it, since it stops waiting and claims nothing at once, but a large iCloud download or Mail fetch may go on after the user cancels. Device checklist steps 9 and 18 record what Mail and iCloud do.

**F18. A "/" inside a grapheme cluster: a path traversal the readers missed (found while closing R3-01).** Swift's `String` compares and searches by `Character`, an extended grapheme cluster, and a "/" followed by a combining mark (such as U+0301), a spacing mark or a zero-width joiner, or preceded by a prepended mark (such as U+0600), forms one `Character` with that mark (Unicode UAX #29, rules GB9, GB9a and GB9b). `split(separator: "/")`, `hasPrefix("/")`, `contains("/")` and `==` then do not see the "/", while `open(2)`, the contracts' patterns and every other platform do (test "the platform fact: a slash inside a grapheme cluster is invisible to Character-based String operations"). The G0.3 path rules used those operations. Before this fix (`host-path-separator-before-fix.log`: the new tests run against the old code), the pack reader accepted the manifest path ".." + "/" + U+0301 + "escape.md" (one component to Swift; ".." and U+0301 + "escape.md" to the file system), and extracting that pack wrote the file into the parent of its extraction directory; it also accepted a leading "/" + U+0301, an empty component, a "." component and 16 components hidden the same way, and missed a file that is also used as a folder and a directory entry ending in "/" after U+0600; the handoff reader accepted an `original_filename` holding such a "/", which the schema refuses; and the drop area resolved the name "../" + U+0301 + "outside.epub" to a file beside Documents, which its Remove then deleted. The escape reaches one level only, because each further ".." needs a "/" before it that Swift does see. In the product the parent of an extraction directory is `Staging/Extracting/`, still inside the app's private storage, and the next launch's recovery removes stray entries there, so the reachable harm was a stray file or folder; but it broke T13's "no sandbox escape" and the rule that readers accept nothing the schema refuses, and none of the earlier differential checks tested it. Fix: every separator, prefix and dot-component test works on UTF-8 bytes (`PathBytes.swift`; 0x2F never occurs inside a multi-byte UTF-8 sequence), in the pack and handoff readers, the drop area, the layout audit and the harness, and extraction refuses any target whose standardized path is not strictly inside its directory, compared byte for byte (defense in depth). Evidence: `PackPathSeparatorTests` and `PathSeparatorTests` on host and simulator ("file written outside the extraction directory: false"); 12 differential cases (10 refusals, and 2 combining marks inside a component that must still be accepted); 3 contract fixtures; the sensitivity check's `separators-as-characters` case. Consequence for the product: path and file-name rules must not use Swift `String`'s Character-based operations for separators or dot components (ADR-0010 consequences); the schemas' descriptions now say so for other platforms. The audit for review R4-01 found one more: the share extension's writer cut "/" out of a shared file name with Foundation's `replacingOccurrences(of: "/", with: "_")`, which leaves a "/" that a combining mark follows; the writer's own validation then refused the name, so such a share failed safely, as not received. It now replaces code points (test "a shared file name holding a slash before a combining mark is recorded with an underscore, and the share is received"; `host-round4-before-fix.log` shows the test failing against the old code).

**F19. Manifest size limits: stated, enforced on both sides, and the entry limit made reachable (review R4-02).** Both readers refuse a manifest above a byte limit, whatever it holds, and neither schema said so. The pack reader's limit was 1 MiB. The writer pretty-prints its manifest, so even with 4-byte paths and every other field as short as the schema allows at most 5,636 files fitted (computed in the writer's layout; the review computed about 7,900 in compact form), and the schema's `maxItems` 9998 (the plan's 10,000 entries, less the two manifest entries) could not be reached. The limit is now 16 MiB, for a measured reason: the writer's manifest for 9,998 files with every path at its 512-byte limit, 128-character media types and 64-character group ids, in 20 audiobook groups with their titles, creators, languages and identifiers at their limits, is 9,356,558 bytes, and a pack of that shape (10,000 entries, 20,524,663 bytes) validates in 2.6 s on the host and 3.1 s on the simulator (test "the entry limit is reachable ..."; debug builds with other tests running alongside, and other jobs on the Mac: indicative). A manifest of exactly 16 MiB reads in 0.27 s on the host (0.44 s on the simulator) and one byte more is refused as `manifest_too_large`. The spike's writer reaches the limit too: PackWriter wrote and self-validated 9,998 files with 512-byte paths in 5.3 s (`host-pack-writer-scaling.log`, release build, load about 10). Its time grows faster than the number of entries (1,000 files: 0.2 s; 4,000: 1.4 s), because ZIPFoundation's `addEntry` reads and rewrites the whole central directory for every entry; the product writer (M6) should write the central directory once. The handoff reader's limit stays 256 KiB: 100 items, the share limit, with 255-byte file names and 128-character type identifiers take 87,803 bytes. Names of control characters, which JSON writes as six-byte escapes, with long type identifiers can exceed it, and the extension used to commit such a manifest, which the app's scan then refused: a "Received" for a handoff that is never imported. The extension now refuses to commit one and shows the fallback (test "handoff.json size: ..."; `host-round4-before-fix.log`). PackWriter likewise refuses an over-limit manifest before writing anything. Both schemas' descriptions state their limit, `sylviapack-tool check-manifest` applies it through the readers' own functions, and the differential check tries each at the limit and one byte over (`host-contract-instances.log`, cases `size-*`). The product owner approves the values (open question 1).
