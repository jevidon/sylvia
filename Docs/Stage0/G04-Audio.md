# G0.4 audio: playback, excerpts and quick capture

**Gate:** G0.4 (plan 21.1): "test the proposed codec/container matrix, long playback, chapters, cross-file excerpts, export timing and main-position-preserving preview. Separately evaluate lock-screen quick capture. Record which part of the aspirational workflow can ship."
**Spike:** `Spikes/G04-Audio` (XcodeGen project `G04Audio`: framework `G04AudioKit`, app `G04AudioHarness`, control extension `G04CaptureControl`, test bundles `G04AudioTests` and `G04QuickCaptureUITests`). Stage 0 evidence code; never shipped.
**Decisions:** ADR-0006 (playback, timeline and excerpts; provisional codec list), ADR-0007 (quick capture). Both Proposed.
**Device steps:** `Docs/Stage0/device-checklists/G04-Audio.md` (all pending).

## How to reproduce

```sh
Scripts/fixtures/fetch.sh                                   # LibriVox sources (SHA-256 pinned)
Scripts/ci.sh g04                                           # Scripts/ci.d/60-g04-audio.sh: everything below; tables in .build/ci-results/g04-audio
G04_RESULTS_DIR=Docs/Stage0/evidence/G04-Audio/results Scripts/ci.sh g04   # the same, writing the evidence tables there
G04_RESULTS_DIR=Docs/Stage0/evidence/G04-Audio/results G04_DEVICE_FIXTURES=1 Scripts/ci.sh g04   # as the clean run: also the device bundle with the fixtures
```

`G04_RESULTS_DIR` may be relative (taken from the repository root) or absolute; the drop-in empties that directory, passes the absolute path to the test process, and fails if any of the 40 expected tables (41 with `G04_DEVICE_FIXTURES=1`; `EXPECTED_TABLES` in the drop-in) is missing or older than the run. A table the tests cannot write is a test failure. The drop-in generates the fixtures if needed (`Scripts/fixtures/generate-g04-audio-fixtures.sh`, `generate-g04-audio-long-formats.sh` and `generate-g04-audio-probes.sh`, Homebrew ffmpeg 8.1.2, about 30 minutes and 8.4 GB the first time), generates the project, builds the tests for a generic iOS device with automatic signing and records the signatures (unsigned when the host has no Apple Development identity), with `G04_DEVICE_FIXTURES=1` also builds and signs that bundle with the 8.6 GB of fixtures inside and checks every bundled file against the fixture manifests (row 30), builds for and runs every test on the simulator `Sylvia-M0-g04-audio`, samples the host's load every 30 s while it runs (`host-load.tsv`; review R4-02), prints the App Intents metadata of the app and the control extension, kills and relaunches the harness app (process-kill trial), decodes kept excerpts with ffmpeg and measures those decodes (portability), runs the quick-capture intent through the system, as the App Shortcut from the Shortcuts app and as the control from Control Center (UI tests), with the build as Xcode signs it and re-signed by the team, and fails unless the quick-capture results this report relies on are there (row 18; review R5-06), shuts down its simulator when it exits, whether it passed or failed (unless `G04_KEEP_SIM=1`; review R4-04), and exits non-zero on any failure or build warning, on a test file that creates a player outside `TestAudio`, or on a harness launch that did not log the quiet volume. Everything plays at 1 % volume unless `SYLVIA_AUDIBLE_PLAYBACK=1` (row 34). A missing fixture is a test failure, never a skip. The clean run below took 85 minutes (the drop-in's header estimates about 90), 40 of them the soak test and 16 the long-format suite.

**Environments.**

- **host:** macOS 26.6.2 (25G83), Apple M5 Max, Xcode 27.0 (27A266a), Swift 6.4, ffmpeg 8.1.2 (Homebrew).
- **simulator:** iOS 26.5 (23F77), iPhone 17 (`iPhone18,3`), simulator `Sylvia-M0-g04-audio`.
- **host load** (review R4-02): the build Mac is shared with other jobs' simulators (2-4 booted during the clean run; 1-minute load average 4.6-121, `host-load.tsv`, with spikes during the codec matrix, the soak and the quick-capture step; the trials and rows that record their load ran at 4.5-18.5, a lightly loaded run compared with round 4's 7-136). Some timings grow with it, the first precise seek into an MP3 and the open scan of native FLAC, MP3 without a header and Ogg Opus most of all, so every timing table records the load averages at its start and end, the cold-resume and capture tables per trial (`load_1m`), and since round 5 the open-time table and the remux rows per row (review R5-05); the clean run's log header records `uptime` and the booted simulators at its start and end.
- **device:** not used (reserved for the serialized device run). Nothing below is inferred for the device.

**Quiet runs.** Every result table of the clean run was taken with the players at **1 % output volume** (product-owner request: the Mac's speakers are shared); the tests' summary tables say `output at 1 % volume (quiet test runs)` in their environment line, and the harness tables record the harness's `output volume=0.01` lines. Evidence from earlier runs that this report also cites was taken at full volume (`release-build-simulator.txt`, `long-formats-cold-resume-earlier-run.tsv`, `intermittent-player-stall.txt`, `soak-earlier-runs.txt`, and the tables at commits `0086b10` and `29bc5c4`) or at 1 % (the clean runs of rounds 3 and 4, tables at commits `943d5e7` and `5d85b1f`, and `budgets-round4-targeted-run.txt`). The volume is applied after decoding, the time-pitch stage and the analysis taps, and the media clock is unaffected, so nothing measured changes (row 34). `SYLVIA_AUDIBLE_PLAYBACK=1` gives full volume; the harness has a full-volume toggle for the device checklist's listening steps.

**Evidence.** The full clean run, from deleted build products: `Docs/Stage0/evidence/G04-Audio/ci-clean-run.log` (with `Scripts/ci.sh contracts`; its header names the commit under test and the host's load at its start and end). Result tables written in that run: `Docs/Stage0/evidence/G04-Audio/results/` (named below without the folder). Fixture generation: `fixture-generation.log`, for the 3- and 10-hour files of every format `fixture-generation-long-formats.log` (its provenance header added in round 5, review R5-08), and for the container probes `fixture-generation-probes.log`. Read a committed table with `git show <commit>:Docs/Stage0/evidence/G04-Audio/results/<table>`.

**Fixtures.** All generated from the public-domain LibriVox *Meditations* recording already in the fixture cache; none committed (all are in `$SYLVIA_FIXTURE_CACHE/generated/g04-audio/`, about 1.1 GB without the long-format files below, with SHA-256 digests in its `manifest.tsv`; two full generations with the current script gave identical digests, `fixture-generation.log`). Two PCM masters (600 s; 2,161 s from sections 1 and 2) are the reference for every timing measurement: each fixture is an encode of a master, so any decoded, played or exported audio is located in the master by normalized cross-correlation, independently of the timestamps the stack reports. Formats: MP3 CBR, VBR with and without Xing/VBRI header, MP3 with ID3 CHAP chapters, the real LibriVox section MP3 (MPEG-2 Layer III, 22.05 kHz mono; the 600 s master is ffmpeg's decode of it), M4A AAC-LC, HE-AAC v1 and v2 and ALAC with chapters, FLAC (native, with `CHAPTERxxx` Vorbis comments, and in MP4), Opus in Ogg (.ogg and .opus, with Vorbis-comment chapters), WebM (Matroska chapters), MP4 and CAF, WAV with RIFF cue points and labels, a 1 kHz tone; 10-hour AAC M4B (17 chapters), CBR MP3 and VBR MP3; 10.2-hour files of every other provisional format (`$SYLVIA_FIXTURE_CACHE/generated/g04-audio/long-formats/`, about 7.3 GB, digests in its own `manifest.tsv`; review R3-01): native FLAC with a seek point every 10 s (as the reference encoder writes it; ffmpeg writes none, so the script inserts it from ffprobe's packet positions and checks every point lands on a frame header) and 17 Vorbis-comment chapters, Ogg Opus (.ogg and .opus), FLAC and Opus in MP4, ALAC, HE-AAC v1 and v2 (17 chapter-track chapters each), Opus in CAF, WAV (3.2 GB) and MP3 VBR without a header, plus 3.0-hour native FLAC and Ogg Opus; and a four-file MP3 book whose file names (`Part 2, 1, 3, 10`) disagree with its embedded track numbers (T14). Container probes (review R5-08; `Scripts/fixtures/generate-g04-audio-probes.sh` into `probes/`, digests in its own `manifest.tsv`, two generations with identical digests in `fixture-generation-probes.log`): the first 60 s of the 600 s master as native FLAC and as Ogg Opus, each with one three-chapter table as Vorbis comments numbered `CHAPTER001`, `CHAPTER000` and `CHAPTER01`. The real LibriVox M4B (4 h 47 m, 12 chapters) is used as downloaded.

**Test suite (simulator).** 140 tests in 24 suites, all passed; three of them pass with known issues (4 in all), each a start/resume budget miss that rows 21 and 33 report: the seek-latency test in the 10-hour files (the slow first precise seek deep into an MP3), the budget test (cold resumes with precise timing more than 0.33 h into an MP3) and the long-format cold resume (native FLAC and MP3 without a header; Ogg Opus stayed within the budget in this run, so it recorded none). A known issue is recorded only when a miss occurs, with its times, and is not marked intermittent (review R3-03). Round 4 added `MP3FrameScannerTests` and `RemoteCommandTests` (unit) and `PerFileTimingTests` (real AVFoundation); round 5 added `ExcerptProtectionTests` (2) and `ContainerProbeTests` (1) (real AVFoundation), two `PlaybackServiceTests` and one `RealPreviewTests` test for loading another edition (review R5-02), one `TimelineTests` test for bounded absent tracks (R5-03), and the UI test `QuickCaptureThroughControlCenterUITests` (R5-01). The ffmpeg portability test (1 test) is skipped in that run by design and runs in its own phase after ffmpeg has decoded the kept excerpts; the UI tests `QuickCaptureThroughShortcutsUITests` and `QuickCaptureThroughControlCenterUITests` (separate scheme `G04QuickCaptureUI`) run twice each in the quick-capture step, once per signing. Unit suites over a deterministic engine and an injectable clock run in parallel; every suite that plays, decodes or exports real audio is nested in one serialized suite so measurements do not compete.

## Findings that change scope or approach

1. **Start/resume: a constant-bit-rate MP3 meets the budget at every depth with the per-file timing mode; the files that must stay on precise timing miss it wherever opening the file or the first seek in it grows with length** (rows 21, 22, 33 and 35). Estimated timing is exact only in a constant-bit-rate MP3 and seconds to minutes off in VBR MP3, native FLAC (with or without a seek table) and Ogg Opus (row 22), so the import decides per file (ADR-0006 decision 2): it proves an MP3 constant by walking every frame header, and the player, the preview and the export then open it with estimated timing: sample-identical decodes, the same content positions as precise timing, and a cold resume in 0.14-0.15 s at every depth to 10 h, at host loads of 4.6-14.0 in the clean run (11-74 in round 4's). LibriVox audiobooks, where the plan's fixtures come from, are 64 kb/s CBR MP3 with LAME `Info` tags; both LibriVox section files and the four book members here are proved. With precise timing, on the simulator: (a) the first seek in an MP3 the process has not read costs about 1 s per hour of depth, more when the host is loaded (the budget crossing lay between about 1.0 and 1.8 h in the runs of rounds 3 to 5, and at 0.41-1.52 h in the round-4 review's run at load averages of 60-148), and (b) opening a native FLAC, an MP3 without a header or an Ogg Opus file scans it, about 2.7-3.4, 0.8-1.0 and 0.09-0.16 s per hour of file over four runs, at every resume depth, and longer under host load (a 10-minute native FLAC took 2.65 s to open during a load spike in the round-5 review's run, 0.49-0.50 s in this run): a 10-hour native FLAC took 27.2-27.4 s to resume in the clean run, a 10-hour MP3 without a header 7.8-8.1 s and a 10-hour Ogg Opus 1.0-1.3 s. Relaunching the app always takes this path (the service opens the member and seeks to the stored checkpoint), and so do a capture's export and pending preview in such a file (27.2 s from the 10-hour FLAC, 10.4-12.0 s 9.5 h into a 10-hour MP3 with precise timing, against 0.07-0.08 s for the proved-CBR MP3 with the per-file mode; the anchor and note are saved first). So a VBR MP3 meets the budget only near the start of each file (in roughly its first hour on a lightly loaded simulator, less under load; depth claims are indicative until the device run), a multi-file VBR book only if its parts are short, a native FLAC book only if its files are shorter than about 25-30 minutes and an MP3 without a header only below about 1.4-1.7 hours (both on a lightly loaded host; shorter under load), and a 10-hour Ogg Opus file sits at the edge (43 of 60 trials within over five runs). MPEG-4 (AAC-LC/M4B, HE-AAC, ALAC, FLAC, Opus), Opus in CAF and WAV are not affected: at most 0.16 s at every depth to 10 h. None of this is a failure to open or decode: every long file opened and resumed at the right place, and a slow open shows as `preparing`, never as a decode error. Proposed: adopt the per-file timing mode (estimated timing only for an MP3 the import proves constant bit rate; precise for everything else) and, for the files that stay precise (VBR MP3, native FLAC, Ogg Opus), the import remux of ADR-0006 decision 17 (packets copied unchanged, measured sample-identical, every cold resume of a copy 0.11-0.16 s), subject to the product owner's choice about keeping the original (open question) and to the device run (checklist steps 1 and 1.5); without the remux, list those formats with their limits in the import guide. This is a budget failure for those files, not a reason to drop MP3, FLAC or Opus.
2. **Opus in WebM is not playable on iOS 26.5 (simulator); Opus in Ogg, MP4 and CAF is.** The release list can include Opus only in those containers, and only after the device run.
3. **Chapters depend on the container.** QuickTime chapter tracks (M4A/M4B with AAC-LC, HE-AAC, ALAC, FLAC or Opus) and ID3 CHAP frames are read exactly; Vorbis-comment chapters in FLAC and Ogg are read with an indefinite last end (the importer closes it at the duration) and only in the three-digit `CHAPTERxxx` form (`CHAPTER01` is ignored; `container-probes.txt`); WAV cue points are not read at all; CAF chapters were not tested (row 4).
4. **The excerpt's stored "actual" timing is the decoder's claim, not the truth.** For MP3 sources it is 13.1 ms off, for HE-AAC 47.9 ms (constant per codec). Within budget; each range's source format is now stored with the excerpt so a correction can be added if a later budget needs it.
5. **AVQueuePlayer posts end-of-item before advancing.** A position store that reads the player's current item at that moment saves the old member. Fixed in the spike (ADR-0006 decision 10); the product must keep it.
6. **Furthest position needs an explicit rule for forward jumps.** The first rule ("contiguous playback from the frontier") froze the frontier for the rest of the book after any skip forward (review R1-02). The rule now adopts a run that started ahead of the frontier after 30 s of contiguous listening (ADR-0006 decision 9). As a result the furthest position is a place reached by listening, not proof that everything before it was heard; completion stays explicit (plan 12).
7. **Lock-screen quick capture is plausible only through an App Intent, and it needs a device to decide.** On the simulator, unlocked, an App Shortcut run from the Shortcuts app (team-signed build) and the control pressed in Control Center (both signings) were performed in the playing app's process and saved before acknowledging (row 18): the system took the `AudioPlaybackIntent` route the design relies on for the control. The bookmark remote command is reportedly not shown since iOS 16, and Live Activity buttons are documented as inactive while locked. A Control or App Shortcut can run while locked, but whether the system still performs the control's intent in the app process while locked, and whether adopting `AudioPlaybackIntent` for an action that does not start audio is acceptable, are open (ADR-0007). Proposed narrowing for approval (plan 3.3): the in-player Capture button is the release baseline; quick capture ships only after device checklist steps 8-13 pass.
8. **Locked capture constrains storage protection.** Every store on the capture path (capture records, checkpoints, retained excerpts and their directories) is class C (`completeUntilFirstUserAuthentication`), set explicitly (review R5-04: the excerpt had been left to the platform default; `ExcerptProtectionTests`; the simulator ignores the class, `simulator-file-protection.txt`, so only a device reads it back, checklist step 9), as ADR-0012 sets for every persistent file: a stricter class makes the save fail while locked, and a weaker one is excluded (plan 18.1, T50). The trade-off, readable while locked once the phone has been unlocked since the restart, is in ADR-0007 decision 4. Before the first unlock after a restart nothing can be saved and nothing may be acknowledged. To be confirmed with G0.5's persistence decision.

## Open questions

- Product owner: approve the quick-capture narrowing (finding 7) and choose whether FLAC, Opus and WAV are advertised if the device passes them (WAV books would have no chapters); confirm mono excerpts.
- Product owner: adopt the per-file timing mode (finding 1, ADR-0006 decision 2: estimated timing only for an MP3 the import proves constant bit rate, precise for everything else) and, for the files that stay precise (VBR MP3, native FLAC, Ogg Opus), the import remux (ADR-0006 decision 17), and if so whether the original is kept beside the copy (the member's storage doubles) or replaced by it, and whether a VBR MP3 is remuxed always or only when long; without the remux, native FLAC, MP3 without a header and very long Ogg Opus files are listed with their length limit, and VBR MP3 with its depth limit.
- Technical lead (M2): whether reading a file through before its first precise seek removes the MP3 first-seek cost on a relaunch. In the clean runs of rounds 4 and 5 the cost did not appear where the process had just read the whole file (row 21: the soak's first play 9.5 h into the VBR MP3 took 0.35 and 0.33 s, against 8.5 s in round 3), but that was not measured as a mitigation, on fresh copies or on a device.
- Design package (G0.6): the vocabulary has no key for "the book is being opened" (`preparing`, which can last tens of seconds for a long native FLAC file without the remux); the harness shows the state's name.
- Design package (G0.6): the vocabulary has no key for "a quick-capture surface was used with nothing loaded" or for "the moment (an audio capture or a bookmark) was not saved"; the spike shows the proposed keys `audio.nothing_to_capture` and `audio.moment_not_saved`. `save.failed` ("Not saved · your text is still here") is the note editor's phrase and is not used for a capture, which has no text (review R2-04). The spike's keys mirror the design package's (`save.done`, `audio.moment_saved`, `audio.excerpt_saved`, `audio.excerpt_not_preserved`).
- Contract consolidation: the audio anchor needs ordered file-local ranges each bound to its asset ID and digest, the actual exported ranges with each range's source format and the excerpt format, and the timeline revision for display (ADR-0006 Open items). The spike's record has no digest field.
- Warnings: none remain. Swift warnings are errors in the project, and the CI step fails on any warning a build prints. The simulator test process logs "Failed to connect to linkd to request update AppShortcut parameters" at launch; with an ad-hoc-signed build the system also refuses to run the App Shortcut, and the control's press makes the App Intents runtime report "a caseDisplayRepresentations entry for AppEnum case "to-0.0" was not found", which the UI test run prints as a warning (the parameter loss of row 18; not a build warning).
