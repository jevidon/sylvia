**Spike:** `Spikes/G05-Recovery` (Swift package `G05Recovery`: library `SylviaRecovery`, host tool `g05-recovery-tool`, test target `SylviaRecoveryTests`). Stage 0 evidence code; never shipped.
**Decisions:** ADR-0003 (persistence), ADR-0012 (retention, backup and restore). Both Proposed.
**Contract:** `Contracts/schemas/backup-manifest.v1.schema.json` with 2 valid and 20 invalid fixtures.

## How to reproduce

```sh
Scripts/ci.d/71-g05-recovery.sh                     # everything below; exits non-zero on any failure
G05_LOG_DIR=Docs/Stage0/evidence/G05-Recovery/logs Scripts/ci.d/71-g05-recovery.sh   # write the evidence logs
Scripts/ci.sh contracts                              # contract validation (shared step)
```

The drop-in builds the package for the host (failing on any compiler warning in the spike's sources), runs the host tests, a 900-kill crash drill, a 150-kill drill with `synchronous=OFF`, the latency benchmark, the scripted restore drill, a 300-kill restore crash drill, a 240-iteration crash drill over a failed migration's put-back and the manifest contract check, then runs the tests on the simulator named by `G05_SIM_NAME` (default `Sylvia-M0-g05-recovery`, iPhone 17, iOS 26.5; another checkout must pass its own name) and shuts it down, and builds the library and tests for iOS devices. After the host tests it fails unless their log has the class-B data-protection evidence of row 10, because those tests skip (and `swift test` still passes) while the Mac's screen is locked; `G05_ALLOW_MISSING_CLASS_B=1` turns that failure into a printed "row 10 evidence missing" warning. The package has no Xcode project; `xcodebuild` uses the package's scheme `G05Recovery-Package` with the committed `Package.resolved` and `-disableAutomaticPackageResolution`. No fixtures need fetching; the committed v1 database fixture is the only one.

**Environments.**

- **host:** macOS 26.6.2 (25G83), Apple M5 Max, Xcode 27.0 (27A266a), Swift 6.4, SQLite 3.51.0.
- **simulator:** iOS 26.5 (23F77), iPhone 17 (`iPhone18,3`), simulator `Sylvia-M0-minors-g05-recovery` (passed as `G05_SIM_NAME`; deleted after the run).
- **device:** not used (reserved for the serialized device run).

**Test suite.** Host: 72 tests in 11 suites, 69 passed, 3 skipped: the device lock probe and the device persistence probe, which need a phone, and the locked-host observation, which runs only while the Mac's screen is locked (`logs/host-tests.log`). The host screen was unlocked for the whole clean run (`ci-clean-run.log` header and footer), so the non-default class-B run and the class-inheritance probe ran and passed, and the drop-in printed "row 10 evidence present" without `G05_ALLOW_MISSING_CLASS_B`. Each skip prints its reason; none is silent.

## Findings that change scope or approach

**F1. GRDB 7.11.1 overrides `synchronous` after `prepareDatabase`.** `DatabasePool` runs `PRAGMA synchronous = NORMAL` on its writer after `Configuration.prepareDatabase`, so a durability pragma set there is silently lost (`DurabilityTests.grdbOverridesPrepareDatabase`; GRDB source `Database.swift` line 539). The library must apply its durability setting on the writer after the pool opens and read it back on every open, failing the open on a mismatch. ADR-0003 records this. Re-check it on every GRDB upgrade.

**F2. GRDB's `appliedMigrations(_:)` cannot detect a newer library.** It returns only registered identifiers, so a file migrated by a newer build looks current. Version checks must use `appliedIdentifiers(_:)` and refuse any unknown identifier (`LibrarySchema.applied`, `MigrationTests.newerSchema`). The plan's "reject newer unsupported schemas" depends on this.

**F3. Data protection cannot be evidenced on the simulator, and GRDB does not expose SQLite's protection open flags.** GRDB's open flags are internal (`Configuration.SQLiteOpenFlags`), so `SQLITE_OPEN_FILEPROTECTION_*` cannot be passed. The spike creates every directory with class C so SQLite-created database, WAL and SHM files inherit it, then sets and reads back the class explicitly. On the macOS host the readback is faithful, and `setAttributes` cannot change an existing file's class (it is refused and detected), so the class must be set at creation: copied files are created new with the class (`FileProtector.copyFile`), never with `FileManager.copyItem`, which keeps the source file's class (review round 1 found media imports failing this way under class B). Class C is the default class on macOS and for iOS app files, so only a run with a non-default class shows that the code applies the class; the host's class-B run does (row 10), but only while the Mac's screen is unlocked, so the drop-in now fails a run that lacks its evidence line. On the iOS Simulator directories report no class and files report class C whatever was requested, so a simulator pass says nothing about protection. Locked-device behaviour (T50) rests entirely on the device checklist, where step 1 also repeats the class-B run. Plan 18.1 is unchanged, but its device evidence must come from a device.

**F4. A process-kill drill cannot choose the durability setting.** With `synchronous=OFF` the same SIGKILL drill also loses nothing, because committed pages survive in the OS page cache when only the process dies. The choice of `FULL` + `fullfsync` rests on SQLite's documented WAL behaviour: `NORMAL` may roll back recent commits after power loss or an OS crash. It does not rest on this drill. Power loss, kernel panics and storage that ignores flushes are not tested, and cannot be on an unmodified iPhone (checklist step 5). On the host the setting is far below the 200 ms budget: p95 3.25 ms over 2,000 saves in this run (`logs/latency.log`). Its cost relative to GRDB's default is not resolved by host runs under parallel load: in this run GRDB's default measured p95 1.53 ms against the chosen setting's 3.25 ms, while the review-round-3 run had them the other way round (2.59 ms for the default, 1.51 ms for the chosen setting). Device numbers are pending.

**F5. Locked-device testing may need a background-capable harness app.** The lock probe runs inside the XCTest runner. If iOS suspends the runner when the phone locks, the probe cannot observe locked-state writes, and checklist step 3 records "inconclusive" rather than passed. The app-level "safe unavailable state before first unlock" cannot be tested without an app target in any case. If step 3 is inconclusive, the plan needs a small harness app with an authorized background mode (audio playback) before T50 can pass.

**F6. Export leases need renewal in the product.** The spike's leases expire after one hour so a crashed export cannot pin blobs forever, and they are not renewed. A product export that can outlast its lease must renew it, or a blob the user deleted mid-export could be collected (ADR-0012 consequences).

**F7. The single-file backup container depends on ADR-0010.** ADR-0010 (Proposed) chooses `readium/ZIPFoundation` 3.0.1 behind `PackStructure`'s strict layout check for `.sylviabackup` as well as `.sylviapack`; until its deciders accept that choice, a `.sylviabackup` is a directory bundle. That works in Files and Finder, but it may not survive every share or AirDrop path as one item. The archive reader must enforce the same path, link, size and digest rules, plus entry-count and expansion limits, before `BackupValidator` runs.

**F8. A backup's database must be treated as untrusted code, not only untrusted data.** Review round 1 showed that a crafted snapshot with refreshed digests could carry a trigger that silently deleted knowledge during restore, or tables without `STRICT` and `CHECK`, and that restore accepted it because it checked only the migration list. Restore now opens the copy in SQLite's defensive mode with `trusted_schema=OFF`, compares every `sqlite_schema` entry (type, name, table and exact SQL) with the schema this build's migrator produces in memory for the snapshot's migrations, before reading counts or writing anything, and repeats schema, integrity, foreign-key and count checks after its own last write. Review round 2 showed that rows the schema does not constrain still mattered: a crafted effective date the app's own `EffectiveDate` rejects, or a ChangeJournal sequence near 2^63 that made every later save fail as "disk full". Restore now also runs `RowCheck` (every effective date against its precision; `sqlite_sequence` equal to the journal's highest sequence) before and after migrating and after its last write. Review round 3 found two more such values: a note's `current_revision` that does not match its revisions (every later edit of the note fails on the revision key, or `Int64.max` makes the edit's `+ 1` trap), and a date component with a sign (`+019`, which Swift's `Int(String)` accepts). `RowCheck` now also requires each note's revisions to be numbered exactly 1 to its `current_revision`, every INTEGER to lie within ±(2^53 - 1) (so the JSON export can always run and no counter the app increments can overflow), and date components to be ASCII digits; `EffectiveDate` requires the digits too, and `reviseNote` refuses an out-of-range revision with an error instead of trapping. Review round 4 led to one more: GRDB reads TEXT as a C string, so a stored NUL hides the text after it and invalid UTF-8 is replaced (finding F12); `RowCheck` now also requires every TEXT value to be valid UTF-8 without a NUL. Any other app-level invariant a future table relies on must be added there. The exact SQL comparison depends on SQLite producing the same schema text for the same migrations; a SQLite or GRDB upgrade must re-run `RestoreTests.referenceSchemaMatchesLibraries` and `restoreOlderBackup`, and a product that runs `ANALYZE` must handle the `sqlite_stat*` tables explicitly (ADR-0012 consequences).

**F9. Canonical cover thumbnails are part of format v1.** Plan 17.3 lists them as backup content, and ADR-0012 makes any later role change a manifest v2, so they were added at design freeze: migration `v2-edition-cover-thumbnail` (a content-addressed thumbnail per edition under `Library/Blobs/covers/`), role `cover_thumbnail` and class `canonical_cover_thumbnail` in the contract, and restore requires the bundle's cover files to be exactly the ones the snapshot references. The spike never garbage-collects covers, so it takes no leases for them; a product cleanup of covers must use the same leases as excerpts.

**F10. Putting a pre-migration snapshot back is itself a multi-step file operation and needs the same crash safety as the restore swap.** Review round 2 found that the first put-back moved the live database aside before copying the snapshot in, with no record of the operation: a kill or a full disk in between left `Library/` without a database, and the next open let SQLite create an empty library while the data sat unreferenced in `Recovery/`. The fix (ADR-0003 steps 2-7) writes an intent before migrating, stages and flushes the snapshot copy before touching the live files, finishes any interrupted put-back at the next open before SQLite opens anything, and refuses to create a database for an installation that already had one (`libraryMissing`). Review rounds 3 and 4 asked for the remaining operations to be exercised: each of the put-back's 20 hooked file operations is now failed in turn by a test, with and without the failed library's `-wal` and `-shm` present, and with the partial staged copy an interrupted staging leaves (row 6). The same pattern (intent, then renames that the next open can finish) applies to any later operation that replaces the library's files.

**F11. Safety copies need a retention rule, or repeated failures fill the device, and the rule must stop at what this layer owns.** Review round 3 found that every failing launch added a pre-migration snapshot and a failed copy to `Recovery/` (about 2.2 times the library) and that nothing removed them; temporary copies abandoned in staging by a crash or an error (a media import's copy can be audiobook-sized) had the same gap. The approach (ADR-0003 "Retention of `Recovery/` and `Staging/Persistence/`"): a retry from the same pre-state reuses the snapshot (equal content digest, which reads every value as stored), `Recovery/` keeps one pre-migration snapshot and one failed copy and keeps pre-restore copies until the user removes them, and every open removes the abandoned entries of this layer's own `Staging/Persistence/`, also before resuming a put-back, since they may be what filled the disk. Review round 4 found that the first version of the staging rule emptied all of `Staging/`, which ADR-0010 and G0.3's `StorageLayout` also use, for intake's durable state: the import journal and the staged jobs, some of them the only copy of an item the share extension already reported as received (plan 8.2 requires a relaunch to finish them; plan 17.1 keeps staging data for live operations and cleans up only abandoned jobs). Built as written in M1, it would have deleted acknowledged imports at every launch (I-03, I-10). The cleanup is now confined to `Staging/Persistence/`, and a test plants intake's layout beside abandoned persistence files and checks it byte for byte (row 6). ADR-0003's and ADR-0010's on-disk layouts still differ and must be reconciled before M1 builds both (open question 8). The product must show `Recovery/` with sizes and a remove action (M1 recovery journal, M7 retention controls); an age-based expiry of the kept snapshot is a product decision.

**F12. GRDB stores and reads TEXT as C strings.** GRDB 7.11.1 binds a Swift `String` with `sqlite3_bind_text(..., -1, ...)` and decodes TEXT with `String(cString:)`. A string holding U+0000 is therefore stored cut off at the NUL; a stored text holding a NUL (which only a crafted database or another tool can write) reads back cut off; and invalid UTF-8 reads back with replacement characters. `SchemaTests.nulTextIsRefused` shows it on host and simulator: binding `"before\u{0}after"` stored `6265666F7265`, and the 12 stored bytes `6265666F7265006166746572` read back as `"before"`. Found while fixing review round 4's finding that the snapshot-reuse digest hashed GRDB's decoded strings and so could not see text after a NUL. In the spike: the digest and the canonical dumps read TEXT as stored bytes (`ExactRows`); the store refuses text containing U+0000 before writing anything (`ValidationError.textContainsNUL`), so "Saved" never stands for a quote or note stored cut off (I-03, I-05); and `RowCheck` refuses a backup's database holding a NUL or invalid UTF-8 in any TEXT value (row 7). For the product: text extracted from a PDF or pasted by the user can in principle contain U+0000, so the capture and note commands must refuse it with a clear message or remove it visibly before saving, never store it cut off. Re-check GRDB's text binding on every upgrade.
