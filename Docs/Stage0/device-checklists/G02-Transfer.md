- Phone: the paired iPhone 17 Pro (iOS 26.7) and, for step 11, the oldest supported iPhone when available. Developer Mode on.

On 12 October 2026 this Mac had neither, and on 13 October 2026 Xcode still reported "No Accounts" (round 3 clean run; earlier the agreement was not accepted: `Docs/Stage0/evidence/G02-Transfer/keychain-identity-signed*.log`). Check first by building the scheme `G02TransferHarness` for the iPhone once in Xcode; a "No Accounts", provisioning or license error means this must be fixed before any step below.
- One library folder and one port for the whole run (runbook correction C33). Make the folder once: `mkdir -p ~/SylviaDeviceTest/library`, `cp Fixtures/epub/se-walden.epub ~/SylviaDeviceTest/library/` and `cp -c "$(Scripts/fixtures/generate-g02-transfer-large.sh --print-path)" ~/SylviaDeviceTest/library/` (an APFS clone), after generating or checking the 5 GiB file with `Scripts/fixtures/generate-g02-transfer-large.sh` (without `--print-path`, which only prints where the file should be; C37). Start every source of steps 2-22 with `--root ~/SylviaDeviceTest/library --port 47800` (any free port, the same each time) and its default state folder, except the rogue of step 3 and the changed key of step 10: the phone keeps the address and port it paired with, and the source numbers its items by root folder and file name. In step 6, pair over the LAN first, then start the same source on its Tailscale address.
- Free space: the phone needs about 12 GB free. The first imported 5 GiB copy stays in the harness (5.4 GB), and each later 5 GiB job needs about 5.4 GB more until it finishes; let each job finish, or cancel it, before the next starts. This holds while the 5 GiB item keeps one version (one library folder, above).
- Build the Mac source: `source Scripts/lib/env.sh && xcrun swift build --package-path Spikes/G02-Transfer/SourceService --product sylvia-source`. The binary is in `Spikes/G02-Transfer/SourceService/.build/debug/sylvia-source`.
- Phone harness: the app `G02TransferHarness` ("Sylvia Transfer Spike", `Spikes/G02-Transfer/iOS`; `sylvia_generate Spikes/G02-Transfer/iOS`, open `G02Transfer.xcodeproj`, scheme `G02TransferHarness`, team A4KBDX665Z, run on the iPhone). It has a pairing field (paste the code or link; "Scan QR code" on a device), the fingerprint in groups of four, "Browse catalog" and "Download", "Check inbox" and "Download from inbox" (what the Mac queued with `send`), a manual "Host or IP" + "Port" field, "Browse the local network" (Bonjour), the transfer list (stage, "received", "verified", parts, Pause/Resume/Cancel, the next step when paused) and recent events. Step 1 uses the hosted tests of the same project.
- The app keeps an event log with IDs, counts, addresses and app states only (no codes, tokens or titles): `Library/Application Support/Transfers/events.jsonl` in its container. Download it with Xcode > Window > Devices and Simulators > the app > Download Container, and attach the `.jsonl` file to the step record. `Spikes/G02-Transfer/Scripts/analyze-relaunch.py <events.jsonl> <source output>` summarises it per launch.
- **The logging source** (steps 8, 9, 13 to 16, 21 and 22, wherever a step asks for "the Mac's request log" or `source.log`): build `sylvia-test-source` the same way (`--product sylvia-test-source`; it lands next to `sylvia-source`) and start it with this exact command line, adding the step's own options (for example `--state <dir>` or `--test-close-connections`):

  ```
  sylvia-test-source --root ~/SylviaDeviceTest/library --port 47800 --lan --test-log-requests --qr 2>&1 | tee /dev/tty \
    | sed -l -E 's/(SYLVIA1-|sylvia:\/\/pair\/v1#)[A-Za-z0-9_-]+/[pairing code redacted]/g' > source.log
  ```

  The terminal shows everything the source prints, including the pairing code, the link, the QR code (`--qr` draws it on the terminal only) and the approval prompt with the Mac's fingerprint, and you answer the prompt there (`y`, Return). `source.log` gets the same lines with the code and the link replaced by `[pairing code redacted]`, the request log with timestamps (`request <time> <method> <path> range=<r> -> <status>`), and never the QR code. Do not redirect the source's output straight into a file (`> source.log` alone): the code, the link and the prompt would then go only into the file, so you could not compare the fingerprint before approving, and the file would hold the invitation secret (review finding R3-03). End the source with `quit`. Before attaching the file, check that `grep -cE 'SYLVIA1-|sylvia://pair/v1#' source.log` prints `0`. When a step restarts the source, log the second run into a new file (`source-2.log`). The CI drop-in runs this command line on the host with a stand-in for the phone (step `cli-logging-recipe`, `Docs/Stage0/evidence/G02-Transfer/cli-logging-source-recipe.log`). Do not use any other `--test-*` option on a device run unless the step says so.
- Record each step in `Docs/Stage0/evidence/G02-Transfer/device/<NN>-<short-name>.md` with: date, device model and iOS version, Mac macOS version, the commit hash, passed-device or failed, what was seen, and the attached screenshots or logs named in the step. Never put a pairing code, token or invitation secret in a screenshot or log: redact the code line (`[pairing code redacted]`).

### 6. Tailscale address from the phone on cellular (T43)

This step checks the same on a device, with both builds.

1. Phone: Wi-Fi off, cellular on, Tailscale connected. Mac: `sylvia-source --root ~/SylviaDeviceTest/library --port 47800 --bind <Mac's Tailscale IPv4> --advertise-host <Mac's MagicDNS name>`.
2. With `G02TransferHarness` (no ATS key): pair with the printed code. **Expected (from the simulator; confirm or contradict):** pairing fails with a TLS failure and the Mac shows no pairing request (nothing was sent). Then try a manual address with the Tailscale IP and with the MagicDNS name on a source paired over the LAN first: both refused the same way.
3. With the ATS probe app (scheme `G02TransferATSVariant`, build setting `G02_ATS_VARIANT=tailnet-exception`, app "Sylvia ATS Probe"; build and install it with `xcodebuild build -project Spikes/G02-Transfer/iOS/G02Transfer.xcodeproj -scheme G02TransferATSVariant -configuration Debug G02_ATS_VARIANT=tailnet-exception -destination "id=<device UDID>" -derivedDataPath Spikes/G02-Transfer/iOS/.build/DerivedData-ats -disableAutomaticPackageResolution -allowProvisioningUpdates -allowProvisioningDeviceRegistration DEVELOPMENT_TEAM=A4KBDX665Z`, then `xcrun devicectl device install app --device <device UDID> Spikes/G02-Transfer/iOS/.build/DerivedData-ats/Build/Products/Debug-iphoneos/G02TransferATSVariant.app`): pair and download one file through the IP and through the MagicDNS name. **Expected:** both work; no public port or relay is involved (the Mac binds only the Tailscale address); the digests match.

### 8. Token after reboot and while locked (plan 14.2, 18.1)

Two different states, which the client must treat differently: **before the first unlock** after a restart the store (class C) and the token cannot be read and the client defers its launch; **locked after the first unlock** both are readable and the client must start and run (a background relaunch while locked must not defer). `UIApplication.isProtectedDataAvailable` is false in both states, so the client does not use it (review finding R2-01); the harness only logs it.

1. Pair, then queue a large item for the phone on the Mac: `items` lists the item IDs, `devices` the phone's device ID (the **last** `active` line: each pairing gives the phone a new ID, and the phone keeps only the newest token; the `device` field of the newest `paired` event in `events.jsonl` is the same), then `send <item-id> <device-id>` (the Mac prints `queued <entry-id> ... state queued_on_mac`). On the phone, under the paired Mac, tap "Check inbox": the entry appears as `observed_by_phone` (the Mac's `queue` command shows the same). Tap "Download from inbox: <title>" to start the background download. ("Browse catalog" > "Download <title>" also starts a download, but then no queue entry is acknowledged.)
2. Restart the phone and do not unlock it. Wait five minutes with the Mac source running.
3. **Expected:** no bytes are fetched before the first unlock (neither the token nor the job store is readable; the client defers its launch, step 15); the job keeps its verified parts; nothing is deleted.
4. Unlock once, then lock the phone again and leave it for ten minutes.
5. **Expected:** the background download continues while locked (after first unlock the token is readable) or waits for the system to schedule it; it never claims Ready before the full SHA-256 check. In `events.jsonl`: `protected_data_will_become_unavailable` when the phone locks; if iOS relaunches the app in the background while the phone stays locked, its `app_launch` has `protected_data_available=false` and is followed by `coordinator_start` (also `protected_data_available=false`) and `launch_reconciliation`, **never** `start_deferred` or `background_events_released`. A `start_deferred` while locked after the first unlock fails this step.
6. **Expected after the import** (`imported`, or `import_already_recorded` for a version imported before): the Mac's `queue` command shows the entry `imported_into_sylvia` (the phone's receipts named it).
7. **Record:** the Mac's request log (`source.log` of the logging source, "Before you start"; `queue` output), the phone's job state before and after unlock, `events.jsonl`, and the times of the restart, the unlock and the lock.

### 13. Background download while the app is suspended and the phone is locked (plan 6.4, 15.2 gate)

On the simulator (`Docs/Stage0/evidence/G02-Transfer/simulator/relaunch-*.log`, raw event lines): after the app was killed, tasks created in the foreground kept running in the system's daemon; about 4 s later the system relaunched the app in the background once, delivered the finished parts, and the app answered the waiting trust challenges of foreground-created tasks (`app_state=background_relaunch`). The tasks the app created during that background relaunch opened no connection in the following 59 s, and the system did not wake the app again in that time, so finished parts waited for the next launch. Apple documents that transfers started while the app is in the background are treated as discretionary; the simulator cannot tell that apart from tasks waiting for a trust answer. A device may schedule differently, and on battery or cellular it may defer discretionary tasks for longer; this step measures it.

1. Mac: the logging source ("Before you start", with the run's library folder and port), logging into `source.log`. Pair (compare the fingerprint on the terminal with the phone's before typing `y`), start the download, wait for two verified parts.
2. Press the side button (lock) and leave the phone untouched for 15 minutes; do not open the app.
3. **Expected (to be measured, not assumed):** the Mac's request log keeps receiving part requests while the phone is locked; the app's event log shows `trust_challenge` entries with `app_state=background` or `background_relaunch` for new connections and `part_verified` entries in those states. The phone was unlocked before, so every launch while it is locked must start the client: `coordinator_start` and `launch_reconciliation` with `protected_data_available=false` are expected, and `start_deferred` fails this step (review finding R2-01: an earlier version deferred every launch while the phone was locked, which would have made this step measure a stall caused by the app). `background_events_finished` should follow each background relaunch. Note how long the transfer stalls, if it does, and whether it resumes without opening the app. For every `part_requested` entry with `app_state=background` or `background_relaunch`, note when (if ever) `source.log` shows that range: this tells whether tasks created in the background run while the phone stays locked.
4. Repeat with `--test-close-connections` added to the source (log into `source-2.log`). **Expected:** to be measured; if progress stops until the app is opened, record the stall length. This decides whether the background claim needs more tasks created while the app is in the foreground, long-lived connections, a certificate the system can validate without the app, or a foreground-only promise (ADR-0008, report finding 4).
5. **Record:** `source.log`, the app's `events.jsonl` (container download), timestamps of lock and unlock.

### 15. Reboot before first unlock with a transfer in progress (plan 18.1, T41)

Before the first unlock the transfer store's files (class C) and the token cannot be read. The client detects that from the files themselves (a store that exists but cannot be read) and defers its whole launch: it creates no session (so it neither adopts nor cancels any outstanding task), pauses nothing and writes no store; if the launch was a background relaunch it releases the system's completion handler at once (`background_events_released`); it starts again when iOS reports protected data available, or at the next launch (`start_deferred` and `protected_data_available` in the event log). The event log (`events.jsonl`) is a class C file too, so entries from before the unlock may be missing; the Mac's request log is the primary evidence. On the host this is tested with files made unreadable (`background-host/unreadable-stores-deferred.log`); whether iOS relaunches the app before the first unlock at all, and what the system does with the outstanding background tasks meanwhile, only a device shows.

1. With the logging source ("Before you start"), start a download; after a few verified parts restart the phone and do not unlock it for five minutes.
2. **Expected:** no request reaches the Mac before the first unlock. If the app is launched in that time (it may not be), its event log has `start_deferred` with the reason `sources_not_accessible`, `imports_unreadable` or `job_store_not_accessible` and nothing else from the transfer client (no `launch_reconciliation`, no `paused`, no `blocked_at_launch`). After unlocking: `protected_data_available` (if the app was running), then one `launch_reconciliation` that keeps the verified parts; the transfer finishes and is imported once (`imported`, or `import_already_recorded` for a version imported before). Nothing verified is lost and `sources.json` still lists the paired Mac.
3. **Record:** the Mac's request log with timestamps, `events.jsonl` (`start_deferred`, `protected_data_available`, `launch_reconciliation`, `store_protection`), screenshots before and after unlocking.

### 18. Local-network permission prompt timing in the harness (T43, plan 15.1)

### 21. A full phone during a background download (plan 15.4; review finding R2-02)

For a background session the system writes each 16 MiB part into the app's container itself before the app sees it. When that write fails on a full phone the task ends with an error and the app never gets the file; the client classifies such errors as this phone's storage (`insufficient_space` at once when out of space or when less free space than a part remains, otherwise `storage_unavailable` after retries), never "Make sure the Mac is awake". On the host this was tested with an injected task error and a substituted free-space figure (`background-host/system-download-not-stored-*.log`) and with a really full disk image for the app's own writes (`background-host/full-phone-storage.log`); which error iOS reports for its own failed write is unknown until this step.

1. With the logging source ("Before you start"), start a download of the 5 GiB file. When about a quarter is verified, fill the phone's storage until Settings > General > iPhone Storage shows less than about 100 MB free (for example by recording a long 4K video, or by copying large files into Files > On My iPhone), without closing the harness.
2. **Expected:** the job pauses with "Free up space on this iPhone, then resume. Verified parts are kept." (`insufficient_space`), either from the reservation before the next request (`space_check_failed`) or from a failed part (`system_download_not_stored`, or `part_failed failure=localStorageFull`); it does not end as `source_unreachable`; verified parts are kept. Note the exact `error=` value of any `system_download_not_stored` entry (the error domain and code iOS used).
3. Delete the filler and tap "Resume". **Expected:** the transfer finishes with the pinned digest and requests only parts not yet verified.
4. **Record:** `events.jsonl`, screenshots of the paused and finished states, and the free space shown in Settings at the pause.

### 22. The 5 GiB full-file check when the last parts arrive while the phone is locked (plan 6.4, 15.5; review finding R3-04)

When a job's last part is verified, the client checks the SHA-256 of the whole file before it hands the file over (`assembly_started`, then `assembly_verified` with `milliseconds`). For a 5 GiB item that is a full read: 2.1 to 2.3 s on the build Mac when it was lightly loaded, and 29 s once under heavy parallel load (`Docs/Stage0/evidence/G02-Transfer/review/round3-5gib-dev-run.log`); unmeasured on a phone. A background relaunch gets limited time from iOS. The client holds the system's background-events completion handler until the check has published its result (`background_events_completed_after_assembly`), but that does not extend the time: iOS may suspend the app earlier. The job then stays `assembling`, and the next launch re-hashes the verified parts (`staging_checked`) and repeats the check from the journal. That is correct, but it may repeat until the app runs long enough, typically in the foreground. Step 11 measures the check only with the app open; this step measures it in the background. Nothing in the spike asks iOS for extra background time (`beginBackgroundTask` or a `BGProcessingTask`); ADR-0009 lists that as an M1 item.

1. Mac: the logging source ("Before you start", with the run's library folder and port). Pair and start the download with the phone unlocked and the app open.
2. When the phone shows about 300 of 320 parts verified, press the side button (lock) and leave the phone locked and untouched for 30 minutes. Do not open the app.
3. Unlock, open the app, and download its container (`events.jsonl`).
4. **Expected (to be measured, not assumed):** from `events.jsonl`, in order: the `app_state` of the last `part_verified` events; each `assembly_started` and its `app_state`; whether `assembly_verified` (with `milliseconds` and `app_state`) and `imported` follow before the unlock (`background` or `background_relaunch`) or only after the app was opened (`foreground`); each `staging_checked` with its `milliseconds` (a launch that re-hashed the parts); each `background_events_launch`, `background_events_finished` with `waiting_for_assembly=true`, and `background_events_completed_after_assembly`. A job still `assembling` at the next launch is not a correctness failure (nothing is handed over before the check passes): report it with the number of launches the check needed. The step fails if the file is ever imported without an `assembly_verified`, imported twice, or if the final SHA-256 is not `d2383fe38d8033b62ef9e6222756369fab813d2c64b2bce41e86ad9494af16d9`.
5. Repeat once on the oldest supported iPhone if available (the check is slowest there).
6. **Record:** `events.jsonl`, `source.log`, the lock and unlock times, the phone models, and a short summary: how many launches the full-file check needed, and whether it ever finished while the phone was locked. This decides whether M1 must request background time around assembly and receipts.
