# The review of the M0 exit preparation: its fix (26 October 2026)

An agent review read branch `m0-exit-prep` at `609ed492`, the last commit of the M0 exit preparation's assembly (integration log section 30), and the workflow relayed two findings, as the complete list:

- **SEC-ZIPGUARD-01** (major): the Zip guard, `Scripts/check-dependency-lock.py`, judged a product manifest's local package only against `Spikes/` and the product roots. Every other path a product manifest names inside `Apps/` and `Packages/` must hold what git tracks (since review round 3, R3-01), but a local package there was never held to that rule, so a `project.yml` or `Package.swift` could depend on a package in a package's own `.build/checkouts`, or in a directory that holds only untracked files, and the check passed, though it read neither that package's manifest nor its sources. ADR-0014's rule 5 (section 1) says product code comes only from what git tracks under the product roots, and the gate summary's row 76 gives the guard as closing the routes of that kind. The review reproduced it as b00, b02 and b03, with b01, the same package outside the product roots, as its control, which the check did report; no product manifest in the tree used the route.
- **SEC-ZIPGUARD-02** (minor): the gate summary's item 22 gave the self-test's counts of 20 October 2026 ("has 239 mutations ... all 111 of its failure branches") in the present tense, while they were 278 and 119.

Which lenses reviewed the branch was not relayed, and no record of the review is committed beyond what this folder and integration log section 31 record. The review's own reproduction scripts are in its worktree, which this fix did not read; the routes here were planted again from the findings' text.

## What changed

- **SEC-ZIPGUARD-01.** `check_product_manifest` now fails a product manifest's local package inside the product roots whose `Package.swift` is not a file git tracks there (category `outside-product`, the message naming the package and, where it is, a build or package-checkout directory). A tracked package's manifest is one the check reads as a product manifest, and its sources files it scans, so a tracked local package is checked as product code; an untracked one is read by nothing, yet a build compiles and links it (part 2 of `reproductions.log`). The rule applies whichever targets use the package, as the rules for a local package under `Spikes/` or outside the roots do. The self-test has five mutations for it (the review's three routes, in the synthetic tree; XcodeGen's `localPackages` form; and a local package path naming a tracked directory with no `Package.swift`, since tracked content alone is not enough) and one allowed change (a product package that depends on another by a path inside the roots, whose manifest git tracks): 283 mutations (278 before), 36 allowed changes (35 before), and all 120 failure branches (119 before) reached. The module docstring, ADR-0014's rule 5, section 3 (its routes and the self-test's counts), status, Evidence, a consequence and the security reviewer's open item describe the rule; the gate summary's row 76 and its checker, which reads this folder's log of `12-dependency-lock` too, record it.
- **SEC-ZIPGUARD-02.** Item 22 gives its counts in the past tense, with a dated note on the counts since; row 76 and item 105, which gave 278 in the present tense too, likewise.
- **The review's status**, wherever the records gave the exit preparation as not reviewed: the gate summary's State line (199 words, within the 200 the fourth fix's recheck allows), Sections 1, 6.1, 6.2 (a row for the review), 6.3 (items 109 and 111-113), 7 and 8, item 4 and the Branch line; the integration log's 30.6 and its new section 31; the ADR index's row of ADR-0014; the Stage 0 README; the runbook's Who wrote it (this fix's only change to the runbook); and the READMEs of the Zip guard's and the assembly's evidence.
