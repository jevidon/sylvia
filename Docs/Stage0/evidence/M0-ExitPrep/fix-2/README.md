## What changed

- **SEC-ZIPGUARD-03, in the guard** (`4d72eeca`, `Scripts/check-dependency-lock.py` alone). The check fails, under the product roots, every file whose name begins with `Package@` and ends with `.swift`, in any letter case (category `manifest-input`): a product package keeps one manifest, `Package.swift`, the one the manifest-input rule reads. The rule does not depend on SwiftPM's rule for choosing among such files, which part 2a of `reproductions.log` shows on the pinned toolchain: `dump-package` evaluated `Package@swift-6.4.swift`, `Package@swift-6.swift`, `Package@swift-6.4.0.swift` and the names `package@swift-6.4.swift`, `Package@Swift-6.4.swift`, `Package@swift-6.4.SWIFT` and `PACKAGE@SWIFT-6.4.SWIFT` instead of a `Package.swift` of the same tools version beside them, and kept `Package.swift` beside `Package@swift-7.swift`, `Package@swift-5.9.swift`, `Package@swift6.4.swift` and `Package@swift-6.4.swift.bak`. A name such as `Package@2x.png`, an image's, is not one. A spike package may keep a version-specific manifest, as spike manifests may read the environment. The cache of `dump-package` results is now keyed by every file there that SwiftPM could take as the manifest, not by `Package.swift` alone, so a synthetic tree that adds one beside an unchanged `Package.swift` is evaluated again.
- **Routes of the same kind, found with the fix** (the same commit). SwiftPM matching the version-specific name in any letter case led to reading every name the check reads as it spells it against the tools. The default macOS file system ignores letter case: git checks a path tracked as `packages/...` out into `Packages/`, where SwiftPM compiles it (part 2e), while the check judged a file by the root its path names, so it read such a file as neither product nor spike code; SwiftPM and XcodeGen, which open `Package.swift` and `project.yml` by name, load `package.swift` and `Project.yml` (part 2c), which the check, reading manifests by their exact names, did not read; and clang loads `MODULE.MODULEMAP`, `Module.ModuleMap` and `MODULE.MAP` as a directory's module map, and `module_private.map` beside a `module.map` (part 2d), which the check did not read either. The check now fails a tracked path whose first directory is a product or spike root in another letter case and a manifest named `Package.swift` or `project.yml` in another letter case, anywhere (new category `letter-case`), and reads module maps by every name clang reads them by, in any letter case. A Swift file whose extension is `.swift` in another case is compiled by neither SwiftPM nor an XcodeGen project (part 2c), so the import scan's reading of `.swift` files by that spelling stays as it was.
- **The self-test**: eight mutations (the review's route, the same in another letter case, a product root, a product package's manifest, a product project and a spike package's manifest, each in another letter case, and a module map named `MODULE.MODULEMAP` and a `module_private.map`, each naming a transitive public header) and two allowed changes (a spike package's version-specific manifest with product files whose names only begin like one, an image named `Package@2x.png` among them; and a module map named `Module.ModuleMap` that names its own header): 291 mutations (283 before), 38 allowed changes (36 before), 24 categories (23), and all 123 failure branches (120 before) reached by the mutation written for them.
