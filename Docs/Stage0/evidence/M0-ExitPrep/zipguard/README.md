# ADR-0014 review round 4: R4-01 and R4-02 answered in the Zip guard, review pending

The final agent review of the dependency lock (round 4, verdict reject, at `67682c2`) found two routes around the CI guard that keeps marmelroy/Zip 2.1.2 (CVE-2023-39135) and spike code out of product code: **R4-01**, XcodeGen expands `${VAR}` from the environment, so a product `project.yml` could reach `Spikes/` code, add `-import-module Zip` or use a test-only package with no literal value for the check to judge; **R4-02**, C-family `#include` paths were judged only against `Spikes/`, so an include outside the product roots or into a package checkout passed. Plan 23.3 (A56) has the security sign-off accept the advisory's residual risk only once both are closed, so the M0 exit waits for them (`Docs/Stage0/M0-gate.md`, Sections 1 and 6.1, row 76).

## What changed

`Scripts/check-dependency-lock.py` (and its drop-in's header, `Scripts/ci.d/12-dependency-lock.sh`), as ADR-0014 sections 1 and 3 now describe:

- **R4-01, and what XcodeGen and SwiftPM evaluate besides the manifest's text** (new category `manifest-input`): a key or value of a product `project.yml` that holds `${` (XcodeGen replaces it from the environment, and in a target template from the target's name, platform or a template attribute; a YAML escape such as `\x24{` is the same text once parsed) or starts with `~` (XcodeGen does not take such a path from the project's directory); a product `Package.swift` that imports anything but PackageDescription and CompilerPluginSupport, or names `Context`, `CommandLine`, `readLine`, `_silgen_name`, `_cdecl`, `_extern`, a random number or a clock, or holds an `#if`.
- **R4-02, and the other ways a file comes in** (category `outside-product`): product code that is not a test brings in a file (`#include`, `#import`, `#include_next`, `#embed`, the assembler's `.include` and `.incbin`, inline assembly included; assembly, Metal, OpenCL, lex, yacc, MIG and IIG sources read as C-family) by a name that is absolute, that climbs out of the directory it is found in with `..` (unless, quoted, it resolves beside the including file to a file git tracks under the product roots), or that passes through a build or package-checkout directory, or by a computed include; a build-settings file `#include`s a file that is not one git tracks under the product roots (`<DEVELOPER_DIR>/...`, an untracked `#include?`, a path with a variable, a line it cannot read); a shipping target declares build rules.
- **R4-03** (a minor finding of the same review, the same reasoning): a product manifest or build-settings file assigns a variable the check evaluates itself (the build-product, SDK, toolchain and project-directory variables; `SDKROOT` to an SDK's name excepted).
- **R4-04** (likewise): `-Werror` and `-Wwarning` take a diagnostic group only in the Swift compiler's flags; in a C or linker flag setting the word after them is an input file, and fails.

The self-test now has 278 mutations (239 before; 39 added, one per route) and 35 allowed changes (30 before), and every one of the check's 119 failure branches (111 before) is reached by the mutation written for it. The repository itself passes unchanged: nothing in `Apps/` or `Packages/` uses any of these routes (no product `project.yml` holds `${` or a leading `~`, `Packages/Design/Package.swift` imports only PackageDescription, and there is no product C-family file).
